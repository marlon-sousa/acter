About Acter

Acter help

Six short sections: what Acter is, moving around the window, who gets your keys, connecting to a shell, sessions Acter has set up, and the dialog that asks. Use your reader's heading key to move between them.

What Acter is

Acter is a terminal you use by listening. You type a command, it runs in a shell, and Acter reads out what the command prints.

Everything it reads is also kept in the results area, above the command line, so you can go back over it at your own pace with the arrow keys. Each command you run gets a heading there, so your reader's heading key moves you from one command to the next.

Moving around the window

The command line is where you type. F6 moves between it and the results area, and Escape brings you back to the command line from anywhere in the window.

F1 opens this help. F10 opens the menu bar, and so does pressing and releasing Alt on its own.

F1 opens this help, and so does Command and slash. Acter's menus are in the menu bar at the top of the screen, with the rest of the Mac's menus: Connect is in the File menu, and Command and K opens it from anywhere in the window.

Ctrl+C, pressed in the command line, stops the command that is running. In the results area the same keys are your reader's own copy command, so they never reach the shell.

Who gets your keys

When you type, your keys are processed either by the program you are running or by Acter. Ctrl+Shift+K changes which, and Acter says which it is each time you connect.

The remote process gets them to start with, so its own line editing works: up arrow brings back what you ran before, Tab completes a name, and Ctrl+R searches its history. Acter reads back the line it draws as you move through that line, so you hear the recalled command, what a completion added, or the character you just moved onto.

Acter processing them instead means nothing is sent until you press Enter. The line is yours to write and re-read first, which is worth having over a connection too slow to answer each keystroke, or in front of a program that shows nothing while you type. What you give up is everything in the paragraph above: the program's history, its completion and its own keys, none of which Acter has of its own.

Connecting to a shell

A window with nothing running has one button, Connect. It opens a dialog with a list of the kinds of shell you can start: Command Prompt, PowerShell, WSL, and a shell on another computer over SSH.

Some kinds need something more before they can start. WSL needs to know which distribution, PowerShell which edition, and SSH the computer and the account. That is what the panel below the list is for, and it starts with nothing chosen, so nothing is ever connected to on your behalf. Enter connects, from anywhere in the dialog.

While the connection is being made, a dialog says so and names what it is connecting to. Some far ends ask you something first, such as a password. When the session is up, the window says what you are connected to.

When a session ends, because you typed exit or the shell stopped, everything it printed stays in the results area and the Connect button comes back.

Sessions Acter has set up, and sessions it has not

Acter cannot see inside your shell. It sees what the shell prints and nothing else — the same characters you would see on the screen. Where one command's output ends, and whether that command worked, are things only the shell knows.

A shell can be asked to say them: to mark where each command begins and ends, and to say how each one finished. A session where that has been done is called an integrated session; one where it has not is called an unintegrated session.

Both kinds work. In both, what you type runs, what it prints is read out and kept in the results area, and each command gets its own heading.

In an integrated session you are told when a command fails, and Acter knows when a command has finished — so the prompt is read to you on its own, instead of arriving at the end of what the command printed.

In an unintegrated session you are not told whether a command worked. You can still tell from what it printed, which is what you would do at any other terminal.

Command Prompt and PowerShell are set up by Acter as it starts them, so they never ask you anything. PowerShell tells Acter everything, including whether a command failed; Command Prompt can only mark where each command begins, so it cannot tell you that.

WSL and a shell reached over SSH are not set up when they start. Acter offers to set them up once the session is running, which is the dialog in the next section.

The dialog that asks to set a session up

It shows you the command Acter would run, in a box you can read through character by character, and two sentences: what shell was found, and what setting it up would give you. Nothing has run when this dialog appears.

Run command runs it. Skip leaves the session as it is, and the session then tells you what it will and will not be able to say about your commands. Escape, and any other way of closing the dialog, means the same as Skip.

Do not show this dialog again keeps your answer for that kind of shell, so you are asked about it once rather than every time you connect.

You can also decide before you connect. The box on the Connect dialog, "Let Acter set this session up", is ticked to begin with; unticking it means nothing is offered and nothing is run.
