# 52.1 — A prompt lands in a different place in the buffer from one run to the next.

Lane: lane-1-ui. Board: [../ROADMAP.md](../ROADMAP.md). This file is the entry until a spec absorbs it; the spec's PR deletes it.

**A prompt lands in a different place in the buffer from one run to the next.** Spec: none yet → specify first.

Found on 2026-09-23 while comparing NVDA's reading of the V1 build with main's (PR #71).
Setup: NVDA 2026.1.1 through the screen-readers bridge, `user` persona, silent capture;
the scripted fake with `default_transcript.json` at its normal delays; a saved connection
that starts in far-end line mode. Steps in every run: Ctrl+Shift+K, type `small`, Enter,
type `fail`, Enter, then Ctrl+Home and Down arrow through the buffer.

The same steps gave three different orders for the `acter>` prompt paragraphs:

- Main's build, one run, and one V1 run read a minute after the commands: heading
  `small`, `hello from acter`, `acter>`, heading `fail`, the error line, `acter>`. Each
  prompt comes after its command's output.
- Two V1 runs read straight after the commands: `acter>`, heading `small`,
  `hello from acter`, `acter>`, heading `fail`, the error line, with no prompt after it.
- In one V1 instance, with the embedded WebDriver on port 4690, `#results` held this after
  a third `small`: heading `small`, output, `acter>`, heading `fail`, output, `acter>`,
  `acter>`, heading `small`, output. That is two prompts in a row before the third
  heading, and none after its output.

NVDA read exactly what the WebDriver dump showed each time, so the order is on the page,
not in the reader. V1 changes only CSS and the window theme, so the two builds produce the
page from the same code. While typing, NVDA announced `acter>` straight after Enter and
before the command's output in every run.

Not yet known: whether this happens against a real shell, or only against the scripted
fake's timing.
