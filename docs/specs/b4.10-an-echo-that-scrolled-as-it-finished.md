# B4.10 — an echo whose last characters arrived as a settlement

Roadmap entry 22.13. Measured 2026-08-23, before anything was proposed, because the entry
named three outcomes and forbade drifting between them.

`a_shell_inside_a_shell_does_not_mangle_the_buffer` in `real_session.rs` fails on clean
main: inside `docker run -it --rm alpine sh` every one of the forty flooded rows arrives
in order, nothing is lost and nothing is duplicated, but the flood never gets a block of
its own — its output stays in the block of the `docker run` command that opened the
container.

## The measurement, which decides it

A probe was written that drives the same session through a real `LocalPty` and a real
`AlacrittyEngine` and prints every read and every `TerminalItem` the engine emitted, with
no pump in the picture at all. What it captured, for the submission
`i=1; while [ $i -le 40 ]; do echo acter-row-$i; i=$((i+1)); done` (64 characters):

```
=== submitting (64 chars) ===
READ "i=1; while [ $i -le 40 ]; do echo acter-row-$i; i=$((i+1)); don"
  line    1 appended  " i=1; while [ $i -le 40 ]; do echo acter-row-$i; i=$((i+1)); don"
READ "e\r\nacter-row-1\r\nacter-row-2\r\n … acter-row-25\r"
  line    0 settled   "C:\\Users\\marlo>docker run -it --rm alpine sh"
  line    1 settled   "/ # i=1; while [ $i -le 40 ]; do echo acter-row-$i; i=$((i+1)); done"
  line    2 settled   "acter-row-1"
  line    3 appended  "acter-row-2"
  …
```

**The container's `sh` echoed the whole line.** The second of the entry's two live
explanations — that `sh` genuinely never echoes the rest — is ruled out by the item on
line 1: `"/ # i=1; while [ $i -le 40 ]; do echo acter-row-$i; i=$((i+1)); done"`, complete
to the final `done`.

**The matcher lost it, and the capture says exactly how.** The pseudoconsole cut the read
one character short of the end of the echo. The next read carried that last character
*and* twenty-five rows of output, so within a single `advance` the echo's row was written
to and then scrolled out of the screen area — and the extractor emits a row that leaves
the screen area as `Settled` carrying its **whole text**, not as `Appended` carrying the
missing `e`. `Pump::boundary` returns early on any revision that is not `Appended`,
clearing its accumulator, so the completed echo is thrown away and the accumulator is left
holding `/ # i=1; while [ $i -le 40 ]; do echo acter-row-$i; i=$((i+1)); don` — a suffix
match that can never succeed. (The roadmap recorded the cut at `do ec`; where the read
lands varies run to run, which is itself the point.)

That is the entry's first outcome — **the matcher is losing an echo it should have
caught** — and it is the only one of the three that is a real defect. It was not a wrap
and not a non-consecutive line item, so B4.4's note about a container's `sh` starting a
new line item is not what happened here.

**It is also a chunk-dependence, which this codebase already forbids.** Had the reads been
cut one byte at a time, every character of that echo would have arrived as an `Appended`
delta, the accumulator would have matched, and the block would have opened. The same
session therefore says two different things depending on where the pipe happened to cut,
which is what `every_session_says_the_same_thing_when_every_byte_is_its_own_read` exists
to forbid and what `Pump::boundary`'s own doc comment claims it achieves by matching on
accumulated text rather than on one append.

**So the test is right and the behaviour is wrong.** DESIGN's sanctioned degradation — "no
echo means no block… a coarser buffer with nothing lost" — is for a far end that did not
echo. This far end echoed. The test is left asserting exactly what it asserts today.

## Decision 1 — a revision that carries the whole row replaces the accumulator

`Pump::boundary` accumulates `Appended` deltas across consecutive line items, bounded by
`Pump::window`, and that stays. What changes is the other two revisions: a `Rewritten` and
a `Settled` item carry the row's **whole text** rather than a delta, so they **replace**
the accumulator instead of clearing it, and the match is then asked exactly as it is of an
append.

Replace, never push: pushing would double-count the part of the row that already arrived
as appends, which is the whole reason the current code clears.

This is the rule [`Echo`] — the matcher for an *integrated* session's `B..C` region —
already follows, three lines away in the same file: an append accumulates, and "the whole
row, so the prompt has to come off the front of it" for a rewrite or a settlement. The
unintegrated matcher was the one that threw the whole row away.

## Decision 2 — only on the row a submission is pending on

A whole-row revision is admitted to the matcher **only when its `LineId` is
`Pump::pending_row`** — the row the far end's cursor was on when Enter was pressed, which
B4.9 already captures. Every other row's whole-row revision clears the accumulator exactly
as today.

The gate is not decoration; without it the fix introduces a defect worse than the one it
repairs. Settlements arrive for **old** rows, out of order and long after they were
written — the capture shows rows 3 through 8 settling *after* rows 27 through 32 were
appended, because rows settle as the screen scrolls past them. Run `dir` twice and the
first command's echo row `C:\Users\marlo>dir` settles while the second `dir` is still
pending: it ends with the pending line at a word boundary, so an ungated rule would open
the second block on a row the far end wrote minutes earlier, before it had echoed
anything — and the real echo, arriving to an empty queue, would then be read back at the
user as output. Position is what makes the whole row admissible evidence, and only one row
has it.

So 22.12 does decide this entry after all, just not the way its sequencing hoped: B4.9's
`pending_row` is not the fix, it is what makes the fix safe.

## Decision 3 — held text is resolved against the whole row

B4.9 holds what is appended to the pending row and drops it when the echo matches,
stripping the submitted line off the end of the held text and publishing whatever came
before it — a prompt, a banner — so that nothing the far end wrote is lost.

That strip cannot work here, and would reintroduce exactly what B4.9 removed: the held
text is `" i=1; … don"`, which does **not** end with the submitted line, because its last
character never appended. The current code's fallback publishes the held text whole, so
the user's own line would be read back at them, one character short.

With the whole row in hand this is arithmetic instead of a strip. The held text is a tail
of that row and the echo is the end of that row, so where the held text sits inside the
row says how much of it lies in front of the echo: that much is published, the rest is the
echo and is dropped. When the row is not known — a match that came from appends alone —
the behaviour is B4.9's strip, unchanged. When neither applies, the held text is published
whole, because losing text is this product's cardinal defect and a stray duplicate line is
not.

## Rejected

**Quarantining the test.** The entry's third outcome, and it was on the table only until
the measurement came back. A quarantine says "out of reach until an anchor rule exists";
the echo was in our hands and we dropped it.

**Rewriting the test to assert order and completeness instead of block attribution.** The
entry's second outcome, and it is the right test for a far end that never echoed. This one
echoed.

**Admitting whole-row revisions on any row.** Decision 2 gives the failure this produces.

**Making the extractor emit the missing delta as an append before settling the row.** It
would fix this case at the layer where the information is freshest, and it is wrong: a row
that scrolled out inside one read has one honest thing to say — its final text — and B3
decision 6 chose `Settled` for it deliberately, with `Pump::due` already relying on a
settlement being how "a line that scrolled out of the screen area inside a single read"
arrives. The defect is in the consumer that discards it.

## Acceptance criteria

1. An echo whose last characters arrive as a `Settled` item on the pending row opens that
   submission's block, with the submitted line as its heading.
2. The same for a `Rewritten` item on the pending row.
3. A whole-row revision on any **other** row opens nothing, even when its text ends with a
   line that is still pending.
4. The held partial echo is not published as output when the whole-row revision completes
   the match; text in front of the echo on that row still is.
5. `a_shell_inside_a_shell_does_not_mangle_the_buffer` passes against a real container.
6. Every other test in the workspace, and the whole real-shell suite, still passes.

The workspace suite is green with no test quarantined, the real-shell suite including the
Docker case is green on a machine with Docker, and the roadmap entry is Done.
