# B5.4 — the connection catalogue: what can be connected to, and what to say when it cannot

Roadmap entry 23.4. Agreed in conversation 2026-08-25, raised by the user while B5.2 was
being finished: the Connect dialog needs to offer things this machine cannot do *and say so*,
rather than hiding them.

## The problem this solves

Three adapters exist now — cmd, PowerShell in two editions, bash under WSL — and the Connect
dialog (entry 13) will list them. On any given machine some of them cannot be started:
PowerShell 7 is installed separately, WSL may have no distribution registered, and cmd does
not exist off Windows at all.

**Hiding what a machine cannot do is the wrong answer**, and it is worth saying why rather
than treating it as obvious. A list that silently omits WSL teaches a listener that Acter
does not support WSL. A list that offers it and fails on connect teaches them that Acter is
broken. Neither is true: the truth is "this machine has no distribution installed, and here
is how to install one", and that is a sentence the product can say.

## Decisions

### 1. Every kind is always in the list, and unavailable ones sort to the end

The catalogue is the same everywhere; only availability differs. An unavailable kind keeps
its place in the world and loses its place in the *order*: available kinds first in their
own order, unavailable ones after them.

**Why sort rather than hide:** a listener arrowing a list builds a mental model of it, and a
list whose length changes with the machine cannot be learned. Sorting keeps the common case
— pressing Down twice to reach the thing you always use — costless, while leaving the rest
discoverable to somebody who arrows to the bottom.

### 2. The label says it, because a screen reader user is not looking at a greyed-out row

`WSL (not available)`. The words are in the accessible name rather than in a visual state,
because a disabled row that *looks* different and *reads* the same is exactly the failure
this product exists to avoid.

**And the item stays selectable.** A row that cannot be focused cannot be read, and the
whole point is that the user can find out *why*. What is refused is connecting, not
arrowing.

### 3. Choosing an unavailable kind shows instructions, read-only

The panel below the list — the same panel that holds a distribution list for WSL and a form
for SSH (spec A8) — holds a read-only text box with what to do about it.

**Read-only rather than a link or a button**, for two reasons. A listener can read it with
ordinary reading commands, character by character if a command has to be typed exactly; and
Acter never installs anything on a user's machine on its behalf, which is a decision worth
making once, here, rather than per kind.

### 4. The instructions are domain strings, and every one is speakable

They are user-facing text, so they are a domain requirement rather than polish (CLAUDE.md),
and they live beside the kind they belong to rather than in the frontend. Each one says
**what is missing, what to do, and where** — in that order, because a listener hears the
first clause first and needs to know whether the rest is worth their attention.

The command in each is written as something a user can type: `wsl --install`, not "use the
Windows Features dialog". A GUI path a blind user has to navigate by description is worse
than a command they can paste.

### 5. Operating-system gating is a property of the kind, not of the machine

cmd, PowerShell 5.1 and WSL are Windows kinds. A Linux terminal and a macOS terminal will be
kinds of their own when those platforms are built. **A kind that does not belong to this
operating system is not in the catalogue at all** — it is not "unavailable", it is not part
of this product on this platform, and offering `WSL (not available)` on macOS with
instructions to install Windows would be absurd.

So there are two different absences and this spec keeps them apart:

- **Not on this platform**: absent from the catalogue entirely. Decided by the build.
- **On this platform, not on this machine**: present, sorted last, labelled, with
  instructions. Decided at runtime.

### 6. This entry is knowledge, not discovery

What this entry builds is the catalogue and the rules above: which kinds exist, how they
order, what they are called, and what each says when it is missing. **Whether a given
machine has PowerShell 7 or a WSL distribution is I/O**, it belongs behind
`InstalledShells`, and it arrives with B7 — which is the entry that asks the machine and
answers `connectable()`.

So availability is an *input* here rather than something looked up: the catalogue is a pure
function from "what this machine has" to "what the dialog shows". That is what makes every
rule above testable without a machine that happens to lack something, and it is why this
entry can land before B7 rather than after it.

## Files touched

- `crates/acter-core/src/entities/connection_kind.rs` — the kinds, their labels and their
  instructions (new; role: entity/value).
- `crates/acter-core/src/policies/catalogue.rs` — availability, ordering and platform gating
  (new; role: policy).
- `crates/acter-core/src/lib.rs` — the facade re-exports.

## Definition of done

- [ ] Every kind carries a label, and an unavailable one reads `<name> (not available)`.
- [ ] Available kinds sort before unavailable ones, and the order within each group is
      stable and stated.
- [ ] Every kind has instructions; each names what is missing, what to type, and where.
- [ ] Kinds that do not belong to the running platform are absent from the catalogue
      entirely, and a test asserts the Windows set on a Windows build.
- [ ] The catalogue is a pure function of the machine's answer, with no I/O in it.
- [ ] Unit tests for ordering, labelling, platform gating and every instruction string being
      non-empty and speakable.
- [ ] `cargo fmt`, `cargo clippy --workspace --all-targets`, workspace tests clean.

No accessibility checklist: this entry ships no user interface. The strings it defines are
heard for the first time when A8 renders them, and that is where they are listened to.
