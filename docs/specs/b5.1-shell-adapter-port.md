# B5.1 — the `ShellAdapter` port, with cmd behind it

Roadmap entry 23.1. Agreed in conversation 2026-08-23, as the first of the six entries that
reorganised the board around building the backends before optimising over them.

**A refactor that changes no observable behaviour, with one deliberate exception** — the
arguments a real `cmd.exe` is started with, which today differ between the application and
every test that measures it. See decision 5, which is the reason this entry is worth a spec
rather than a commit message.

## What exists

ARCHITECTURE has named `ShellAdapter` as a driven port since the beginning, and lists it
beside `Transport`, `TerminalEngine`, `Clock` and `EventSink`. It has never been written,
because until now there was one shell to know anything about.

What stands in for it is `acter-shells::cmd`: three constants (`PROMPT`, `ENVIRONMENT`,
`MARKERS`), a predicate `is_cmd`, and a two-arm branch in the composition root:

```rust
let (environment, markers) = if cmd::is_cmd(&program) {
    (cmd::ENVIRONMENT, cmd::MARKERS)
} else {
    (&[][..], ShellMarkers::Full)
};
```

That `else` is the null adapter, written as an absence. Two more shells arrive in 23.2 and
23.3, and each of them needs *arguments* as well as environment — PowerShell's whole
injection is a `-Command` snippet, and WSL's far end is chosen by `-d <distro>` — which the
branch above has nowhere to put.

## Decisions

### 1. The trait lives in `acter-core`, and the implementers stay in `acter-shells`

Where ARCHITECTURE already put it: `ports/driven/shell_adapter.rs`. The domain needs to
know what a shell can mark; the world supplies the rest. `acter-shells` keeps its
per-shell modules and gains one implementer per shell.

### 2. Four facts, in two methods

```rust
pub trait ShellAdapter: Send + Sync {
    /// How to start this shell: the program, its arguments, and the environment its
    /// session setup needs.
    fn launch(&self) -> ShellLaunch;

    /// How far this shell's own markers reach.
    fn markers(&self) -> ShellMarkers;
}

pub struct ShellLaunch {
    pub program: String,
    pub args: Vec<String>,
    pub environment: Vec<(String, String)>,
}
```

**The three launch facts are one value rather than three methods**, because they are one
decision. cmd's injection is an environment variable, PowerShell's is an argument, and
WSL's far end is an argument too — a caller that could take the environment of one shell
and the arguments of another would be assembling a session that nobody designed. One value
also makes the whole of a shell's launch a single assertion in a test.

**Markers stay a separate method** because they are a claim made to the *domain*, not to
the transport: `ShellMarkers` decides how the boundary tracker behaves, and it is consumed
by `SessionService`, while the launch is consumed by `LocalPty`. B4.5's rule that the two
must travel together is not weakened by this — it is strengthened, because one object now
owns both instead of a branch computing them side by side.

**Owned `String`s rather than `&'static str`.** cmd's values are constants and could be
borrowed; WSL's cannot, since `-d Ubuntu` is built at runtime. A port shaped around the
one shell whose data happens to be static would have to be reshaped by the third entry in
this group.

### 3. No display name on the port

The connect list needs a label for each thing a user can connect to, and it is tempting to
put it here. It does not belong: the same adapter appears in the list more than once (two
PowerShell editions, one entry per WSL distribution), so the label belongs to the profile
that *selects* an adapter, which is B7's. A port carrying a display string is a port that
has learned about the user interface.

### 4. The null adapter becomes a type

`Plain` — a shell Acter knows nothing about: no arguments, no environment, and
`ShellMarkers::Full`, which is exactly what today's `else` arm produces. It is the honest
name for what it is, and it makes the case reachable in a test instead of implicit in a
branch.

Selection stays where the environment is read. `acter_shells::adapter_for(program) ->
Box<dyn ShellAdapter>` maps a program name to its adapter and answers `Plain` for anything
it does not recognise, so `ACTER_SHELL=cmd.exe` keeps working unchanged and
`ACTER_SHELL=anything-else` degrades exactly as DESIGN's reliability case 2 says it should.

### 5. The adapter owns the arguments, and that closes a real gap

**Production spawns `cmd.exe` with no arguments. Every test spawns it with `/Q /K`.**

```rust
// container.rs
LocalPty::spawn(&program, &[], environment, COLUMNS, SCREEN_LINES)
// local_pty.rs and real_session.rs
Self::over(&["/Q", "/K"])
```

`/Q` turns off cmd's own script-style echo of the commands it runs. With it off — the
suites — the only echo in the stream is the pseudoconsole's echo of what was typed, which
is what B4.9's "no command line is read back" and B6.1's echo-based correlation were
measured against. With it on — the application — cmd re-prints each command itself, and
nothing in any suite has ever seen that stream.

**This is a candidate explanation for 22.14**, the empty level 2 heading a marked cmd
session grows after its first command. That entry established that the backend alone does
not reproduce it and concluded the frontend was implicated — but the backend run was a `/Q`
session and the application run was not, so the two differed by more than the frontend.
This spec does not claim to fix 22.14 and must not be read as fixing it: it removes the
confound, and 22.14 is re-measured after this lands rather than assumed gone.

The arguments themselves are **moved, not re-chosen**: cmd's adapter declares `/Q` and
`/K`, the pair the suites have been measuring against all along. Whether `/K` earns its
place is a separate question and not this entry's.

**The tests stop hardcoding them.** `local_pty.rs` and `real_session.rs` ask the adapter
for the launch instead of spelling arguments out, so the application and the suites cannot
drift apart again by construction. That is the acceptance criterion that matters here.

### 6. No EOF yet

`SessionIntent` still ships with `Interrupt` alone. EOF is shell knowledge and this is now
the port it will live on, but the method arrives with the shell that needs it (23.2, per
the roadmap), not as an empty seat. B1's rule: no speculative surface.

## Files touched

- `crates/acter-core/src/ports/driven/shell_adapter.rs` — the port and `ShellLaunch`
  (new), re-exported from `lib.rs`.
- `crates/acter-shells/src/cmd.rs` — `Cmd`, the first implementer, keeping the existing
  constants as its data and its doc comments as they are.
- `crates/acter-shells/src/plain.rs` — the null adapter (new).
- `crates/acter-shells/src/lib.rs` — `adapter_for`, and the facade.
- `crates/acter-app/src/container.rs` — the branch becomes one `adapter_for` call.
- `crates/acter-transports/tests/local_pty.rs`, `crates/acter-transports/tests/real_session.rs`
  — shells started through the adapter rather than through hardcoded arguments.

## Definition of done

- [ ] `ShellAdapter` and `ShellLaunch` exist in `acter-core`, declared with their module
      role, and are re-exported from the facade.
- [ ] `Cmd` and `Plain` implement it; `adapter_for` maps program names to them and answers
      `Plain` for the unknown.
- [ ] The composition root names no shell: no `is_cmd` branch, no inline arguments, no
      inline environment.
- [ ] The real-shell suites obtain their launch from the adapter, so no test spells out
      `/Q` or `/K` any more.
- [ ] Unit tests: cmd's launch carries the arguments and the `PROMPT` injection and claims
      `PromptAndCommandLine`; `Plain` carries neither and claims `Full`; `adapter_for`
      resolves `cmd`, `cmd.exe`, a full path, and an unknown program.
- [ ] The real-shell suite passes unchanged against a real `cmd.exe` — same markers, same
      correlation, same headings.
- [ ] `cargo fmt`, `cargo clippy --workspace --all-targets` and the workspace test run are
      clean.

No accessibility checklist: nothing user-facing changes and no string is added or altered.
**But 22.14 is re-measured through NVDA after this lands**, because the application's
`cmd.exe` stream changes for the first time since that entry was written, and its recorded
candidates were established under a confound this entry removes.
