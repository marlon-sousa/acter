# B5.8 — zsh is a shell Acter sets up

Roadmap entry 23.16, lane 2. It adds the second measured shell setup, and it is the
first one written for a shell whose hooks are not bash's.

## What is true today

`setup_for` answers `bash` and `sh`/`dash`, and everything else with `None`. A far end
running zsh therefore starts, works, and is told the truth: "zsh, which Acter cannot set
up yet." No blocks, no headings, no exit codes — the grace period expires and the
listener hears why.

That is honest and it is not enough. zsh is one of the two shells a Linux account is
likely to have as its login shell, it is the default on macOS, and every oh-my-zsh user
is one. B5.5's rule is the reason nothing was guessed: **the identity may be guessed from
the name; the setup may never be.** This entry pays that rule's price and measures one.

## What was measured, and where

**zsh 5.9 on Debian bookworm, interactive on a pseudoconsole through `script -qec`**, one
scenario directory per `.zshrc`, each submitting the setup line and then one command that
succeeds and one that exits 7, so a wrong verdict is visible rather than inferred. Then
the same line, **read out of the crate rather than retyped**, in two places that carry real
bytes: over a real `sshd` against the rig's new `zshuser` account, and through a real
`wsl.exe` against a real zsh in Ubuntu 24.04.

## Decisions

### 1. zsh earns `ShellMarkers::Full`, and reaches it by a shorter route than bash

All four markers arrive. The line that produces them is about half of bash's, and every
line it does not have was dropped because a measurement said it could be:

- **No status variable.** bash needs `__acter_status=$?` as the first statement of a
  sandwich, because any hook running before it hands us *its* status — the failure that
  made Acter announce a success for a command that exited 7. zsh has `%?`, a prompt
  escape it expands itself from a status snapshotted before hooks run. Measured against a
  `.zshrc` whose own hook runs a command and returns success: `(exit 7)` still announced
  `D;7`. The failure is unreachable rather than defended against.
- **No firing guard.** `preexec` is a real hook and fires exactly once per submitted
  line. Measured: `true | false`, `for i in 1 2 3; do true; done` and `true; (exit 7)`
  each produced one `C`. bash's `__acter_seen` exists only because a `DEBUG` trap fires
  per simple command.
- **No captured hook.** `precmd_functions` is an array, so ours is appended and the
  user's are left where they are. bash's `PROMPT_COMMAND` is one string with two ends
  anybody can glue onto, which is the whole reason the sandwich exists.
- **No `__acter_started`.** The `D` lives in the prompt rather than in a hook, so the
  first prompt after the setup closes the setup itself. Measured: `D;0`.

### 2. The program is zsh's own, not bash's with a substitution

`$'...'`, `print -n`, `[[ ]]`, `%{ %}` and `%?` are zsh's. This is B9.5 decision 8's rule
meeting its second instance, and the rule has now been paid for twice: `sh` needed its
own program because `\[` is readline's, and zsh needs its own because none of the five
constructs above exist in bash's dialect.

### 3. The re-wrap guard is bash's, and for bash's reason

`[[ $PROMPT == *'133;A'* ]]` asks whether *this* prompt carries the marker. A theme that
rebuilds `PROMPT` before every prompt then costs one cycle rather than the session, which
is the `CDCDC` failure that a one-shot boolean produced under bash. Measured against two
rebuild shapes — a `precmd` function that reassigns `PROMPT`, and an array hook doing the
same — and the full cycle survived both.

### 4. The markers cost no columns, and that had to be measured

Roadmap 23.14 is why: in busybox the same markers cost sixteen columns its line editor
could not see, and dash draws `\[` literally. On an 80-column pseudoconsole with a
four-column prompt, zsh's echo of a typed line began a second row at exactly the same
length marked and unmarked. `%{` and `%}` are honoured. Three shells, three answers, none
of them guessable from the others.

### 5. `0x04` ends a zsh session over SSH, measured rather than inherited

bash's `eof` is `0x04` because B9 sent the byte down a real connection and watched the
session close, and zsh was asked the same question rather than assumed to agree —
because B5.2 measured and *disproved* both obvious candidates for PowerShell. It does
agree, so `over_ssh` answers `0x04` for zsh too.

### 6. The WSL cell is measured too, and measured twice for two different reasons

The setup is keyed by the shell's name rather than by the transport, so a distribution whose
account runs zsh gets this line. What is worth measuring is whether zsh's markers survive
`wsl.exe`'s pseudoconsole — a different cell of the matrix, in the sense that keeps `eof()`
`None` for every shell under WSL.

**The automated test gets there with `exec zsh`, and that is deliberate.** A test may not
depend on the login shell of whoever runs it, and `chsh` in a test would edit a developer's
own machine to make it pass. So it does what a person does when they want another shell: it
replaces the process, and Acter sets *that* up with zsh's own line. Measured 2026-08-31, zsh
5.9 on Ubuntu 24.04: the block gets its heading, the block closes on zsh's own `D`, and
`(exit 7)` is announced as `Failed(ExitCode(7))`.

**The accessibility pass gets there the way a user does, which is what closes the discovery
half.** With the account's login shell temporarily set to zsh — and set back afterwards — the
whole flow was driven with NVDA: the probe read the passwd entry, named zsh, and Acter offered
*zsh's* line in the disclosure dialog rather than bash's. What a listener heard was "connected
to WSL: Ubuntu, zsh". That is the half `exec zsh` can never show, and it is why both exist
rather than either being redundant.

## Definition of done

- A remote zsh draws a marked prompt and `(exit 7)` is announced as `Failed(7)`, with the
  setup line taken from the crate.
- A zsh under `wsl.exe` does the same, so the claim that one mechanism serves every
  transport is measured on both rather than argued from one.
- Acter's own setup line is not read aloud (23.12) at a zsh far end either.
- The four hostile `.zshrc` shapes 23.11 established for bash produce the full cycle.
- No setup writes anything into the far end — the pinned constraint, asserted over every
  program including this one.
- `cargo test --workspace` green; `cargo clippy --workspace --all-targets` clean.

## Accessibility checklist for the PR body

Driven through the screen-readers bridge as `user` where the item can be observed, and
left to a human where it cannot.

- Connecting to a zsh far end, the connection sentence no longer says the shell cannot be
  set up.
- A command run in a zsh session gets a heading, reachable with F6 and heading navigation.
- A command that fails in a zsh session is announced as having failed, with its code.
- Acter's own setup line is not read aloud when the session is established.
- All four again over WSL, against a distribution whose login shell is zsh, so the claim
  that one mechanism serves every transport is heard on both rather than argued from one.

## What implementing it did not settle

**A fresh account with no zsh startup files meets `zsh-newuser-install`**, an interactive
menu that reads a single keypress. Measured 2026-08-31 against the rig before its account
had a `.zshrc`: the setup line's leading `p` was consumed as the menu's answer, the menu
aborted, and the remainder reached the shell as `rint -n ...` — `zsh: command not found`.
The session still ended up integrated, because every statement after the first `;` ran,
which is luck rather than design. Filed as its own roadmap entry; it is a property of the
far end rather than of this setup, and the fix is not "make the line survive losing a
character".

**Powerlevel10k's instant prompt is unmeasured.** It redraws through `zle` rather than
through `precmd`, which is a different mechanism from any of the five scenarios here.

**A hook added after the setup runs is not re-wrapped**, because ours is already in the
array and cannot move behind it. Same shape as re-sourcing `~/.bashrc` under bash, and it
degrades the same honest way.
