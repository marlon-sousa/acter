# V2.4 — a block nothing was printed into is never drawn

Lane 5, the look; roadmap entry 53.4.

## What is true today

Found on 2026-09-24 while checking V2.3 against Windows PowerShell 5.1 (PSReadLine off), in
far-end line mode:

- Run `gh repo create`, press Down Arrow once, then Ctrl+C. `gh` exits, and the buffer holds the
  returning prompt followed by an empty block with no heading.
- Type `echo after` and press Enter. The new block's heading comes after the empty block, so the
  prompt is not followed by a heading, is not floated, and is drawn alone on its line, with
  `echo after` on the line below.
- Measured through the embedded WebDriver: the last children of `#results` were `P.prompt`, then
  an empty `DIV.response`, then `H2: echo after`.
- NVDA 2026.1.1 is unaffected: after the Ctrl+C it said "command failed, exit code 2", then
  "PS C:\Users\marlo>", and the far-end field read blank.

Measured on 2026-09-25 through the `SessionEvent`s a real `LocalPty` session produces, with keys
sent 80 ms apart, in both line modes. The programs stopped with Ctrl+C were `ping -n 100
127.0.0.1`, a Python script that draws and erases a list the way `gh` does, and `gh pr create` on
an unpushed branch, cancelled at its first list. Ctrl+C was also pressed at an idle prompt:

- **Windows PowerShell 5.1, far-end mode, `gh pr create`.** After `CommandFinished`, the verdict
  and `PromptDrawn`, the session sends `CommandStarted { command_line: None }` with no output. That
  block stays open until `echo after` closes it. This is the empty block. It did not happen for
  `ping`, the Python list, idle Ctrl+C, or in local mode.
- **Its cause.** Logging every `PreCommandLookupAction` call showed PowerShell looking up
  `Out-Default` after the prompt was drawn, with nothing typed. The setup's hook prints `C` on
  the first lookup after a prompt, so a `C` arrives that no line caused. The pump's `claim` finds
  nothing submitted, mints an id, and opens a block nobody submitted. At an idle Ctrl+C,
  PowerShell also looked up `prompt` after the prompt, once, with the same effect.
- **A second route to the same block, measured on the V2.4 branch once the first was closed.**
  Tracing the pump showed the settling after the prompt publishing an empty appended row, the
  row below `gh`'s erased list, while no block was open. `unclaimed` opened a block nobody
  submitted for it, `CommandStarted { command_line: None }` went out, and the actor dropped the
  empty append, so the frontend again drew an empty block. Which route a run takes varies from
  run to run.
- **No PowerShell-side signal separates the two.** `CommandOrigin` was `Runspace` for every lookup,
  typed or not, and `[runspace]::DefaultRunspace.GetCurrentlyRunningPipeline()` is null inside
  the hook. `Out-Default` is looked up once per session, when it is first needed, so skipping it
  by name would lose the `C` that a typed `2+2` gets from that same lookup (spec B5.2).
- **cmd, marked and unmarked; `sh` in an Alpine container; bash under WSL, unintegrated.** No
  block without a command line appears in any case.
- **bash under WSL, integrated, far-end mode, idle Ctrl+C.** A block headed `^C` fails with 130
  (roadmap 28.12). After the prompt, a block with no heading opens holding ` ^C`, which was
  printed into. That is roadmap 53.5, not this spec.

Read from the code on 2026-09-25:

- 28.11 (spec B6, amendment A) already names this block: in bash, every empty Enter is a whole
  `C..D` cycle, `claim` mints an id, and the block that closes is nobody's. The pump marks it
  `barren`, and at `D` sends `NothingRan` instead of `CommandEnded`, so no verdict is announced.
- But `open` sends `CommandStarted` for it at `C`. The frontend's `ensureBlock` then appends an
  empty `div.response`, and `NothingRan` reaches the frontend as `CommandFinished`, which leaves
  that `div` in the buffer. Every empty Enter at an integrated bash leaves one, and the
  PowerShell `C` above leaves one.
- `barren` is set only for a block nobody submitted and nothing names, and `output` clears it.
  So a block that is still `barren` when it closes had nothing printed into it.
- `running` counts a `barren` block as a command running, so while PowerShell's stray block is
  open, Acter believes something runs at an idle prompt.

## Decisions

1. **A block nobody submitted is started when its first line with text is printed, not at `C`.**
   When `block_started` or `unclaimed` opens a block that nobody submitted and nothing names, the
   pump keeps the id but sends no `CommandStarted`. The first `output` into that block whose text
   is not empty sends `CommandStarted { command_line: None }` before the `Output`, exactly as the
   block would have looked had it been sent at `C`. An empty line before it is not sent: the
   actor drops an empty append anyway, and it would print nothing.
2. **A block that closes with nothing printed into it was never there.** It sends no ending of any
   kind: no `CommandEnded`, no `CommandInterrupted`, and no `NothingRan`, which goes away with the
   actor's `nothing_ran`. The frontend is told nothing, so there is no `div` to draw. The pump
   still clears `standing` when it opens, so the prompt that follows is announced as today (28.11).
3. **It does not count as running until it is shown.** `running` is true for an open block only
   once it has been started toward the frontend. At an idle prompt after PowerShell's stray `C`,
   Ctrl+C in local mode answers `NothingToActOn`, as at any idle prompt.
4. **A block nobody submitted that prints something is unchanged.** Its `CommandStarted`
   arrives just before its first line, with no heading, and it keeps its verdict
   (`a_block_nobody_submitted_that_printed_something_keeps_its_verdict`).

## What V2.4 does not do

- It does not change the PowerShell setup. The stray `C` still arrives; nothing reaches the
  frontend because of it.
- It does not touch 28.12 (bash's `^C` block and its 130) or 53.5 (a command line's row
  printed after the next prompt).
- It does not change what is spoken.

## Acceptance criteria

1. Session tests:
   - an empty Enter after a failure sends no `CommandStarted`, no `CommandFinished` and no
     verdict, and the prompt after it is still spoken. `the_block_it_opens_is_closed_all_the_same`
     is replaced by this test;
   - after it, Ctrl+C answers `NothingToActOn`;
   - a `C` with nothing submitted, followed by a line, sends `CommandStarted { command_line: None }`
     then that line's `Output`;
   - a `C` with nothing submitted, followed only by an empty line, sends no `CommandStarted`;
   - `a_block_nobody_submitted_that_printed_something_keeps_its_verdict` and
     `a_command_that_fails_silently_and_unrecognised_keeps_its_verdict` pass unchanged.
2. The actor test `a_block_nothing_ran_in_finishes_and_says_nothing` goes with `NothingRan`.
3. All existing tests pass, and the ignored real-shell tests for PowerShell and cmd pass.
4. Against Windows PowerShell 5.1 in far-end mode, the events after `gh pr create`, Down and
   Ctrl+C hold no `CommandStarted` between `PromptDrawn` and `echo after`'s block. A screenshot
   shows the prompt and `echo after` on one line.
5. NVDA 2026.1.1 through the bridge, `user` persona: the same steps speak "command failed, exit
   code 2", the prompt, and then "after", as today.
