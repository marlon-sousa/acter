# B9.6 — `sh` can say how a command went, and nothing Acter says to itself is read aloud

Roadmap entries **23.15** and **23.12**, specified together and agreed in conversation
2026-08-29.

They are one PR because they are one connection: what a listener meets when a `sh` session
comes up. Today Acter's own five-hundred-character setup command is read aloud between the
connection sentence and the prompt, and the session it sets up then gives headings and never
says whether anything worked. After this, nothing is read aloud in that window and a command
that fails says so.

They also help each other. 23.15 gives `sh` a `D`, which means the block Acter's own line opens
now ends on a verdict in every shell that has a measured setup — so 23.12's window has one
closing condition rather than two.

Depends on **B9.5** for the setup mechanism and the marker claim it revises, on **B4.5** for
`ShellMarkers` and the synthesized `C`, on **B5.6** for the prompt as its own announcement, on
**B4.9** for what a submitted line does to a buffer a screen reader reads, and on **B1** for
`ReadMode::Quiet`, which is the mechanism 23.12 needs and which has shipped since.

## What happens today

**A `sh` session gives headings and no verdicts.** B9.5 decision 8 declared
`ShellMarkers::PromptAndCommandLine` for POSIX `sh` on the reasoning that a verdict needs a
post-execution hook and POSIX `sh` has none — only `PS1`. The Connect dialog says so out loud:
"Acter cannot yet tell you when a command fails in this shell."

**And Acter's own setup command is read aloud at connect**, measured on two different far ends
on 2026-08-29, for two different reasons:

- **busybox redraws a wrapped line out of order.** Driving NVDA 2026.1.1 as the `user` persona
  in silent capture against a real `docker-desktop` session, what a listener heard between the
  connection sentence and the prompt was the prompt with two fragments of the setup's echo
  behind it, split and in the wrong order. `sh`'s setup line is 93 characters and busybox's
  prompt is 30, so it wraps at 80 columns and busybox redraws it in an order the echo matcher
  cannot recognise. bash in the same pass is clean and its line is five times longer, so what
  differs is the shell's line editor.
- **`sshd` draws a banner before the prompt.** Found in the SSH rig against Debian bookworm and
  bash 5.2.15 over a real `sshd`. `sshd` prints `Last login: ...` first, so the first *drawn*
  line the setup waits for is the banner and not the prompt, and the row B4.9 holds a
  submission on is a row the echo is never written to. The suppression cannot fire, and the
  listener gets Acter's own command read aloud **twice**: once in the unclaimed block the
  banner opened, once in the setup's own.

In both, what is wrong is what a listener hears and nothing else. The setup worked each time:
the connection sentence is right, the block is headed by the command verbatim, the markers
arrive, the grace period never contradicts any of it, and the user's own commands afterwards
are clean in the same run.

## What is wrong with it

**The verdict half is a wrong conclusion from sound reasoning.** `PS1` is expanded *every time
the prompt is drawn*, and `$?` at that moment is the status of the command that just finished.
Measured 2026-08-29 against busybox 1.37.0 on `docker-desktop` and dash 0.5.12 on Ubuntu:

```
PS1='[status=$?]# '
true       -> [status=0]#
(exit 7)   -> [status=7]#
```

Measured through the whole stack the same day, with `\033]133;D;$?\007` added to the front of
the prompt string and nothing else changed, `(exit 7)` in `docker-desktop` announced
`Failed { exit_code: ExitCode(7) }` — the test asserting that no verdict is forged failed with
`left: Some(ExitCode(7))`, which is the measurement.

**It matters more than one missing feature**, because roadmap 23.14 weighed what setting `sh`
up buys against what it costs and found nothing measurable on the credit side. Headings come
free from the echo (B6.1), output comes free, echo suppression comes free, and the two costs
are real: a heading truncated on a wrapped line without saying so, and Acter's own command read
aloud at connect. The one thing an unintegrated session genuinely cannot offer is whether the
command worked — so a `sh` setup that cannot offer it either is a setup that earns nothing.
This entry is what makes the offer sentence true for this shell.

**The read-aloud half is not a matcher problem and must not be fixed as one.** Both causes are
echo recognition failing, in two unrelated ways: one is a far end redrawing a line, the other is
a far end printing something before its prompt. A better matcher would have to solve both, and
would then have to keep solving them for every far end nobody has met yet. Shortening the setup
line is not the fix either: the prompt's width is the user's, so any length can wrap, and a
banner has no length at all to shorten.

## Decisions

### 1. `ShellMarkers` gains a third state: prompt, command line and exit code

`PromptCommandLineAndExitCode`. It marks where the prompt begins and where the command line
does, it reports how the command ended, and it says nothing about where output begins — so the
boundary tracker synthesizes `C` at the end of the echoed line exactly as it does for
`cmd.exe`.

Adding a variant to a Decided value type is a design decision, which is why 23.15 recorded the
measurement and left the change for this conversation.

**It supersedes B9.5 decision 8** for what `sh` claims. The mechanism that decision built — a
`sh` program of its own, never bash's with a substitution — stands entirely; what changes is
how far that program reaches. An amendment note rides in the B9.5 spec.

### 2. The question two rules were asking is the verdict, not the full cycle

`ShellMarkers::marks_output_start` is joined by `ShellMarkers::reports_exit_code`. Two rules in
the session pump asked "is this `Full`" when what they meant was the second one, and until now
the two questions had the same answer in every shell that existed:

- **`Pump::drawn`** decides whether the prompt is announced on its own. A shell with a verdict
  ends its commands on the verdict, so its prompt is news rather than an ending.
- **`Pump::marked`** decides whether the prompt is a block's content. Same reason, other side:
  with a `D` to end on, a prompt arriving inside the block would read as something the command
  printed.

The boundary tracker needs no change at all: it asks only `marks_output_start`, the `D` arrives
before the `A` and closes the block with a code, and the `B` that follows finds nothing open.

The Connect dialog's offer sentence and the connection sentence follow from `reports_exit_code`
for the same reason — where output begins is a boundary Acter supplies for itself, and a
listener is never told about it. So a shell that reports exit codes gets the sentence bash gets.

### 3. `SetUpOutcome::Partly` is kept although nothing reaches it

`sh` was the only shell that reached it, and `cmd.exe` — the one remaining shell that marks only
its prompt — is injected at launch and never reaches that question. What the state is kept for
is the next shell somebody measures whose prompt is all it has. That is not a hypothesis: it is
where `sh` was believed to be a day ago. Deleting it would mean rebuilding it, and rebuilding
the sentence a listener hears with it. Its tests exercise it directly, and their fixture is
named as a shape rather than as a shell that ships this way.

### 4. `$?` goes into `PS1` as text, and the shell fills it in

The exit marker is written into the prompt string as `\033]133;D;` then a literal `$?` then the
bell, and the shell expands the `$?` every time it draws the prompt. `\$` inside the
double-quoted assignment is what leaves it there; every other byte of the markers is put in
place once, by `printf`, at setup time. Writing `$?` unescaped would freeze the setup command's
own status into the prompt for the life of the session.

**The digits go inside the non-printing brackets on the busybox branch.** They are as invisible
on screen as the marker around them — the terminal consumes the whole OSC sequence — so a shell
told to skip the marker and count the digits would miscount by one column per digit of every
exit code. dash takes the branch without brackets, for B9.5 decision 8's measured reason: it
draws them literally.

The first prompt after the setup therefore carries `D;0`, which is the setup line's own status
and is honest: what the line does is an assignment, and an assignment succeeds. Whether the
setup *worked* is still the grace period's to answer (B9.5, decision 12).

### 5. From the write to the block close, the session is Acter talking to itself

One flag, and it is a window rather than a matcher. From the instant the pump writes Acter's own
line to the instant that line's block closes, everything the far end says is rendered and none
of it is spoken.

**It is indifferent to how any far end behaves**, which is the whole reason it fixes both
causes: it never has to recognise an echo, so it does not care whether the echo was redrawn out
of order or landed on a row nobody was watching.

**Nothing is withheld.** `ReadMode::Quiet` already means "accumulates silently in the buffer",
and it is what the window asks for — so every byte stays where the disclosure the Connect dialog
is about can be read back. That is what makes this affordable at all: the command was shown
before it ran, and it is still there afterwards.

**It also settles the doubled prompt** B9.5 recorded as an observation on its second checklist
item. The unmarked prompt drawn before the setup and the marked prompt drawn after it are 155
milliseconds apart and say the same thing; the first falls inside the window and the second does
not, so only the one that is news is spoken.

### 6. The window is applied in the actor, and it silences announcements as well as text

`SessionInput::SelfTalk(bool)` is an internal input beside `FollowMode(bool)`: it reaches the
actor and nothing else, so there is no protocol event, no frontend change and nothing new for a
window to render.

The actor maps one policy decision at a time: a flush becomes a quiet flush, and `StillRunning`
and `OutputContinues` become nothing. The patience and babble announcements are about the
progress of a command, and the user did not run this one.

**It is not applied inside the pacing policy**, and that is where it belongs: the policy answers
questions about size and repetition, and this is a fact about *whose* command is running, which
the policy has no business knowing.

### 7. The window opens at the write, and closes on the block or on the grace period

**At the write rather than at connect.** Opening it at connect would be tidier and would remove
a race, but it would silence a cold distribution's real startup output for up to the whole grace
period, which is roadmap 23.10's territory. Opening it at the write keeps it to the handful of
milliseconds it needs.

**Two closing conditions.** The block Acter's own line is running as, when it ends — sent after
the ending rather than before it, so the flush that ending triggers is quiet too, and so a
verdict on a line the user did not type is not read to them. And the grace period expiring with
the window still open, which is the catch that stops a setup whose markers never arrive from
silencing the session for the rest of its life. That moment is also when a listener is told this
session has no boundaries, which is exactly when they need to hear the text that does arrive.

### 8. One race is accepted and written down

The pump and the actor are separate tasks. Text the far end drew just before the setup is
written sits in the actor's unspoken buffer and is quieted when the flush comes, because the
flush is driven by a timer and the window arrives first on an ordered channel. A pacing timer
firing in the microseconds between the two would still speak that text.

It is a race rather than an impossibility. The gap is microseconds against a quiescence window
measured in hundreds of milliseconds, and the cost of losing it is one prompt spoken twice —
which is what happens today, every time. Recorded here rather than claimed away.

## Definition of done

- `ShellMarkers` has three states and two questions, and the two questions are asserted to
  disagree for the new one.
- `sh`'s setup line carries `\033]133;D;` with `$?` left unexpanded on both branches, and the
  busybox branch keeps the exit code inside the brackets it honours.
- A `PromptCommandLineAndExitCode` session announces a verdict for a command that failed,
  announces its prompt on its own, keeps the prompt out of the block's content, and still opens
  its block where the echo ends.
- The Connect dialog offers failures to a shell that reports exit codes, and still says what a
  prompt-only shell cannot do.
- While the window is open, everything reaches the buffer and nothing is announced — including
  the size, patience and babble announcements.
- The window closes with the setup's block, and closes on grace-period expiry if that block
  never ends.
- Against a real far end: `(exit 7)` in `docker-desktop` announces `Failed(7)`, and neither the
  busybox session nor the SSH session reads Acter's own setup command aloud, while both keep it
  in the buffer.
- `cargo fmt`, `cargo clippy` and the workspace suite are clean.

## Accessibility checklist for the PR body

One item per check, findings written inline on the unchecked item, naming the NVDA version and
the capture mode. Items an agent cannot observe stay the human's.

- Connecting to `docker-desktop` reads the connection sentence and then the prompt, and nothing
  between them. (Agent-observable.)
- Connecting over SSH to a host whose `sshd` prints a login banner does the same. (Agent-
  observable.)
- The setup command is still findable in the buffer afterwards, by arrowing or by F6.
  (Agent-observable.)
- A command that fails in `sh` is announced as having failed. (Agent-observable.)
- The Connect dialog for `sh` offers headings *and* failures. (Agent-observable.)
- The prompt is heard once per command rather than twice. (Agent-observable.)
- Nothing about the quieted window feels like a gap or a hang to a listener waiting for the
  session to come up. (Human — this is about comfort and timing, not about what was spoken.)
