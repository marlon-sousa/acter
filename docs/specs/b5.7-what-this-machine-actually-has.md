# B5.7 — What this machine actually has, and who signed it

Roadmap entry 23.9. Agreed in conversation 2026-08-27, from the user's objection: *"I won't
want to execute a pwsh.exe to discover we had run a malware."* Depends on **B5.3** for the
`InstalledShells` port and on **A11** for the editions panel that shows the result.

## What is asked today, and how

`InstalledShells::is_available` answers "does a program of this name exist somewhere Windows
would start it from" by walking `PATH` and `PATHEXT` and asking whether any candidate
`is_file()`. `ConnectService` asks it once per kind and once per edition when the Connect
dialog is built; `LocalPty` later spawns the program **by name**, and Windows resolves the name
again.

Two separate problems live in that paragraph, and only the second is the one the user raised.

## Measured first, because two of the obvious answers are wrong

All of the following was measured on 2026-08-27 on the developer's machine, Windows 11 Pro
26200, and each measurement changed a decision below.

**The Windows-supplied shells are catalog-signed, not embedded-signed.** `cmd.exe`,
`powershell.exe` and `wsl.exe` in System32 all report `Status: Valid`,
`SignatureType: Catalog`, signer `CN=Microsoft Windows, O=Microsoft Corporation`. A
verification built the obvious way — `WinVerifyTrust` over a `WINTRUST_FILE_INFO` — asks only
whether the *file* carries a signature, and would report `TRUST_E_NOSIGNATURE` for every one of
them. Acter would flag the unremovable Windows shell as unsigned.

**PowerShell 7 here is the Store build, and the registry key everyone recommends is absent.**
`pwsh` resolves to
`C:\Program Files\WindowsApps\Microsoft.PowerShell_7.6.5.0_x64__8wekyb3d8bbwe\pwsh.exe`, which
is `SignatureType: Authenticode`, signer `CN=Microsoft Corporation`. And
`HKLM\SOFTWARE\Microsoft\PowerShellCore\InstalledVersions` **does not exist** — the MSI writes
it and the Store package does not. So "read the registry, it is authoritative" would have found
no PowerShell 7 on a machine that has PowerShell 7. It is rejected on that measurement.
(`HKLM\SOFTWARE\Microsoft\PowerShell\3\PowerShellEngine` does exist and reports 5.1.26100.8875,
so the key is right for Windows PowerShell and wrong as a general rule.)

**The app execution alias can be started but cannot be read.**
`%LOCALAPPDATA%\Microsoft\WindowsApps\pwsh.exe` is a zero-byte reparse point. Rust's
`Path::is_file()` returns `true` for it and `fs::metadata` returns `Ok(0)`, so the current
lookup finds it — the worry that Store PowerShell was invisible to Acter was wrong. But opening
it fails: `Get-AuthenticodeSignature` returns *"The file cannot be accessed by the
system"* (`ERROR_CANT_ACCESS_FILE`). **So resolve-then-verify does not compose with an
execution alias**, and that is the hardest thing in this entry.

## Decisions

### 1. Resolve once, verify that file, start that file

The reason the two problems above are one entry. Today the name is resolved twice — once by
`is_available` to answer a question, and again by `CreateProcess` to start something — and
nothing guarantees the two resolutions land on the same file. Checking a signature under that
regime would be theatre: it would verify a file and then start whichever file `PATH` happened
to name a moment later.

So availability stops returning a boolean and starts returning **the path it found**, that path
is what is verified, and that path is what `ShellLaunch::program` carries to the transport. The
window between the check and the spawn does not close completely — nothing on Windows closes
it — but it narrows from "any file on `PATH`" to "this file, moved or replaced in the seconds
since".

### 2. `which` for the mechanics

`candidates()` is a hand-rolled `PATH` + `PATHEXT` walk, and the `which` crate is the same rule
with more of Windows' edge cases in it and a resolved path as its return value, which decision 1
now needs. It replaces the private half of `installed.rs`; the port and its sentences stay.

### 3. Verification handles both signing shapes, or it is worse than nothing

`WinVerifyTrust` with `WINTRUST_ACTION_GENERIC_VERIFY_V2`, tried as a catalog member first —
hash the file with `CryptCATAdminCalcHashFromFileHandle`, look for a catalog with
`CryptCATAdminEnumCatalogFromHash`, verify through `WINTRUST_CATALOG_INFO` — and falling back to
`WINTRUST_FILE_INFO` for an embedded signature. The measurement above is why the order is that
way round: every shell Windows ships is in the first case and PowerShell 7 is in the second.

Then **who** signed it, which is a second question and a different call: `CryptQueryObject` over
the file, `CryptMsgGetParam` for the signer, `CertGetNameStringW` for the subject. "Trusted, and
signed by Microsoft" and "trusted, and signed by somebody else" are different sentences and the
verdict has to be able to tell them apart.

Through the `windows` crate rather than a wrapper. `codesign-verify` exists and does roughly
this, and is a small, low-traffic dependency in the one place in the product where being wrong
is a security answer rather than a bug; `windows-sys` is already a dependency of
`acter-transports`.

### 4. An alias is resolved to its package, and an alias that will not resolve is *said*

Preference order for a candidate that cannot be opened: take another candidate from `PATH` that
can be; failing that, read the `IO_REPARSE_TAG_APPEXECLINK` reparse point with
`FSCTL_GET_REPARSE_POINT` and verify the target executable it names; failing that, report the
file as unverifiable with the reason, and go to decision 5.

**Unverifiable is never quietly treated as trusted, and never quietly treated as malicious.**
Both of those are lies to a listener who cannot see the file.

### 5. Never a gate. A verdict is a sentence, and a refusal is the user's

This is the decision the whole entry turns on, and it follows A11 decision 3 and B9's host-key
question rather than inventing a stance.

A shell that fails to verify is **still listed and still startable**, and starting it asks a
question first — the same shape `KnownHosts` established for an unknown host key: what was
found, what it means, and a default that does nothing. A self-built pwsh, a corporate re-signed
build, a machine whose catalog database is damaged, an offline revocation check: all
legitimate, all common, and a product that hid the user's shell for any of them would have
taught exactly the lesson B5.4 refused to teach.

What the check buys is real and narrower than it sounds: it defeats `PATH`-order hijacking,
which is cheap and common, and it tells the user *before* the program runs rather than after.
It is not a sandbox and says nothing about what a correctly signed program then does.

### 6. Verified when it is about to be started, not when the list is drawn

`WinVerifyTrust` is not free and revocation can reach the network. The Connect dialog builds
its list on open, in front of a listener who is waiting, and B5.7 must not put a network
timeout there. So the list keeps the cheap existence question, and verification happens once,
on the connection, where there is already a conversation with steps in it (B9). The verdict is
cached by resolved path, size and last-write time for the life of the process.

### 7. Revocation is checked, with a bound, and a timeout is unverifiable rather than untrusted

`WTD_REVOKE_WHOLECHAIN` with `WTD_CACHE_ONLY_URL_RETRIEVAL` so a machine with no network answers
from its cache instead of hanging. A revocation answer that never comes is decision 4's
unverifiable state, not a failure — a listener on a train is not under attack.

## What this entry does not do

It does not verify WSL distributions or SSH far ends. `wsl.exe` itself is in scope as a program
this machine starts; what runs inside the distribution is not a file on this filesystem, and a
remote shell is not one either. Nor does it re-verify a program between the check and the spawn,
which Windows offers no way to do.

## Files touched

- `crates/acter-core/src/entities/` — the verdict: trusted and by whom, untrusted with a
  reason, unverifiable with a reason.
- `crates/acter-core/src/ports/driven/` — the signature port, and `InstalledShells` answering
  with a resolved path.
- `crates/acter-shells/src/installed.rs` — `which` in place of `candidates()`.
- `crates/acter-shells/src/signature.rs` — new adapter: WinTrust, the catalog path, the signer
  name, the alias resolution.
- `crates/acter-core/src/services/connect.rs` — the verdict as a step in the connection
  conversation, and the question it can ask.
- `crates/acter-app/src/container.rs` and `ui/src/adapters/connect_dialog.ts` — the question and
  its default.

## Definition of done

- [ ] `cmd.exe`, `powershell.exe` and `wsl.exe` as Windows ships them verify as trusted and
      signed by Microsoft, through the catalog.
- [ ] `pwsh.exe` verifies as trusted and signed by Microsoft, both as the MSI install and as the
      Store package reached through its execution alias.
- [ ] A file that is unsigned, tampered with, or signed by an untrusted root produces an
      untrusted verdict naming which of those it was — asserted against fixtures, not against
      whatever this machine happens to have.
- [ ] An unverifiable file produces the unverifiable verdict with its reason, and never either
      of the other two.
- [ ] The path verified is the path started, asserted through the port.
- [ ] Building the Connect dialog's list performs no verification and no network access.
- [ ] Every verdict has a spoken sentence, and every sentence names what to do next.
- [ ] `cargo fmt`, `cargo clippy --workspace --all-targets`, workspace tests, the `#[ignore]`d
      real-shell suite, and `npm test` in `ui/` all clean.

## Accessibility checklist for the PR body

- [ ] Connecting to a normally installed shell says nothing new: a verdict nobody needs to act
      on is not an announcement.
- [ ] A shell that fails to verify asks a question that is read in full, whose default is to
      cancel, and which can be refused with one key.
- [ ] The question names the file's full path and who signed it, in a form that can be read
      character by character.
- [ ] Choosing to start it anyway is announced, so nobody is unsure what they just agreed to.
- [ ] The Connect dialog opens no more slowly than it does today.
