# B5.7 — What this machine actually has, and who signed it

Roadmap entry 23.9. Agreed in conversation 2026-08-27, from the user's objection: *"I won't
want to execute a pwsh.exe to discover we had run a malware."* Depends on **B5.3** for the
`InstalledShells` port and on **A11** for the editions panel that shows the result.

## What is asked today, and how

`InstalledShells::is_available` answers "does a program of this name exist somewhere Windows
would start it from" by walking `PATH` and `PATHEXT` and asking whether any candidate
`is_file()`. `ConnectService` asks it once per kind and once per edition when the Connect
dialog is built; `LocalPty` later spawns the program **by name**, and Windows resolves the
name a second time.

Two separate problems live in that paragraph, and only the second is the one the user raised.

## Measured before deciding, because four obvious answers are wrong

All of the following was measured on 2026-08-27 on the developer's machine, Windows 11 Pro
26200. Each one killed a candidate design.

**The Windows-supplied shells are catalog-signed, not embedded-signed.** `cmd.exe`,
`powershell.exe` and `wsl.exe` in System32 all report `Status: Valid`,
`SignatureType: Catalog`, signer `CN=Microsoft Windows, O=Microsoft Corporation`. A
verification built the obvious way — `WinVerifyTrust` over a `WINTRUST_FILE_INFO` — asks only
whether the *file* carries a signature, and would report `TRUST_E_NOSIGNATURE` for every one of
them. Acter would flag the unremovable Windows shell as unsigned.

**PowerShell 7 here is the Store build, and the registry key everyone recommends is absent.**
`pwsh` resolves to
`C:\Program Files\WindowsApps\Microsoft.PowerShell_7.6.5.0_x64__8wekyb3d8bbwe\pwsh.exe`, which
is `SignatureType: Authenticode`, signer `CN=Microsoft Corporation`. And
`HKLM\SOFTWARE\Microsoft\PowerShellCore\InstalledVersions` **does not exist** — the MSI writes
it and the Store package does not. `HKLM\SOFTWARE\Microsoft\PowerShell\3\PowerShellEngine` does
exist and reports 5.1.26100.8875, so the registry is right for Windows PowerShell and wrong as
a general rule.

**The app execution alias can be started but cannot be read.**
`%LOCALAPPDATA%\Microsoft\WindowsApps\pwsh.exe` is a zero-byte reparse point. Rust's
`Path::is_file()` returns `true` and `fs::metadata` returns `Ok(0)`, so the current lookup finds
it — the worry that Store PowerShell was invisible to Acter was wrong. But opening it fails
with `ERROR_CANT_ACCESS_FILE`, so it has **no readable signature and no readable anything**.
That is the wall the whole entry turns on.

**The file lies about its own version.** `powershell.exe` reports FileVersion
`10.0.26100.8875` and ProductVersion `10.0.26100.8875` — the *Windows build*, not 5.1. (`pwsh`
reports `7.6.5 SHA: ea554a8f…`, truthful but with a git hash glued on.) So a plan that reads
the PE version resource is wrong for one of the two editions in exactly the direction that
matters.

## What everybody else does, looked up rather than assumed

**Microsoft's official guidance is from 2009 and covers PowerShell 1.0.** The PowerShell
Team's [detection-logic post] gives `HKLM\SOFTWARE\Microsoft\PowerShell\1\Install` and warns:
*"Depending on any other registry key(s), or version of PowerShell.exe or the location of
PowerShell.exe is not guaranteed to work in the long term."* There is no updated official
answer, so that warning stands against every method in use today, this spec's included. It is
recorded here so nobody later mistakes the design below for a supported contract.

**Windows Terminal does not consult `PATH` at all.** Its `PowershellCoreProfileGenerator`
enumerates known roots — `%ProgramFiles%\PowerShell` and its x86 and ARM twins, the Store via
`PackageManager.FindPackagesForUser()` for `Microsoft.PowerShell_8wekyb3d8bbwe` and
`Microsoft.PowerShellPreview_8wekyb3d8bbwe`, `%USERPROFILE%\.dotnet\tools`, and
`%USERPROFILE%\scoop\shims`. **It never reads the version resource and never runs the
binary**: version comes from the directory name (`…\PowerShell\7\pwsh.exe` → 7) or the package
identity, and dotnet-tool and scoop installs are recorded as version 0, indeterminable, which
it ships as an honest state rather than a failure.

That is independent confirmation of the fourth measurement above, and it is where decision 2
comes from.

## Decisions

### 1. Resolve once, verify that file, start that file

The reason the two problems are one entry. Today the name is resolved twice — once by
`is_available` to answer a question, again by `CreateProcess` to start something — and nothing
guarantees the two resolutions land on the same file. Checking a signature under that regime
would be theatre: it would verify a file and then start whichever file `PATH` happened to name
a moment later.

So availability stops returning a boolean and starts returning **the path it found**, that path
is what is verified, and that path is what `ShellLaunch::program` carries to the transport. The
window between check and spawn does not close completely — nothing on Windows closes it — but
it narrows from "any file on `PATH`" to "this file, moved or replaced in the seconds since".

### 2. Discovery is a union of sources, and `PATH` is one of them rather than the whole of it

The user's shape — look on `PATH`, check the signature, offer what you found — is right, and
`PATH` alone is where it breaks. Measured and read: an MSI install with "add to PATH"
unchecked is invisible to it; scoop and chocolatey put *shims* on it that are not pwsh; and on
the developer's own machine it yields **two hits for one install**, the package directory and
the alias. Worse, the hit an ordinary machine gets is the alias, which cannot be opened — so a
`PATH`-only design walks straight into the wall and has nothing to verify.

The sources, unioned and then deduplicated by canonical target:

- **`PATH`**, every match rather than the first (`which::which_all`).
- **Known roots**: `%ProgramFiles%\PowerShell\<N>`, the x86 and ARM twins, preview directories.
- **The Store**, by package family name.
- **`%USERPROFILE%\.dotnet\tools`.**
- **The registry**, for Windows PowerShell's `ApplicationBase` and for MSI installs of 7
  deliberately kept off `PATH`.

**`PATH` is kept for the one thing no other source knows: what `pwsh` means to this user.** If
they type it in any other terminal, `PATH` decides — so the entry `PATH` resolves first is
marked as the default rather than merely included. That is the half of the user's proposal
that Windows Terminal gets wrong by dropping `PATH` entirely.

### 3. An install is identified by where it came from, never by what the file says

Decision 2's fourth measurement, made into a rule. The provenance is the identity: the
versioned directory name, or the Store package identity, or the registry's own value for
Windows PowerShell. A file found somewhere that says nothing — a dotnet tool, a scoop shim, a
path the user typed — is **indeterminable**, which is a state this product ships rather than a
gap it fills with a guess.

`$PSVersionTable` is the only authoritative answer and it costs a process. B5.3's
`installed.rs` already refuses to pay that: *"starting each candidate to find out whether it
starts would open sessions nobody asked for."* That refusal stands.

### 4. The alias is resolved to its package, and one that will not resolve is *said*

Nothing can be read about an execution alias, so it is resolved first: `CreateFile` with
`FILE_FLAG_OPEN_REPARSE_POINT`, then `DeviceIoControl(FSCTL_GET_REPARSE_POINT)`, reading the
`IO_REPARSE_TAG_APPEXECLINK` (0x8000001B) buffer for the package family name and the target
executable. That is what `CreateProcess` itself does through `LoadAppExecutionAliasInfoEx`, and
PowerShell added support for the same tag in its own filesystem provider.

**It is a measured dependency and not a documented contract.** The tag's buffer layout is not
in the official documentation; it is described by reverse-engineering write-ups and confirmed
by the behaviour of `CreateProcess`. So the resolution is attempted, its failure is an ordinary
outcome, and a candidate that cannot be resolved is reported **unverifiable with its reason** —
never quietly trusted and never quietly condemned. Both of those are lies to a listener who
cannot see the file.

Preference order for a candidate that cannot be opened: another `PATH` or known-root entry
resolving to the same package; then the reparse point; then unverifiable.

### 5. Verification handles both signing shapes, or it is worse than nothing

`WinVerifyTrust` with `WINTRUST_ACTION_GENERIC_VERIFY_V2`, tried as a catalog member first —
hash with `CryptCATAdminCalcHashFromFileHandle`, look for a catalog with
`CryptCATAdminEnumCatalogFromHash`, verify through `WINTRUST_CATALOG_INFO` — falling back to
`WINTRUST_FILE_INFO` for an embedded signature. The first measurement is why that order: every
shell Windows ships is in the first case and PowerShell 7 is in the second. Microsoft documents
this exact fallback, which is the one part of the design that rests on supported guidance.

**Who** signed it is a second question and a different call: `CryptQueryObject` over the file,
`CryptMsgGetParam` for the signer, `CertGetNameStringW` for the subject. "Trusted and signed by
Microsoft" and "trusted and signed by somebody else" are different sentences and the verdict
must tell them apart.

Through the `windows` crate rather than a third-party wrapper. `codesign-verify` does roughly
this and is a small, low-traffic dependency in the one place in the product where being wrong
is a security answer; `windows-sys` is already a dependency of `acter-transports`.

### 6. **Never a gate.** Everything found is listed; the unverified is labelled and asked about

The decision the entry turns on, and the one place this spec argues with the user's third step.
"List the ones that are approved" makes the signature a filter, and A11 decision 3 and B5.4
both settled the opposite: a thing this machine has keeps its place in the list and says what
to do about it.

A self-built pwsh, a corporate re-signed build, a damaged catalog database, an offline
revocation check — all legitimate, all common. Hiding any of them teaches a user that Acter
cannot see the PowerShell they are looking straight at, which is exactly the lesson B5.4
refused to teach about WSL. So: everything discovered is listed, an unverified entry carries
its verdict in its **name** the way A11's missing edition does, and starting one asks a
question first — the same shape `KnownHosts` established for an unknown host key: what was
found, what it means, and a default that does nothing.

What the check buys is real and narrower than it sounds: it defeats `PATH`-order hijacking,
which is cheap and common, and it tells the user *before* the program runs rather than after.
It is not a sandbox and says nothing about what a correctly signed program then does.

### 7. Verified when it is about to be started, not when the list is drawn

`WinVerifyTrust` is not free and revocation can reach the network. The Connect dialog builds
its list on open, in front of a listener who is waiting, and this must not put a network
timeout there — 23.7's objection. So the list keeps the cheap discovery, and verification
happens once, on the connection, where B9 already established a conversation with steps in it.
The verdict is cached by resolved path, size and last-write time for the life of the process.

### 8. Revocation is bounded, and a timeout is unverifiable rather than untrusted

`WTD_REVOKE_WHOLECHAIN` with `WTD_CACHE_ONLY_URL_RETRIEVAL`, so a machine with no network
answers from its cache instead of hanging. A revocation answer that never comes is decision 4's
unverifiable state. A listener on a train is not under attack.

### 9. What tells two installs apart is where they came from

The question A11 leaves open once more than one PowerShell 7 can appear. Windows Terminal
answers "the folder", and that is the answer here too: an entry is named by its provenance —
`PowerShell 7`, `PowerShell 7 (preview)`, `PowerShell 7 (Microsoft Store)`, `PowerShell 7
(C:\tools\pwsh)` — rather than by a version number nobody can read off the file reliably.

**This keeps A11's row count.** The kinds stay Command Prompt, PowerShell, WSL; what grows is
the edition panel, and only on a machine that genuinely has more than one. A machine with one
7.x sees exactly what it sees today.

## What this entry does not do

It does not verify WSL distributions or SSH far ends. `wsl.exe` itself is in scope as a program
this machine starts; what runs inside the distribution is not a file on this filesystem, and a
remote shell is not one either. It does not re-verify between the check and the spawn, which
Windows offers no way to do. And it does not run any candidate to ask its version, which is
decision 3.

## Definition of done

- [x] `cmd.exe`, `powershell.exe` and `wsl.exe` as Windows ships them verify as trusted and
      signed by Microsoft, through the catalog.
- [x] `pwsh.exe` verifies as trusted and signed by Microsoft, both as an MSI install and as the
      Store package reached through its execution alias.
- [x] A file that is unsigned, tampered with, or signed by an untrusted root produces an
      untrusted verdict naming which of those it was — asserted against fixtures, not against
      whatever this machine happens to have. **Amended while implementing**: unsigned is a
      real file the test builds; tampered and untrusted-root are asserted against
      `WinVerifyTrust`'s own status codes, because producing either needs a signing
      certificate nothing here has. See amendment 2 below.
- [x] An unverifiable file produces the unverifiable verdict with its reason, and never either
      of the other two.
- [x] The path verified is the path started, asserted through the port.
- [x] Two installs of PowerShell 7 are told apart by provenance, and a machine with one sees
      what it sees today.
- [x] An install found somewhere that says nothing is reported indeterminable rather than
      guessed at.
- [x] Building the Connect dialog's list performs no verification and no network access.
- [x] Every verdict has a spoken sentence, and every sentence names what to do next.
- [x] `cargo fmt`, `cargo clippy --workspace --all-targets`, workspace tests, the `#[ignore]`d
      real-shell suite, `npm test` and `npm run typecheck` in `ui/`, **and `npm run test:e2e`**
      — the last because this touches the Connect dialog, and A13 shipped red for omitting it.

## Accessibility checklist for the PR body

- [ ] Connecting to a normally installed shell says nothing new: a verdict nobody needs to act
      on is not an announcement.
- [ ] A shell that fails to verify asks a question that is read in full, whose default is to
      cancel, and which can be refused with one key.
- [ ] The question names the file's full path and who signed it, in a form that can be read
      character by character.
- [ ] Choosing to start it anyway is announced, so nobody is unsure what they just agreed to.
- [ ] A machine with two PowerShell 7 installs reads as two entries a listener can tell apart
      without opening either.
- [ ] The Connect dialog opens no more slowly than it does today.

## What implementing it measured, and the two places the spec was amended

Written 2026-08-27, in the PR that implements this. Everything here was found by writing the
code rather than by reading about it, and both amendments ride in this PR as CLAUDE.md
requires.

**`where pwsh` answers with the package directory first and the alias second.** The Store
package's own directory is on `PATH` here in its own right, so the two hits deduplicate onto
one file the moment the alias is resolved — and the file that survives is a real one with a
real signature. The worry behind decision 4 did not materialise on this machine, and the
alias resolution is what makes that true rather than luck. **The packaged `pwsh.exe` also
starts when it is launched directly, by full path, outside its alias** — measured by running
it, because decision 1 requires that the file verified is the file started, and a package
that could only be started through its alias would have broken that.

**`CryptQueryObject` with `CERT_QUERY_CONTENT_FLAG_ALL` crashes the process on a catalog.** A
`.cat` is a certificate trust list as well as a signed message; asking for "all" made it
answer `CERT_QUERY_CONTENT_CTL` and set **no message handle**, so reading the signer through
it was a null dereference — `STATUS_ACCESS_VIOLATION`, every time, on the first file this was
run against. Naming the two content types this product actually asks about,
`PKCS7_SIGNED | PKCS7_SIGNED_EMBED`, is the fix, and both the return value and the handles
are checked now.

### Amendment 1: the Store is reached through its execution alias, not through `PackageManager`

Decision 2 lists "the Store, by package family name" as a source and Windows Terminal reaches
it with `PackageManager.FindPackagesForUser()`, which is WinRT — an apartment, a projection,
and a good deal more of Windows than anything else in this product touches. The alias
resolution decision 4 already requires yields the same two facts, the package family and the
file, out of a reparse point; and measured above, the package directory is on `PATH` here in
its own right. So the Store arrives through `PATH` and through the alias, and discovery does
not go looking for it a third way. The decision is unchanged; how it is reached is narrower
than Windows Terminal's and gets the same answer on this machine.

### Amendment 2: the untrusted fixtures are the status codes, and one real unsigned file

The definition of done asks for tampered and untrusted-root verdicts "asserted against
fixtures, not against whatever this machine happens to have". Two of the three turn out not to
be buildable here, and it is worth saying exactly why rather than quietly weakening the item:

- **Unsigned is a real file, and it is built by the test.** A *copy* of `cmd.exe` still
  verifies, because catalogs claim a file by its hash rather than by where it is — measured,
  and asserted, because it is a surprising fact that a reviewer would otherwise take for a
  bug. Changing one byte of the copy takes it out of every catalog on the machine and leaves
  a genuine PE that nothing has signed, which is the fixture the item asks for, built from
  something every Windows machine has.
- **Tampered needs an embedded signature, and there is none to borrow.** Every System32
  binary sampled here is catalog-signed — `cmd.exe`, `powershell.exe` and `wsl.exe` as the
  spec records, and `curl.exe`, `tar.exe`, `notepad.exe`, `mshta.exe`, `msinfo32.exe` and
  `ftp.exe` besides. A tampered *catalog* member reports as unsigned rather than as tampered,
  which is correct and is not the fixture. Producing a real one means signing a file, which
  needs a certificate and a signing tool that nothing in this repository has.
- **Untrusted root needs the same certificate**, for the same reason.

So the classification is a pure function over `WinVerifyTrust`'s own status codes, and **those
codes are the fixtures**: every status this product claims to understand is asserted against
the verdict it produces, in `acter-shells/src/signature/trust.rs`. That is a weaker guarantee
than a signed fixture and a stronger one than nothing: it pins the mapping a listener hears,
and it leaves the Win32 call itself covered only by the trusted and unsigned cases, which are
real files. A machine with a signing certificate could add the other two later without
changing the design; the seam is already a pure function.

## What still has to be measured, and is not measurable here

The developer's machine is one data point and it broke four assumptions. Before the checklist
is run, these want a machine that is not it:

- an **MSI-installed 7.x** — does `PowerShellCore\InstalledVersions` appear, and does its
  `InstallLocation` agree?
- **side-by-side 7.4 and 7.6** — do both reach `PATH`, and which wins?
- a **preview** build — what does the Store package identity say?
- a machine with **no PowerShell 7 at all**, so the A11 unavailable-edition path still reads
  correctly through the new discovery.
