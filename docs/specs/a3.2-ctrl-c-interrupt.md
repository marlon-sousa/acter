# Spec: PR A3.2 — the `Ctrl+C` interrupt surface

Lane 1. Frontend work over a backend method that already exists and is already
tested, plus two data changes in the built-in transcript that the frontend surface
makes correct for the first time.

## Why now / relation to the roadmap

A3.1 deliberately did not build this. It wrote down why: the edit-field ownership
model was under discussion, and under a pass-through model `Ctrl+C` would be byte
`0x03` written to the PTY with no port method, no ack and no dedicated announcement —
so the whole frontend surface was exactly the work that would be deleted.

That question is answered, and in the direction DESIGN's **Decided** "Edit field
ownership (non-interactive mode)" already pointed: the field is 100% local and the
shell sees no bytes until Enter. An interrupt is therefore never "a key that reaches
the pty". It is a report to the session about a key the frontend chose not to handle,
and the backend decides what it means.

B6 then built that backend. `SessionApi::send_key` takes a `KeyPress` and answers a
`KeyAck`; `policies::keybindings::intent_for` is the pure table binding `Ctrl+C` and
nothing else; `Transport::interrupt` is a port method because over SSH an interrupt is
a channel request rather than bytes; and the service records that it asked for an
interrupt, so a block closing with no exit code while one is outstanding is announced
as stopped rather than as "finished, exit code 0". The Tauri command, its managed
state and its router test all exist.

So what remains is entirely the frontend's, and one promise is overdue: A3's
alt-screen string already tells the user to press `Ctrl+C` to return to the prompt,
and until this lands there is no key to press.

## What this entry does not have to do

**No protocol change and no binding regeneration.** `Key`, `KeyPress` and `KeyAck`
are already in `ui/src/protocol.ts`, generated by B6. The frontend consumes types it
has been shipping unread.

**No new domain concept.** Which keystrokes mean something is the backend's table.
This PR adds no meaning; it adds a caller.

## Design decisions this spec makes

1. **The frontend reports a keystroke, never an intent.** The controller gains
   `reportKey(press: KeyPress)`, not `interrupt()`. B6 decision 4 put the binding
   table behind the port precisely so adding an intent later is a backend change with
   no frontend release, and a frontend method named for the meaning would quietly put
   the table back on this side of the wire. The word "interrupt" appears nowhere in
   `ui/src/` outside a comment.

2. **The adapter reports exactly the keystrokes it does not consume locally, and
   today that is one.** The frontend does not forward every unhandled key: the edit
   field owns text keys, F6 and Escape are Acter's own, and flooding the IPC with
   every character typed would be a different product. The keyboard adapter
   recognises `Ctrl+C` with neither Shift nor Alt, and reports that. DESIGN's layer 1
   (`Ctrl+Shift+letter`) is Acter's own and is not reported at all — those bindings
   are unimplemented, and reporting them would announce "unbound" for keys that are
   reserved rather than free.

3. **The selection question is the edit field's own, and needs a port method there.**
   An `<input>`'s internal selection is invisible to `window.getSelection()`, so a
   document-level check would be wrong in exactly the one place DESIGN spells the rule
   out. `EditFieldView` therefore gains `hasSelection(): boolean`, implemented over the
   mechanism the field actually has.

   **Amended by decision 5.** As first written this put `hasSelection()` on *both* view
   ports and had the controller ask whichever area had focus, because the interrupt was
   then meant to work from either. With the interrupt belonging to the edit field alone,
   nothing asks the buffer, and `BufferView::hasSelection` was removed rather than left
   as a method with no caller.

4. **A `Ctrl+C` with a selection is consumed locally and never reported.** The
   handler does not call `preventDefault()` in that case, so the native copy runs
   exactly as the platform provides it. Nothing is announced: the screen reader
   speaks its own copy feedback, and a second voice over it would be noise. This is
   the half of DESIGN's sentence that `policies::keybindings` documents as never
   reaching the backend, and it stays true by construction — the invoke is not made.

   **Amended during implementation.** This spec first put the selection guard inside
   `reportKey`, which cannot work: `preventDefault()` has to be decided synchronously,
   in the same tick as the keydown, while `reportKey` is async — so the adapter would
   have had to ask the same question a second time to know whether to prevent. The
   guard is therefore the adapter's single decision, made once, over a public
   `AppController.focusedAreaHasSelection()`; `reportKey` is a pure report. The
   controller still owns *which area answers*, which is the part decision 3 is about.
   The tests moved with it: the per-focus routing is tested on the controller, and
   "not reported and not prevented" is tested on the adapter, where both halves of
   the consequence are visible together.

5. **The interrupt belongs to the edit field and to nowhere else.** DESIGN names it
   only there, and asks the results buffer for "standard text interaction"; the
   no-selection case in the buffer was the one thing DESIGN left silent.

   **This spec first filled that silence the other way, and the NVDA pass proved it
   wrong.** The original decision extended the interrupt into the buffer, reasoning that
   a user reviewing output should not have to press F6 first. That binding cannot be
   pressed: where the buffer lives a screen reader is in its own browse mode, and
   `Ctrl+C` is *its* copy command — NVDA answers "no selection" itself and the keystroke
   never reaches the application. A binding that cannot be pressed is worse than no
   binding, because it reads as an interrupt the user can rely on. Reversed by decision
   (conversation, 2026-08-21) and written into DESIGN's layer 2 in this PR, which is
   where a keystroke rule belongs.

   **What the frontend enforces, and what it must not try to.** The session hears a
   keystroke only while the edit field has focus and holds no selection. Reader mode is
   not part of that test and must never be: browse versus focus mode is the reader's own
   state, invisible to a web frontend and carried by no event — and it needs no
   detecting, since browse mode does not deliver the key at all. The rule has two owners
   and only the second half is ours.

   The focus half is enforced **by construction**: the `Ctrl+C` listener is bound to the
   edit field element rather than to `document`, so a keydown reaches it only when that
   field already has focus. What remains for the controller is the selection.

6. **`Applied` says nothing.** `SessionEvent::CommandInterrupted` already speaks
   `command stopped`, and it speaks it when the interrupt has actually taken effect
   rather than when it was accepted. An ack-time announcement would say it twice, and
   the first one would be a claim about the future.

7. **`NothingToActOn` and `Unbound` are the two answers only the frontend can voice,
   and both get a pinned string.** A3.1 decision 6 named the first of them: the typed
   `stop` had no honest way to say "nothing to stop", because the only surface that
   could justify one is a key with an ack to report it. This is that surface. The
   wordings, in `ui/src/controllers/app.ts` beside the other pinned strings:

   - `NothingToActOn` → `nothing running to stop`
   - `Unbound` → `that key does nothing here`

   `Unbound` is unreachable today, since the only keystroke reported is the only one
   bound. It is still spoken and still tested, driven by a fake backend that answers
   it: an unreachable string is cheap, and a silent black hole the first time a second
   key is reported is not. Silence is this product's worst failure mode, and a key
   the user pressed that produced nothing at all is precisely the case the ack exists
   to make speakable.

8. **The typed `stop` rule leaves the built-in transcript.** It was A3.1's only way
   to halt an endless scenario, and it modelled an interrupt by consuming a submitted
   line. That is what mints a `CommandId` for something that is a keystroke in the
   shipped product, and B6.1 records the consequence found under NVDA: the id is
   never claimed, the queue does not recover, and from that point every block in the
   session carries the previous command's heading. This PR removes the trigger
   because it finally has a replacement — a real key, on the real path, through
   `Transport::interrupt`. It does **not** remove the hole; B6.1 still owns that, and
   the `0x03` rule the transcript already carries is what `Ctrl+C` now reaches.

9. **The interrupt rule leaves the alternate screen.** The `0x03` rule emits `^C` and
   a bare `D` and no `ESC [ ? 1049 l`, so interrupting `nano` today would close the
   block while leaving the session believing the alternate screen is still up — A3's
   promise half-kept, which is worse than unkept because the user was told to press
   the key. The rule gains the leave-alternate-screen sequence ahead of its `^C`.
   This is safe for an ordinary `Ctrl+C` on the normal screen because `SessionActor`
   compares the next `SessionState` against the current one and emits nothing when
   they match, so a leave that changes nothing produces no `AltScreenLeft` and no
   spurious "interactive program ended". The dedupe is existing, tested behavior;
   this decision depends on it and says so.

10. **This PR carries an accessibility checklist.** Unlike B3.5, B3.6 and A6 it has a
    real user-facing surface: a new key, two new strings, and the first time a
    listener can stop a command by pressing something.

11. **The completion beep is fixed here, in `acter-core`, because the checklist item
    could not otherwise mean anything.** A3.2's own checklist asks whether a *stopped*
    command beeps; driving it showed that no command beeped at all, ever. The frontend
    fires the beep on the ending event for any command a `TooBig` armed, and
    `SessionActor::close` emitted the ending *before* applying the policy's last word —
    so the arming verdict always arrived one event too late. The fix is to apply that
    last word before sending the terminal event, which is what `close`'s own doc comment
    already claimed it did.

    It is the same inversion behind what this run first heard as a wording oddity: after
    a stop, the accumulated output was read out *after* `command stopped`. One reorder
    fixes both, and it restores the rule A6 decision 2 set for `Failed` — an announcement
    about text that arrived during a command precedes the event saying the command ended.
    Two actor tests pin it, and both were confirmed to fail against the old order before
    the fix was kept. Landing it here rather than filing it was decided in conversation:
    it is small, it is central, and A3.2 cannot honestly report its own checklist while
    the arming is broken.

12. **A debug event recorder ships in this PR, debug builds only.** Decided in
    conversation after the beep defect took an afternoon and an ad-hoc monkey-patch of
    `AudioContext` to find, because the bug was never audible: it was an *ordering* bug,
    and ordering is exactly what neither the DOM nor the live region preserves.

    It is a decorator over `BackendApi` — not a new protocol shape. That matters: adding
    a `SessionEvent::Debug` variant would put a tooling concern on the wire and force A2's
    exhaustiveness guard to handle it, while a *separate* channel would lose the one
    property the recorder exists for, since two streams cannot be interleaved after the
    fact. Recording the real stream as it arrives keeps exact order and changes nothing.

    Gated exactly as T2 gated the embedded WebDriver: a `#[cfg(debug_assertions)]` plugin
    injects `window.__ACTER_DEBUG__` before any page script, and only then does the
    frontend wrap its backend and install the reader. A release build injects nothing, so
    the recorder is never constructed and no entry is ever produced. The gate is at
    runtime rather than at build time on purpose — E2E runs a *production* frontend bundle
    inside a *debug* binary, so `import.meta.env.DEV` is false precisely where the recorder
    is most needed. The cost is a few unreferenced kilobytes in the release bundle.

## Deliverables

### `ui/` — the port and the router

- `ports/backend_api.ts` gains `sendKey(key: KeyPress): Promise<KeyAck>`, documented
  as reporting a keystroke the frontend did not consume and answering what became of
  it — the key, not the meaning.
- `routers/tauri.ts` gains the wrapper: `invoke<KeyAck>('send_key', { sessionId:
  SESSION_ID, key })`. `KeyPress` serialises as the generated mirror describes, with
  `Key` externally tagged (`{ Char: 'c' }`).

### `ui/` — the view ports

- `ports/edit_field_view.ts` gains `hasSelection(): boolean`; `adapters/edit_field.ts`
  implements it as `selectionStart !== selectionEnd`.
- `ports/buffer_view.ts` gains `hasSelection(): boolean`; `adapters/buffer.ts`
  implements it over `window.getSelection()`, requiring a non-collapsed range whose
  anchor is inside the results element — a selection somewhere else in the document
  is not the buffer's.

### `ui/` — the controller

- `AppController.reportKey(press: KeyPress): Promise<void>`: returns without invoking
  when the focused area has a selection, otherwise awaits `backend.sendKey` and
  announces per decision 7.
- Two pinned strings exported beside the existing ones.

### `ui/` — the keyboard adapter

- `bindKeys` takes the edit field element and binds the `Ctrl+C` branch to it, so the
  focus half of the rule holds by construction. F6 and Escape stay on `document`: they
  are Acter's own and belong to the whole window.
- It recognises `Ctrl+C` with neither Shift nor Alt, calls `preventDefault()` only when
  it is going to report the key, and builds the `KeyPress` from the event.

### `ui/` — the debug recorder

- `adapters/debug_recorder.ts`: `installDebugRecorder(backend)` returns the backend
  untouched unless `window.__ACTER_DEBUG__` is set, and otherwise wraps it in a decorator
  recording every inbound event and every call and ack into a bounded ring, exposed at
  `window.__acterDebug` for the harness.

### `acter-core` — the ordering fix

- `SessionActor::close` applies the policy's last word before sending the terminal event,
  and returns `bool` rather than an action for the caller to apply.

### `crates/acter-app/` — the debug flag

- A `#[cfg(debug_assertions)]` plugin injecting `window.__ACTER_DEBUG__`, beside the
  WebDriver plugin and gated the same way.

### `crates/acter-transports/` — the transcript

- `default_transcript.json`: the `stop` rule is deleted; the `0x03` rule gains the
  leave-alternate-screen sequence.
- The scenario-name lists in `scripted/transcript.rs` and `fake/unmarked.rs` drop
  `stop`, and `unmarked.rs`'s assertion that the literal `stop` line interrupts goes
  with it. The inline transcripts inside `scripted.rs`'s own tests are self-contained
  and keep their `stop` rule: they test the pipe's interrupt plumbing, not the
  shipped scenario table.

### `e2e/`

- `stop.spec.ts` is rewritten around the key. Its long header comment predicted this
  entry by name and asserted the silence B6 left behind; the same file now asserts
  the halt **and** the speech, because Acter did the stopping this time.

## Tests

- Controller unit tests over a fake backend, one per ack: `Applied` announces nothing,
  `NothingToActOn` announces its string, `Unbound` announces its string.
- Controller unit tests for the per-focus routing: the focused area answers, a stale
  selection in the unfocused area does not answer for it, and focus in neither area
  reports no selection.
- Adapter tests for the consequence: with a selection the key is neither reported nor
  prevented, and without one it is reported exactly once as
  `{ key: { Char: 'c' }, ctrl: true, shift: false, alt: false }` and prevented.
- A jsdom test of `bindKeys`: a `Ctrl+C` keydown reaches `reportKey`; `Ctrl+Shift+C`
  and a plain `c` do not; `preventDefault` is called when the key is reported and not
  called when a selection consumed it.
- Adapter tests for `EditFieldDom.hasSelection()` over real DOM, including that the
  document Selection API cannot see the range it reports.
- Adapter tests that `Ctrl+C` from the results buffer, and from the document at large, is
  neither reported nor prevented, while F6 still is from anywhere.
- Actor tests pinning that the last word precedes the ending, on both endings. Both were
  run against the old order first and fail there; a regression test that cannot fail is
  not one.
- Recorder tests: nothing installed without the flag, arrival order recorded, an entry
  written before the controller's handler runs, calls and acks paired, sequence numbers
  monotonic, and the reader handed a copy.
- E2E: submit `forever`, wait until it is genuinely producing, press `Ctrl+C`, assert
  the output halts and `command stopped` is announced.
- E2E: press `Ctrl+C` with nothing running and assert the nothing-to-stop string.
- E2E: dispatch `Ctrl+C` at the results buffer and assert the command keeps producing and
  nothing is said, then stop it from the edit field — so the assertion is about where the
  key lands rather than about a session that had stopped listening.
- E2E: read the recorder's tape after `big` and assert the too-big verdict precedes
  `CommandFinished`, which is the beep's arming condition expressed as the ordering it
  actually depends on.
- Rust: the existing suites stay green with the two transcript changes, which is the
  point of making them data changes.

## Acceptance criteria

- Pressing `Ctrl+C` with no selection stops the running command and the listener hears
  `command stopped` once.
- Pressing `Ctrl+C` with nothing running speaks `nothing running to stop` and nothing
  else.
- Pressing `Ctrl+C` with a selection copies and neither stops anything nor speaks.
- Pressing `Ctrl+C` anywhere but the edit field does not stop anything.
- A too-big command's verdict is emitted before its ending, so the completion beep arms.
- A release build installs no debug recorder and injects no debug flag.
- Running `nano` and pressing `Ctrl+C` returns the session to the prompt: the listener
  hears the alt-screen-left string and then `command stopped`, and the next command
  behaves normally.
- The word "interrupt" does not appear as a method or type name anywhere in `ui/src/`.
- `cargo test`, `cargo clippy`, the `ui` unit suite and the e2e suite are green.
- No pinned string other than the two added differs from main, by diff.

## Manual accessibility checklist (PR body)

Agent-observable through the screen-readers MCP bridge as the `user` persona, except
where noted. NVDA does not switch focus mode by itself on the tester's machine, so
each item reads the current mode and sets the one it needs rather than assuming.

- With `forever` running, `Ctrl+C` from the edit field speaks `command stopped` once,
  and the buffer stops growing.
- With `forever` running, `Ctrl+C` from the results buffer (F6 first, no selection)
  does the same, with NVDA in focus mode. In browse mode NVDA consumes the key for its
  own copy command and the item cannot pass; record which mode was used.
- With nothing running, `Ctrl+C` speaks `nothing running to stop` once.
- With text selected in the edit field, `Ctrl+C` copies it and Acter says nothing of
  its own; the running command keeps running.
- With text selected in the results buffer, `Ctrl+C` copies it and says nothing of its
  own.
- `nano`, then `Ctrl+C`: the interactive-program-ended string and `command stopped`
  are heard as two separate utterances, and a command submitted afterwards runs and is
  read normally.
- A stopped command does not beep (**human-only**: the bridge captures speech and
  braille, not audio).

## Out of scope

- **The correlation drift (B6.1).** This PR removes the reachable trigger, not the
  hole. An id submitted for a line that never opens a block still stays queued.
- **Configurable bindings.** DESIGN Decided they are configurable and global; the
  table stays a constant behind the port, and making it configurable is a backend
  change with no frontend release, which is the whole point of B6 decision 4.
- **`Ctrl+Shift+C`, `Ctrl+Shift+R` and the rest of layer 1.** Reserved, unimplemented,
  and deliberately not reported.
- **EOF.** Filed on B5 with the `ShellAdapter` it needs.
- **Interactive mode's pass-through** (`Ctrl+Shift+Space`, plain `Ctrl+C` to the app):
  phase 2.
- **Reporting any second keystroke.** Tab is A4's.

## Definition of done

`Ctrl+C` is a key the user can press: it copies when there is something to copy,
stops the running command when there is not, and says something honest when there is
nothing to stop. A3's alt-screen promise is kept end to end. The typed `stop` scenario
is gone from the shipped transcript. Every suite is green, the checklist is recorded
in the PR body with each item marked agent-observed or human-verified, and the ROADMAP
entry for A3.2 is flipped to Done with this spec's path, in this PR.
