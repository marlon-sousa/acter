# B5.3 — the WSL adapter, and what is installed

Roadmap entry 23.3. Agreed in conversation 2026-08-23. Depends on 23.1 for the port.

Two things at once, and they are related: a bash far end reached through `wsl.exe`, and the
first port that answers **what this machine actually has**, since a WSL adapter with no
distribution to name is not a session anyone can start.

## What 22.6 already measured about this far end

Measured 2026-08-23 and not to be re-derived: `wsl.exe` is a client to a shell in another
kernel, exactly as `docker.exe` is. Two consequences land directly on this entry.

**An interrupt reaches it, and it reaches it as data.** `0x03` written to the pseudoconsole
crossed `wsl.exe` into the distribution, bash's own line discipline turned it into `SIGINT`,
the running loop died and the prompt came back — zero ticks in six seconds. So nothing
special is needed here for Ctrl+C.

**Environment variables do not cross.** A variable set on the Windows side is not in the
distribution's environment unless `WSLENV` says to pass it. This is the constraint that
shapes the injection below, and it is why the mechanism cannot simply be copied from cmd.

## Decisions

### 1. The launch names a distribution

`wsl.exe -d <distro>`, one adapter value per distribution, the way PowerShell has one per
edition. The distribution name is data the adapter carries, which is the reason 23.1's
`ShellLaunch` is owned rather than borrowed.

### 2. Acter does not edit the user's machine to get integration

The pinned constraint for this entry, and the one that decides the injection. cmd's markers
ride in an environment variable — "no snippet to source, no profile to edit, nothing to
fail silently on a locked-down machine" — and PowerShell's ride in a `-Command` argument.
Neither writes anything. **A WSL adapter that appends to the user's `.bashrc`, or drops an
init file into their home directory, is not an acceptable implementation** even though it
would be the easiest one: it changes a machine the user has to live in after Acter is
closed, and it fails differently for every distribution.

### 3. The injection is measured, and it may not fully succeed

Candidates, in the order they will be tried:

- **`WSLENV` carrying `PROMPT_COMMAND`.** Bash evaluates `PROMPT_COMMAND` before drawing
  each prompt, and an interactive bash inherits the environment before it sources
  `.bashrc`. Many `.bashrc` files set `PS1` and never touch `PROMPT_COMMAND`, so this is the
  candidate most likely to survive the user's own configuration.
- **`WSLENV` carrying `PS1`.** Simpler and more fragile: a distribution's default `.bashrc`
  usually sets `PS1` unconditionally and would overwrite ours.
- **`bash --rcfile` or `--init-file`** pointing at a file inside the distribution. Ruled out
  by decision 2 unless nothing else works, and then only in the open.

**What happens if none of them survives is already designed for.** `ShellMarkers` exists
precisely so a shell can declare it marks less than everything, and B4.5 established that a
shell which cannot emit `C` gets a session that degrades honestly rather than one that
looks integrated and says nothing. A WSL adapter that can only mark `A` and `B`, or nothing
at all, is a correct outcome of this entry — what is not correct is claiming markers that
do not arrive.

### 4. What is installed goes behind a port of its own

Running `wsl.exe -l -q` is I/O: it starts a process, it depends on what is on the machine,
and it can fail. That is an adapter by ARCHITECTURE's classifying question, so it gets a
port:

```rust
pub trait InstalledShells: Send + Sync {
    /// Which WSL distributions this machine has, in the order WSL reports them.
    fn wsl_distributions(&self) -> Vec<String>;

    /// Whether this program can be started at all — how PowerShell 7 is offered only
    /// where it exists.
    fn is_available(&self, program: &str) -> bool;
}
```

One real implementer in `acter-shells`, one fake for tests, and B7 is its only consumer.
It carries both questions rather than one, because "what can this machine run" is a single
question the connect list asks once, and two ports answering halves of it would be two
fakes to keep in step.

**The output is UTF-16LE**, measured on this machine 2026-08-23: `wsl.exe -l -q` returned
bytes that read as `U b u n t u` when decoded as UTF-8. Decoding it correctly, including
the byte-order mark and the trailing carriage returns, is the substance of this adapter and
gets a unit test over captured bytes rather than a live process.

### 5. Everything installed is listed, including `docker-desktop`

The same machine reported `docker-desktop` beside `Ubuntu`. **Acter does not filter it
out.** Deciding which of a user's distributions is a "real" one is not knowledge this
program has, the guess is invisible to the person it is wrong for, and a user who wants a
shell in that distribution is entitled to it. If the list is noisy, that is WSL's noise and
the user can read it.

### 6. Failure is a sentence, not an empty list

`wsl.exe` missing, WSL not enabled, or no distribution installed are three different
situations and all three end with "there is no WSL entry in the connect list". The adapter
reports them apart so B7 can say which one happened. A user who has never installed WSL and
a user whose WSL is broken need different sentences, and neither is served by a list that
silently omits a thing they expected to see.

## Files touched

- `crates/acter-core/src/ports/driven/installed_shells.rs` — the port (new).
- `crates/acter-shells/src/wsl.rs` — the adapter, the distribution list, the UTF-16 decode.
- `crates/acter-shells/src/installed.rs` — the real `InstalledShells` implementer.
- `crates/acter-shells/src/lib.rs` — facade and `adapter_for`.
- `crates/acter-transports/tests/real_session.rs` — a real WSL session, `#[ignore]`d and
  skipped when WSL is absent, the way the Docker tests are skipped.

## Definition of done

- [ ] The UTF-16LE decode is unit-tested against captured bytes, byte-order mark and
      carriage returns included, with no process involved.
- [ ] `docker-desktop` is listed rather than filtered, and there is a test saying so on
      purpose.
- [ ] A real session starts in a real distribution, runs a command and returns its output.
- [ ] Whatever marker level survives a real `.bashrc` is measured, declared in
      `ShellMarkers`, and the session degrades honestly if it is less than full — the
      failure mode is a badly-labelled line that is still spoken, never a silent one.
- [ ] Nothing is written into the distribution: no file created, no dotfile appended, and a
      test or a recorded manual check saying so.
- [ ] An interrupt stops a program inside WSL. This is already measured (22.6) and is
      pinned here as a test, since this is the first shipped shell where it is the *product*
      relying on it rather than a probe.
- [ ] The three "no WSL here" situations are distinguishable.
- [ ] `cargo fmt`, `cargo clippy --workspace --all-targets`, workspace tests clean, and the
      workspace run still spawns no process.

**Accessibility checklist in the PR body**: a WSL session is navigable — headings where the
markers allow them, output that reads, and, if the session degrades to unintegrated, the
existing spoken explanation for that rather than silence.
