# B5.3 — the WSL adapter, and what is installed

Roadmap entry 23.3. Agreed in conversation 2026-08-23. Depends on 23.1 for the port.

Two things at once, and they are related: a bash far end reached through `wsl.exe`, and the
first port that answers **what this machine actually has**, since a WSL adapter with no
distribution to name is not a session anyone can start.

## What 22.6 already measured about this far end

Measured 2026-08-23 and not to be re-derived: `wsl.exe` is a client to a shell in another
kernel, exactly as `docker.exe` is. Two consequences land directly on this entry.

**An interrupt reaches it, and it reaches it as data.** `0x03` written to the pseudoconsole
crossed `wsl.exe` into the distribution, bash's own line discipline turned it into `SIGINT`,
the running loop died and the prompt came back — zero ticks in six seconds. So nothing
special is needed here for Ctrl+C.

**Environment variables do not cross.** A variable set on the Windows side is not in the
distribution's environment unless `WSLENV` says to pass it. This is the constraint that
shapes the injection below, and it is why the mechanism cannot simply be copied from cmd.

## Decisions

### 1. The launch names a distribution

`wsl.exe -d <distro>`, one adapter value per distribution, the way PowerShell has one per
edition. The distribution name is data the adapter carries, which is the reason 23.1's
`ShellLaunch` is owned rather than borrowed.

### 2. Acter does not edit the user's machine to get integration

The pinned constraint for this entry, and the one that decides the injection. cmd's markers
ride in an environment variable — "no snippet to source, no profile to edit, nothing to
fail silently on a locked-down machine" — and PowerShell's ride in a `-Command` argument.
Neither writes anything. **A WSL adapter that appends to the user's `.bashrc`, or drops an
init file into their home directory, is not an acceptable implementation** even though it
would be the easiest one: it changes a machine the user has to live in after Acter is
closed, and it fails differently for every distribution.

### 3. The injection is measured, and it may not fully succeed

**Measured 2026-08-24, and it fully succeeded.** The first candidate below is the one that
shipped, and it reaches further than this decision expected: the full OSC 133 cycle with
real exit codes, not the `A` and `B` the pessimistic case allowed for. What was measured,
and the two bash facts that shape the program, are written out under "What was measured"
below. `ShellMarkers::Full` is therefore a measurement here rather than the assumption
`Plain` makes.

Candidates, in the order they will be tried:

- **`WSLENV` carrying `PROMPT_COMMAND`.** Bash evaluates `PROMPT_COMMAND` before drawing
  each prompt, and an interactive bash inherits the environment before it sources
  `.bashrc`. Many `.bashrc` files set `PS1` and never touch `PROMPT_COMMAND`, so this is the
  candidate most likely to survive the user's own configuration.
- **`WSLENV` carrying `PS1`.** Simpler and more fragile: a distribution's default `.bashrc`
  usually sets `PS1` unconditionally and would overwrite ours.
- **`bash --rcfile` or `--init-file`** pointing at a file inside the distribution. Ruled out
  by decision 2 unless nothing else works, and then only in the open.

**What happens if none of them survives is already designed for.** `ShellMarkers` exists
precisely so a shell can declare it marks less than everything, and B4.5 established that a
shell which cannot emit `C` gets a session that degrades honestly rather than one that
looks integrated and says nothing. A WSL adapter that can only mark `A` and `B`, or nothing
at all, is a correct outcome of this entry — what is not correct is claiming markers that
do not arrive.

### 4. What is installed goes behind a port of its own

Running `wsl.exe -l -q` is I/O: it starts a process, it depends on what is on the machine,
and it can fail. That is an adapter by ARCHITECTURE's classifying question, so it gets a
port:

```rust
pub trait InstalledShells: Send + Sync {
    /// Which WSL distributions this machine has, in the order WSL reports them.
    fn wsl_distributions(&self) -> Result<Vec<String>, NoDistributions>;

    /// Whether this program can be started at all — how PowerShell 7 is offered only
    /// where it exists.
    fn is_available(&self, program: &str) -> bool;
}
```

**Amendment 1, forced by decision 6.** The signature above returned a bare `Vec<String>` as
agreed, and a `Vec` cannot tell three situations apart: an empty one is exactly the silent
omission decision 6 forbids. It returns a `Result` instead, whose error is the
`NoDistributions` enum decision 6 describes. Nothing else about the port changed.

One real implementer in `acter-shells`, one fake for tests, and B7 is its only consumer.
It carries both questions rather than one, because "what can this machine run" is a single
question the connect list asks once, and two ports answering halves of it would be two
fakes to keep in step.

**Amendment 2: the fake travels with its consumer, so it is not in this PR.** B7 is the
only thing that will ever inject one, and a fake nothing injects is unreachable code that
the visibility ladder would have to make `pub` for nobody. The real implementer is
`ThisMachine`; the decode it depends on is a pure function, so everything worth asserting
about a distribution list is asserted here without one.

**The output is UTF-16LE**, measured on this machine 2026-08-23 and again 2026-08-24:
`wsl.exe -l -q` returned bytes that read as `U b u n t u` when decoded as UTF-8. Decoding
it correctly, including the trailing carriage returns, is the substance of this adapter and
gets a unit test over captured bytes rather than a live process.

**Amendment 3: there was no byte-order mark.** The spec expected one and named it in the
definition of done. Sixty-four bytes of output on WSL 2.5.7.0 began straight at the first
character — the first two bytes are `55 00`, not `ff fe`. One is stripped anyway if it ever
appears, since a mark that reached a caller would become an invisible first character of a
distribution's name, and the test that says so also asserts that the capture itself carries
none. The claim "a real WSL emits a byte-order mark here" is therefore **withdrawn, not
verified**: it may be true of some other WSL version, and this repository has no evidence
of it.

### 5. Everything installed is listed, including `docker-desktop`

The same machine reported `docker-desktop` beside `Ubuntu`. **Acter does not filter it
out.** Deciding which of a user's distributions is a "real" one is not knowledge this
program has, the guess is invisible to the person it is wrong for, and a user who wants a
shell in that distribution is entitled to it. If the list is noisy, that is WSL's noise and
the user can read it.

### 6. Failure is a sentence, not an empty list

`wsl.exe` missing, WSL not enabled, or no distribution installed are three different
situations and all three end with "there is no WSL entry in the connect list". The adapter
reports them apart so B7 can say which one happened. A user who has never installed WSL and
a user whose WSL is broken need different sentences, and neither is served by a list that
silently omits a thing they expected to see.

## What was measured

Everything in this section was taken off this machine on 2026-08-24, driving a real
`wsl.exe` through `LocalPty` on a real pseudoconsole — the way B4.5 measured cmd's `PROMPT`
— or by running `wsl.exe` and dumping its bytes. Nothing here comes from documentation. The
machine: WSL 2.5.7.0, kernel 6.6.87.1, Windows 10.0.26200.9168, with Ubuntu 24.04.2 (bash
5.2.21), `docker-desktop` and Debian installed.

### The distribution list

`wsl.exe -l -q` redirected to a file produced sixty-four bytes, exit code 0, standard error
empty. In hexadecimal, the first sixteen: `55 00 62 00 75 00 6e 00 74 00 75 00 0d 00 0a 00`
— `U b u n t u CR LF`, one zero byte after each character. The whole capture is three
names: `Ubuntu`, `docker-desktop`, `Debian`, each terminated `0d 00 0a 00`. Those exact
bytes are the fixture the decode is tested against, spelled out in
`crates/acter-shells/src/wsl/distributions.rs` rather than built by a helper.

`docker-desktop` is listed beside the two distributions a person installed, which is what
decision 5 is about; it is offered rather than filtered, and a test says so on purpose.

A distribution name that does not exist produced `There is no distribution with the
supplied name.` on **standard output**, in UTF-16LE, with exit code 127 and standard error
empty. Reading only standard error would have produced a broken-WSL sentence with nothing
after it, which is why the adapter reads stdout first.

### The injection

`WSLENV=PROMPT_COMMAND` plus a `PROMPT_COMMAND` holding a small bash program. It survives
the user's own `.bashrc` because bash exports the environment into the shell *before* it
sources that file, and every Debian-family default `.bashrc` sets `PS1` unconditionally and
leaves `PROMPT_COMMAND` alone. So the injection runs after the user's configuration and
gets to wrap the prompt that file chose, rather than losing to it — which is the opposite
of what the `PS1` candidate would have done, and the reason the candidate order in decision
3 is the right one.

What three submissions produced, escapes written out. `ESC ] 133 ; A ESC \`, then Ubuntu's
own green-and-blue `marlon@splyt:/mnt/c/Users/marlo$`, then `ESC ] 133 ; B ESC \`, then the
echo of the submitted line; then `ESC ] 133 ; C ESC \` and the command's output; then
`ESC ] 133 ; D ; 0 ESC \`. `false` closed with `ESC ] 133 ; D ; 1 ESC \` and an interrupted
loop with `ESC ] 133 ; D ; 130 ESC \`. Counted across the session: four prompts drawn, four
`A`, four `B`, three `C`, three `D`. Debian produced the same stream, and so did `wsl.exe`
with no `-d` at all.

**Two bash facts, both measured rather than read, and both load-bearing.** `C` has to come
from a `DEBUG` trap, since nothing else fires between Enter and the command running. The
obvious way to fire it once is to have the trap remove itself, and that does not work: a
`trap - DEBUG` executed inside a shell function is discarded when the function returns,
while a `trap ... DEBUG` set inside one sticks. The self-removing version emitted four `C`
markers per command instead of one. The guard is therefore a variable the trap sets and the
prompt clears. And a trap armed inside a function fires for the statements that follow it
*in that same function*, so the guard is cleared before the trap is armed and never after —
the other way round put one spurious `C` before the session's first prompt.

**Nothing was written into the distribution.** `.bashrc` and `.profile` hashed identically
before and after an integrated session, the home directory listing was unchanged at
thirty-one entries, and the same check asked from *inside* the running session agreed. A
test pins it by comparing a hash taken inside the session against one taken from a
`wsl.exe` Acter never drove. Bash's own append to `.bash_history` is excluded deliberately:
that happens whenever a person uses bash and is bash's business, not Acter's.

### One thing worth knowing that is not a defect

A WSL session can be flagged `IntegrationUnavailable` before its first marker arrives,
because starting a distribution takes seconds and the grace period may be shorter. DESIGN
decision 8 already covers it — a marker arriving later upgrades the session silently — but
it means "was this session ever flagged" is a question about the clock as much as about the
shell. The real-shell suite's accelerated two-hundred-millisecond grace does flag a WSL
session; the shipped five seconds does not, on this machine, and the test that asserts the
session is integrated uses the shipped value rather than the accelerated one.

  (new), plus the three facades above it.
- `crates/acter-shells/src/wsl.rs` — the adapter.
- `crates/acter-shells/src/wsl/injection.rs` — the measured `PROMPT_COMMAND` program and
  the `WSLENV` entry that carries it (new).
- `crates/acter-shells/src/wsl/distributions.rs` — the UTF-16LE decode (new).
- `crates/acter-shells/src/installed.rs` — the real `InstalledShells` implementer,
  `ThisMachine`.
- `crates/acter-shells/src/lib.rs` — facade; `crates/acter-shells/src/selection.rs` —
  `adapter_for`.
- `crates/acter-transports/tests/real_session.rs` — four real WSL sessions, `#[ignore]`d and
  skipped when WSL is absent, the way the Docker tests are skipped.
- `crates/acter-app/src/container.rs` — one doc comment, no behaviour.

**Amendment 4: `wsl.rs` earned a folder.** The spec put the adapter, the distribution list
and the decode in one file. They are three concepts with three sets of tests, and the
injection alone is forty lines of measurement written down, so the module has genuinely
private internals and takes `wsl/` by the same rule `adapter_for` took its own module in
B5.1. The decode does not live under the adapter for tidiness: it is a *policy* — pure
bytes in, names out — and the adapter that runs the process is `installed.rs`, which is the
only file in the crate holding a `Command`.

**Amendment 5: `adapter_for("wsl.exe")` starts WSL's own default distribution.** That
function has a program name and nothing else, so it cannot name one. Naming a distribution
is the connect list's business and B7 builds `Wsl::in_distribution` directly. Asking WSL to
pick is not the same as this program picking: only the first of the two is still right
after a user changes their default. Measured to start the same integrated bash as a named
distribution does.

**Amendment 6: one doc comment in the composition root.** `ACTER_SHELL`'s documentation
said "`cmd.exe` is now integrated, and nothing else is", which this entry makes false. It
now names both. No code in `acter-app` changed.

## Definition of done

- [x] The UTF-16LE decode is unit-tested against captured bytes, carriage returns included,
      with no process involved. Eleven tests in `wsl/distributions.rs` over the sixty-four
      bytes this machine produced. The byte-order mark this item also asked for is
      **amendment 3**: none was emitted, so the test asserts both that one would be
      stripped and that the capture carries none.
- [x] `docker-desktop` is listed rather than filtered, and there is a test saying so on
      purpose: `a_service_distribution_is_offered_rather_than_hidden`.
- [x] A real session starts in a real distribution, runs a command and returns its output.
      Four `#[ignore]`d tests at the end of `real_session.rs`, green against a real
      `wsl.exe` on 2026-08-24.
- [x] The marker level that survives a real `.bashrc` is measured, and it is **the full
      cycle with real exit codes** — better than this item allowed for, so the degradation
      path is not exercised by the shipped adapter. It is still the answer to a `.bashrc`
      that sets `PROMPT_COMMAND` itself: no marker arrives, the session is flagged
      unintegrated, and the user hears the existing explanation rather than silence.
- [x] Nothing is written into the distribution: hashes of `.bashrc` and `.profile` and the
      home directory listing identical before, during and after an integrated session, and
      `a_wsl_session_leaves_the_distributions_own_files_alone` pins it. A unit test also
      forbids the injection string from containing a redirection, an `--rcfile`, a
      `source`, a `tee` or an `mkdir`.
- [x] An interrupt stops a program inside WSL:
      `an_interrupt_stops_a_program_inside_a_wsl_distribution`, which additionally sees the
      `130` arrive in a `D` marker — the interrupt is not merely delivered, it is reported.
- [x] The three "no WSL here" situations are distinguishable: `NoDistributions` has three
      variants with three different spoken sentences, tested. **Two of the three were
      reproduced on this machine** — a refusal (an unknown distribution: exit 127, WSL's
      own sentence on stdout) and a successful list. A machine with `wsl.exe` absent and a
      machine with WSL and no distribution were **not** reproduced here; their code paths
      are unit-tested over the process outcome, not against a real such machine.
- [x] `cargo fmt --all`, `cargo clippy --workspace --all-targets` and `cargo test
      --workspace` clean on 2026-08-24, and the workspace run still spawns no process:
      `is_available` looks a name up on `PATH` rather than running it, and every test that
      needs a live `wsl.exe` is `#[ignore]`d and says so in its ignore reason.

**Accessibility checklist in the PR body**: a WSL session is navigable — headings where the
markers allow them, output that reads, and, if the session degrades to unintegrated, the
existing spoken explanation for that rather than silence.
