# B4.6 — an interrupt through a proxied shell

Roadmap entry 22.6. Measured 2026-08-23, before anything was proposed, because the entry
named two outcomes with different consequences and said plainly that they are
indistinguishable from Acter's own stream — output stops either way — so the difference
had to be decided by looking at the container.

## The measurement, which decides it

### The blocker was stale

The entry ended with "Not measurable on the development machine as of 2026-08-22 — Docker
is not installed". Docker 29.7.2 with a Linux daemon is installed and running on this
machine, and everything below was measured on it. Nothing else in the entry rested on that
line, and it is replaced rather than amended.

### Twenty-four leaked containers had to be cleaned up first

Before measuring anything: twenty-four `alpine` containers on this machine, seventeen of
them still running, the oldest up twenty-four hours — left behind by the Docker tests of
B4.9 and B4.10. They were removed before the probe ran, because a stale container is
exactly what the "the client died and the container survived" outcome looks like, and one
left standing would have read as this measurement's survivor. The leak itself is measured
below, and it turns out not to be Acter's.

### The byte crosses as data, three runs out of three

The probe drives a real `cmd.exe` on a real `LocalPty` — no session service, no engine
beyond the one that answers device queries — enters `docker run -it --name … alpine sh`,
and starts a loop that prints one `tick-N` per second, so that **the container's own
stdout is a clock**. Then it writes `0x03` and asks the container rather than asking our
own stream.

Every run, identical:

- 16 to 22 milliseconds after the write, our stream carries `^C`, a carriage return, a
  line feed and the container's prompt. That `^C` is the **container's** tty echoing the
  control character, which is direct evidence that the byte arrived inside as data rather
  than being consumed as a console event on this side.
- The container's own stdout, read back with `docker logs`, stops at exactly the tick our
  stream stopped at — `tick-3` on both sides. The loop is dead **inside the container**,
  not merely inaudible to us.
- `docker top` shows only the container's `sh`; the `sleep` child is gone.
- `docker inspect` reports the container still running.
- `uname -s` submitted afterwards answers `Linux`, so the client is still attached, the
  container's shell is still the far end, and the session goes on working.

That is the entry's first outcome on every one of its signatures. The second — ConPTY
turning the byte into a console control event aimed at the client, killing `docker.exe`
and detaching or killing the container — is ruled out on all of them.

### It is not a fact about Docker

The same probe through `wsl.exe -d Ubuntu`: `^C`, **zero** ticks in the six seconds after
the interrupt, bash's prompt redrawn, `uname -s` still answering `Linux` from inside WSL,
and `exit` returning cleanly to the outer `cmd.exe`. A different client, a different kernel
boundary, an identical shape.

So the finding is about `0x03` being data all the way down rather than about Docker, which
makes `ssh` and `kubectl exec` the same argument rather than two more measurements.

### An interrupt at an idle proxied prompt is harmless

`0x03` at the container's own idle prompt echoes `^C`, redraws the prompt — cursor hidden,
absolute reposition, cursor shown — and leaves the container running. The same nothing
`cmd.exe` does.

Recorded here because 22.8 sends exactly that: a real session believes a command is always
running, so Ctrl+C at an idle prompt is accepted and written. A proxy does not make that
worse, and 22.8 does not need to treat proxied sessions as a separate case.

### What was not measured, deliberately

Whether `docker.exe` clears `ENABLE_PROCESSED_INPUT`. The entry named it as the mechanism,
and it stays a presumption. What was measured is the container echoing the control byte and
signalling its own foreground job, which is the observable the entry needs whatever the
mode bit says.

**B4.1's four disproven mechanisms are the reason not to promote a plausible mechanism to a
finding on the strength of behaviour that merely agrees with it.** Reading another
process's console input mode would need attaching to its console, which is a great deal of
machinery to confirm something no decision depends on.

## The container outlives the session, and it is not Acter's

Measured on the way past, three runs of three: the session is torn down, `LocalPty::drop`
kills `docker.exe`, and three seconds later the container is still running — `--rm`
notwithstanding, and un-removed as well as un-stopped. That is where the twenty-four leaks
came from, and on its own it looks exactly like a defect of Acter's teardown.

**The control decides it.** `cmd.exe /k docker run -it --rm …` in its own console window,
and then the window closed — `WM_CLOSE`, which is what Alt+F4 posts. Afterwards: the window
gone, `cmd.exe` exited, **zero** `docker.exe` processes left, and the container still
running and still not removed. Windows delivers `CTRL_CLOSE_EVENT` with its five-second
grace; the client either ignores it or does not get far enough to stop the container, and
the end state is byte for byte what Acter's teardown produces.

So Acter is doing what the platform's own terminal does, and there is nothing here to fix.
Doing better would mean reaching outside our process tree to stop something that was never
our child — the stance B4.1 settled explicitly, that Acter enumerates and terminates
nothing, because that is the kernel's job done from the wrong layer.

**It is the same structural fact as the finding above, seen from the other side.** The
container is unreachable from this process tree in both directions: teardown cannot stop it
because there is no signal path to it, and the interrupt reaches it *only* because the byte
travels as data. This is written down here, rather than filed as a roadmap entry, so that
the next person to find two dozen leaked containers does not file it as one.

## What follows

### Decision 1 — no product code, and what that bounds about B4.1

The entry's own condition is met: the interrupt already survives a proxied shell, so
nothing in `LocalPty`, the session service or the domain changes.

**What it bounds is how B4.1 may be read.** B4.1's mechanism is the transitive inheritance
of a Windows console attribute, Acter to shell to program, and it cannot be what carries an
interrupt into a container: that shell is the daemon's child, in another process tree and
another kernel. Two independent mechanisms give Acter the same behaviour for entirely
different reasons — the inherited attribute inside our tree, the byte-as-data plus the far
end's own line discipline outside it — and neither depends on the other.

The consequence for B5: **there is nothing for `ShellAdapter` to declare.** "Is this a
proxy" looks like a shell question and is not one; Acter cannot tell, does not need to, and
the correct behaviour is identical either way.

### Decision 2 — one regression test, in `local_pty.rs`

`an_interrupt_survives_a_proxied_shell`, beside the two interrupt tests B4.1 landed,
`#[ignore]`d like everything in that file and skipped with a printed line rather than failed
when Docker is absent — a machine without Docker has not discovered a defect.

It asserts four things, and the shape of the assertions is the point:

1. Our stream stops receiving ticks (one tick of slack, because the interrupt can land
   between the loop printing and the byte arriving).
2. **The container's own stdout stops at the same tick.** This is the half our stream
   cannot answer, and the reason the test talks to `docker logs` at all: a client killed by
   a console control event looks exactly the same from here while the loop runs on unheard.
3. The container is still running, so the interrupt stopped the program rather than the
   container.
4. `uname -s` afterwards answers `Linux`, so the far end is still the container's shell and
   not the `cmd.exe` we came from — which is what fails loudly if a future change kills the
   client instead of signalling the program.

The container is held by a `Container` guard whose `Drop` removes it, so a panicking
assertion cannot leave one behind. It is deliberately started **without** `--rm`, because
`docker logs` and `docker inspect` after the interrupt are the measurement and `--rm` would
delete the evidence in the outcome that matters.

**What it guards is a plausible future change**, which is what earns it its fifteen seconds:
replacing the byte written by `Transport::interrupt` with a Windows console control API —
the obvious-looking thing to reach for while fixing 22.8 — would leave every other interrupt
test passing and silently take the interrupt away from every proxied session.

**The negative control was run**: with the `interrupt()` call removed, the test fails on
assertion 1 with "the loop went on ticking after the interrupt: our stream reached tick-8,
against tick-3 when the interrupt was sent". A test that cannot fail would have been worth
nothing here.

Three consecutive green runs against the real thing; the tick numbers were identical in all
of them.

### Decision 3 — the container leak is not a roadmap entry

For the reason measured above: Acter matches the platform, and the fix direction is closed
by B4.1's stance. It lives in this spec and in the test's `Container` doc comment, which is
where someone hitting it will be standing.
