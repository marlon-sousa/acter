# Spec: PR B4.2 — text that scrolled away must not be said twice

Agreed in conversation 2026-08-22. Lane 2, entry 22.2. Stops a previous command's rows
being emitted into the current command's block as they scroll off the emulated screen.

## Why now / relation to the roadmap

The most severe open defect on the board, and the reason it outranks its number. It is not
a cosmetic repeat: content from a *finished* command interleaves line by line into the
block a user is reading, so a screen reader user reviewing that block has no way to tell
which lines belong to the command they ran. The buffer becoming unreadable is this
product's worst failure mode. It also blocked an accessibility check in B4.1's own PR —
the tail after an interrupt could not be judged for comfort because everything around it
was debris from another command.

It degrades exactly the sessions B4.1 just made usable: a real shell, long enough to
scroll, which is every real shell.

## What was measured

From the user's manual pass, captured 2026-08-22. A session that had earlier run
`dir /s C:\Windows\System32`, then ran and interrupted `ping -n 20`. The `ping` block
contains the replies alternating with `fms.dll.mui`, `mlang.dll.mui`,
`Total Files Listed`, `27253 File(s)` and `5793 Dir(s)` — the last screenful of the
finished `dir`, one row per new line of `ping` output.

One old row per new line of output is the signature of the mechanism below, and it is what
rules out the entry's original reading of "the current command's own output said twice".

## The mechanism, in two halves

The roadmap entry names the pump's cleared record. That is half of it. The other half is
that **the extractor is never told a boundary happened at all** in an unintegrated session.

1. `AlacrittyEngine::place` calls `Extractor::settle_block` **only** on
   `Osc133Marker::CommandEnd` (`alacritty_engine.rs:101`). A real `cmd.exe` emits no
   markers, so the extractor's on-screen rows are never frozen: they keep their `LineId`
   and their `emitted` text across submissions, indefinitely.
2. The user submits the next command. `Pump::submit` sees `Integration::Unintegrated` and
   calls `close(None)` (`session.rs:388`), which does `self.lines.clear()`
   (`session.rs:506`).
3. Each new line of output scrolls the screen by one, pushing one old row above
   `View::top`. `Extractor::emit_line` takes the live-line branch and emits `Settled`
   carrying that row's **full text** (`extractor.rs:203`).
4. `Pump::due` does `self.lines.remove(&id).unwrap_or(true)` (`session.rs:574`). The record
   was erased in step 2, so `None` becomes `true` — *owed* — and the old row's text is
   forwarded into the open block.

## Design decisions this spec makes

1. **Dropping the line is the only correct destination, because there is nowhere else to
   put it.**

   `SessionInput::Output` carries `text` and no `LineId` (`session_actor.rs:45`). A line
   belonging to a block that has closed therefore cannot be filed to that block: the only
   reachable destinations are the open block, which is the defect, and nowhere. This is
   what removes "route it to the block it belongs to" from the candidate list before any
   of the entry's three options are weighed, and it is why the fix is a rule about what the
   pump *declines* to forward rather than machinery for late delivery.

2. **The fix is `Pump::close` demoting its record instead of clearing it.**

   `lines: HashMap<LineId, bool>` maps a line to whether its final text is still owed:
   `false` once some of its text has been forwarded, `true` if it was rewritten and the
   final text has not been. `close` replaces `clear()` with setting every remaining entry
   to `false`.

   The demotion is factually accurate rather than a convenient lie. Every entry in the map
   at a boundary describes a line whose text was forwarded to the block that is closing —
   a `Rewritten` only ever reaches `due` for a line that appended first, since the
   extractor's first emission for any line is `Appended` or `Settled`. So at a boundary,
   whatever these lines had to say was said, to the block it belonged to, and nothing
   further is owed to anyone.

3. **`unwrap_or(true)` stays, and the demotion is what makes it honest.**

   The default exists for a real case: a line that scrolled past inside a single read,
   never having appended, arrives settled and complete and is genuinely owed. The bug was
   never that default — it was that `clear()` manufactured a second, unrelated way to have
   no record, and the default could not tell the two apart. With the record kept, "no
   record" means only "never seen", which is what the default assumes.

4. **The extractor is unchanged, and the `close`/`settle_block` orders do not need to
   agree.**

   In an *integrated* session the demotion is a no-op, and it is worth stating why rather
   than discovering it later. `place` pushes `settle_block`'s items into the batch **before**
   the `CommandEnd` marker, so the pump consumes those settlements — each with its record
   present — and only then does the marker produce `BoundaryEvent::BlockEnded` and call
   `close`. The map is already drained by the time the boundary is applied. The change
   therefore alters unintegrated sessions only, which is where the defect lives.

5. **The map is bounded by the screen, not by the session, so keeping it costs nothing.**

   This is the obvious objection to not clearing, and it does not hold. `due` removes an
   entry on `Settled`, and every id the extractor emits as `Appended` is eventually emitted
   as `Settled` on some path: scrolling out of the screen area (`emit_line`), being
   swallowed as a continuation (`absorb`), a block boundary (`settle_block`), a screen
   change or resize (`settle_and_forget`), or staging saturation (`settle_from_record`). So
   the map holds exactly the lines that are live on screen. `clear()` was hygiene against a
   leak that cannot happen, and the map is *already* documented as deliberately outliving
   regions (`session.rs:285`).

6. **`last_line = None` at `close` stays.** It is separator bookkeeping, not the line
   record, and a new block must not inherit the previous one's idea of what it was
   separating from.

7. **The premise is measured against the real engine, not read out of it.** *(Added
   during implementation.)*

   Everything above rests on one claim about a component this PR does not touch: that the
   extractor really does re-emit a finished command's rows as `Settled`, with their full
   text, while the next command is running. That claim was read from `extractor.rs:203`.
   Reading is not measuring, and the service tests cannot close the gap — they hand
   `TerminalItem`s to a fake engine, so they assert the pump's rule against a premise they
   themselves supply.

   So the fix is also pinned one layer down, where a real `AlacrittyEngine` scrolls a real
   grid, and again with no fake anywhere in the stack at all. Both fail on the parent
   commit with the interleaving the capture showed, which is what turns "this explains the
   symptom" into "this is the symptom".

## Rejected alternatives

- **Keep the record unchanged rather than demoting it** (the entry's first option). One
  line shorter, and it leaks the case where a previous block's row was rewritten before the
  boundary: its entry is `true`, so its eventual settlement is still forwarded into the
  wrong block. Rare — it needs cursor addressing back into a finished command's rows — but
  the demotion costs one iteration over an at-most-screenful map and closes it, and a fix
  that is *nearly* complete for the product's worst failure mode is not worth the saving.

- **Ignore settlement for any line whose text was already forwarded** (the entry's second
  option). This is the same rule stated as a global invariant rather than a boundary
  action, and it is strictly worse: it also suppresses the legitimate case where a line
  appended, was rewritten, and settles inside the same block, which is how a progress line's
  final text reaches the user.

- **Have the pump signal the engine so `settle_block` runs at an unintegrated boundary
  too.** This fixes it at the source — old rows would settle *at* the boundary rather than
  dribbling out during the next command — and it is the more principled shape. It is
  rejected for B4.2 on scope and sequencing: it is a port change to `TerminalEngine`, and
  22.5 measured that `cmd.exe` can carry OSC 133 `A` and `B` from `PROMPT`, so the
  population of marker-less sessions this would serve is about to change shape. Deliberately
  left as a possibility for after 22.5 rather than foreclosed.

- **Reaching for `Term::damage()` or any other "what changed" signal.** Out of scope and
  already decided against in B3 for the reason `extractor.rs:17` records: damage filters out
  anything not currently visible, which is exactly the population of rows this defect is
  about.

## Tests

Service, in `session.rs`, against the fake far end. The defect is reproducible there
because the fake engine is fed `TerminalItem`s directly, which is exactly the shape the
real extractor produces when an old row scrolls off:

- **The regression, stated as the capture.** An unintegrated session appends a line, the
  user submits a new command, and the old line then settles with its full text. Its text
  must not appear in the new block. This test fails on the current tree.

  A helper is added for the third revision — `settled(id, text)`, beside the existing
  `line` and `rewritten` — and one for reading `Output` events as a list rather than as
  the single concatenated string `rendered()` returns, since what is under test is which
  block received what.
- The interleaving shape specifically: two old lines settling between two lines of the new
  command's output leave the new block containing only its own two lines, in order.
- A line rewritten before the boundary and settled after it is also dropped — the case
  plain keeping would have leaked, pinned so the choice between the two options cannot
  silently regress.
- **The case the default exists for still works**: a line first seen as `Settled` inside
  the open block, having never appended, is still forwarded. This is what stops the fix
  from being "drop settlements", and it fails if `unwrap_or` is flipped.
- An integrated session is unaffected: a full `command(..)` sequence renders exactly its
  own output, before and after the change.

Pipeline, in `pipeline.rs`, against the real `AlacrittyEngine` — decision 7's first half.
The built-in transcript already has the ingredients: `big` is thirty rows on a twenty-four
row screen, and `Unmarked` takes the markers off any far end, which is what makes the
extractor keep its rows across the submission.

- `big` then `small`. The flood's block keeps all thirty of its rows — text is never lost,
  which is the invariant the fix must not buy its correctness from — and the second block
  has `hello from acter` and no row of the first. On the parent commit it has `line 8` and
  `line 9` interleaved between the new rows, one per row.

Real session, in the new `real_session.rs` — decision 7's second half, `#[ignore]`d.

- A real `cmd.exe` prints forty rows onto a twenty-four row screen, then runs one `echo`.
  The second block holds only the `echo`. On the parent commit it holds three stale rows
  wrapped around it.
- The same, one shell deeper: `sh` in an Alpine container inside that `cmd.exe`. This is
  the regime the defect cannot be argued out of — markers are injected into the shell
  Acter launches, and a container's shell is on the far side of that injection point, so
  no amount of B5 can integrate it. It fails on the parent commit exactly as the flat case
  does, which establishes that nesting is not a second mechanism needing a second fix.
  Skipped, loudly, where no Docker daemon is running.

## Acceptance criteria

1. `cargo test --workspace` green; `cargo clippy --workspace --all-targets` clean under
   `-D warnings`; `cargo fmt --check` clean; `npm run test:ui`, `npm run typecheck` and
   `npm run test:e2e` all green. (There is no `npm test` script; earlier specs name one.)
2. The regression test above fails on the parent commit and passes on this one, and the
   rewritten-row test additionally fails under the rejected "keep the record unchanged"
   variant — so the choice between the two options is pinned by a test rather than by
   this document.
2a. The pipeline and real-session regressions also fail on the parent commit, so the
   extractor's behavior is measured rather than assumed (decision 7). Recorded in the PR
   body: what the pre-fix block actually contained, in each of the three layers.
3. `acter-term` and every port are unchanged; no new dependency anywhere.
4. Module role rule and the visibility ladder hold.
5. **Accessibility checklist in the PR body**: a real `cmd.exe` session in the real app,
   long enough to scroll, running a second command after a first one whose output filled
   the screen — the second block reviewed through NVDA and confirmed to contain only its
   own output. Which items were agent-observed through the screen-readers bridge and which
   were human-verified is stated plainly.

## Out of scope

- **Reading anything aloud.** An unintegrated session still reads nothing; that is 22.4.
  This entry makes the buffer correct, which is what review depends on and what the
  blocked B4.1 check needed.
- **22.3's teardown read.** Independent, and untouched by this.
- **The prompt row's echo appearing in the new block.** In an unintegrated session the
  shell echoes the submitted line onto the row the prompt is on, which is an `Appended` to
  a line that already existed — decision 10's "every line, echo included" rule, deliberate
  and unchanged here.
- **Whether a boundary should freeze the extractor's rows.** Recorded above as rejected for
  this entry rather than for good; revisit after 22.5.
