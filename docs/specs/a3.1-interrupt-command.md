# Spec: PR A3.1 — stopping a running scenario (fake-side)

Adds a typed `stop` line to the fake's scenario table that halts every running
scripted command, and the protocol event that lets the frontend announce it. The
endless scenarios (`forever`, `tail`, `burst`, `slow`) stop being one-way doors, so a
manual NVDA session or an E2E spec can return to a clean state without restarting the
app.

## Why now / relation to the roadmap

- New lane-1 entry A3.1, inserted before A4. It is an A3 iteration entry rather than
  an A5.x entry: A5.x is reserved for findings from an NVDA pass, and this is a scope
  addition agreed in conversation on 2026-08-15, motivated by test reproducibility —
  after `forever` or `tail`, neither a manual session nor an E2E spec can get back to
  a clean state.
- **Deliberately scoped below the user-facing interrupt.** The first draft of this
  spec also wired `Ctrl+C` in the edit field (the surface DESIGN.md's keystroke map
  already decided) and added `interrupt_command` to `SessionApi` with an
  `InterruptAck`. That was cut in the same conversation, because an input-model
  question is open (below) whose answer decides whether any of it survives. What
  remains here is the part that survives either answer.

### The open question this spec deliberately does not bet on

A change to the edit-field ownership model is under discussion: passing every
keystroke through to the terminal, labelling the edit field with the shell prompt, and
letting backend events write into the field. That would reverse the **Decided**
invariant at DESIGN.md "Edit field ownership (non-interactive mode)". It is not
decided, and it is a DESIGN.md conversation rather than a spec.

It matters here because under a pass-through model `Ctrl+C` is simply byte `0x03`
written to the PTY: there is no port method, no ack, no dedicated announcement — the
shell prints `^C` and redraws its prompt, and Acter merely renders that. So the
frontend `Ctrl+C` surface is exactly the work that would be deleted. This spec omits
it. If the pass-through model is rejected, a follow-up entry adds `Ctrl+C`,
`SessionApi::interrupt_command`, and `InterruptAck` on top of what lands here.

## Design decisions this spec makes

1. **One surface: the typed `stop` line.** It joins the fake's scenario table like any
   other scenario name. It is a fake-only test hook, not a user-facing feature — the
   real backend will not have a command named `stop` — and the scenario table is
   exactly where a fake-only command name belongs.
2. **No `SessionApi` change.** Because `stop` arrives through `submit_command`, the
   fake service can cancel its own running scripts internally. Adding a third port
   method with no frontend caller would be dead code, and its shape is precisely what
   the open question above would dictate. The port stays at two methods.
3. **`stop` stops every running command in the session.** The fake permits concurrent
   commands (A3 decision 7's accepted deviation), and "get me back to a clean slate"
   is the whole motivation. This is fake semantics, recorded as a deviation of the
   same kind, not domain truth about what an interrupt means.
4. **`CommandInterrupted` is a new, terminal protocol event.** Added to `SessionEvent`
   as `CommandInterrupted { command_id }`. It is terminal: no `CommandFinished`
   follows, and the frontend closes the block on it. The alternative — emit
   `CommandFinished` with a SIGINT-convention exit code and map that number to
   different wording — was rejected: it makes announcement wording depend on a magic
   number that is a Unix convention (Windows Ctrl+C exit is `0xC000013A`), and it
   mis-announces a real program that genuinely exits 130. A distinct variant also
   makes A2's exhaustiveness guard force the frontend to handle it.
5. **Pinned announcement string** (a domain requirement, CLAUDE.md): `command stopped`.
   It lives in `ui/src/controllers/app.ts` beside A3's pinned strings, in exactly one
   place (A3 acceptance criterion 6 extends to it).
6. **`stop` never interrupts itself, and says nothing of its own.** It allocates its
   own `CommandId` like any submission, cancels every *other* running command, then
   emits `CommandStarted` and `CommandFinished` (exit 0, `Quiet`). Its empty block
   appears in the buffer, which is honest: a command was typed. With nothing else
   running it is silent — there is no "nothing to stop" announcement, because the only
   surface that could justify one (`Ctrl+C`, which has an ack to report it) is out of
   scope here.
7. **No beep on a stopped command**, even one that had carried a too-big chunk. The
   beep answers "the big output you were warned about has finished"; a stopped command
   already has a spoken answer.
8. **Interruptible sleeps, not thread killing.** Rust has no safe thread cancellation,
   and the scripts are mostly asleep. Each running command gets a cancel token (a flag
   plus a condvar); every scripted delay waits on the condvar with a timeout instead of
   `thread::sleep`, so a stop wakes the playback thread promptly rather than after a
   pending 8-second `tail` interval. Every scenario checks the flag after each wait and
   returns early. This is why the change is not a one-liner in the fake.

## Deliverables

### `acter-core` — protocol only

- `entities/protocol_events.rs`: new `SessionEvent::CommandInterrupted { command_id }`
  variant, covered by the existing round-trip and tagging tests.
- The generated TypeScript mirror (`ui/src/protocol.ts`) is regenerated by the existing
  specta test; the A2 drift guard must be green with the committed file.
- No port change (decision 2), no new command payload.

### `acter-app` — cancellation in the fake

- `services/fake_session.rs`:
  - A `CancelToken` value (flag plus `Mutex<()>`/`Condvar`) and a registry
    `Arc<Mutex<HashMap<CommandId, Arc<CancelToken>>>>` on `FakeSessionService`. A
    command registers on spawn and deregisters when its script ends, however it ends.
  - `sleep(range)` becomes a cancel-aware wait returning whether it was cancelled;
    every scenario arm checks it after each wait and returns early. `forever`'s loop
    exits on the flag.
  - On early return the playback thread emits `CommandInterrupted { command_id }` and
    nothing else — no `CommandFinished`.
  - `Scenario::Stop` added to the selection table for the line `stop`, playing
    decision 6's shape against a clone of the registry handle.

### Frontend

- `controllers/app.ts`: new `CommandInterrupted` case — ensure the block, announce
  `commandStoppedMessage`, then the same cleanup `CommandFinished` performs
  (`tooBig.delete`, `openBlocks.delete`), and deliberately no beep (decision 7). The
  pinned string is exported beside A3's.
- No change to `backend_api.ts`, `routers/tauri.ts`, `keyboard.ts`, `edit_field.ts`,
  or the edit-field port — the entire frontend delta is rendering one more event.

### Tests

- `acter-app` unit (recording sink, all-zero-delays config as in A3):
  - `forever` stopped mid-flight emits `CommandInterrupted` and then nothing further.
  - Two concurrent commands are both stopped by one `stop`; each gets its own
    `CommandInterrupted`.
  - Typed `stop` does not interrupt itself: exact event sequence asserted, including
    its own quiet finish.
  - `stop` with nothing else running emits only its own started/finished pair.
  - A completed command is deregistered, so a later `stop` does not emit a stray
    `CommandInterrupted` for it.
  - Because the mechanism is about waking a *sleeping* script, one case runs with a
    non-zero delay and asserts the stop lands well before that delay would have
    elapsed — an all-zero config cannot prove the wake works.
- `ui` vitest: `CommandInterrupted` announces `command stopped`, closes the block, and
  does not beep even when the command had carried a too-big chunk; the `SessionEvent`
  switch stays exhaustive (A2 guard) with the new variant.
- E2E (WebdriverIO): a new spec submits `forever`, waits for its first chunks, submits
  `stop`, and asserts the stop announcement plus no further output growth.

### Docs

- `ROADMAP.md`: insert this entry as lane-1 entry 8 (renumbering the entries after it),
  flipped to Done with this spec's path by the implementing PR.
- No `DESIGN.md` or `ARCHITECTURE.md` change: no rule moves, no new module roles, and
  the keystroke map is untouched because `Ctrl+C` is out of scope.

## Acceptance criteria

1. With `forever` running, typing `stop` halts it: `command stopped` is announced,
   output stops immediately, and the block closes.
2. The same holds for `tail`, `burst`, `slow`, and `nano` — the stop lands during a
   pending delay, not after it expires.
3. `stop` does not interrupt itself and adds no speech of its own.
4. A stopped command that had carried a too-big chunk does **not** beep.
5. `cargo test --workspace` green, including the wake-during-a-real-delay case.
6. `npm run typecheck` and `npm run test:ui` green; the `SessionEvent` switch is
   exhaustive with `CommandInterrupted`.
7. E2E suite green including the new stop spec; the bindings drift guard is green with
   the regenerated `ui/src/protocol.ts` committed.
8. `command stopped` appears verbatim in exactly one place in the frontend.
9. Manual NVDA checklist (below) completed in the PR body; findings spawn A5.x entries.

## Out of scope

- **`Ctrl+C` as an interrupt surface, `SessionApi::interrupt_command`, and
  `InterruptAck`** — deferred pending the input-model question above.
- Interrupting a *real* process (ConPTY, signal delivery) — B4/B6.
- Any edit-field ownership change, prompt-as-label, or shell-side completion — those
  are the open DESIGN question, not this PR.
- Clearing the edit field on stop; configurable keybindings; stopping one specific
  command by id.
- The babble guard, pacing policy, and everything else already deferred to B1.

## Manual accessibility checklist (PR body)

One checkbox per item; findings written inline on the unchecked item (NVDA version,
expected vs observed):

- `forever` then `stop`: `command stopped` is spoken once; no further output arrives;
  focus stays in the edit field.
- `tail` then `stop` during a long gap between lines: the stop is immediate and
  audible, not delayed until the next line would have arrived.
- `big` then `stop` after the too-big announcement: `command stopped` is spoken and no
  beep sounds.
- `stop` with nothing running: silent, and its empty block appears in the buffer —
  confirm this is merely unhelpful rather than confusing (decision 6).
- Two commands running at once, then `stop`: both commands actually stop, and the
  resulting announcement is observed and recorded verbatim. **Amended after the run:**
  a single concatenated utterance is the accepted outcome here, not a failure — see the
  amendment below for why this is a fake-only artifact that is documented rather than
  fixed. What this item checks is that both commands die and that what was spoken is
  written down, not that the two stops are separately intelligible.
- After a stop, the session is immediately usable: submitting `small` behaves exactly
  as on a fresh launch.
- F6 and heading navigation still work across a stopped command's block.

## Amendment (from the manual NVDA run, 2026-08-15)

The checklist was run against a real NVDA 2026.1.1 through the screen-readers MCP
bridge, which captures every utterance as the synthesizer received it. One finding,
recorded here and deliberately **not fixed**.

**Stopping two commands at once produces a single stuttered utterance.** With
`forever` and `tail` both running, one `stop` produced exactly one utterance reading
`command stopped command stopped` — not two. Both `CommandInterrupted` events landed in
the same live-region mutation batch, and the screen reader read the batch as one
utterance. The checklist item asked for "both stops announced intelligibly rather than
colliding into one unparseable utterance", and this is a collision.

**Decided: document it, do not fix it.** Concurrent commands exist only in the fake.
A3 decision 7 accepted that deviation because the fake has no stdin and every Enter
opens a new block; with a real shell there is one foreground command, so two
simultaneous `CommandInterrupted` events cannot occur and the stutter cannot arise.
Fixing it — naming the command in the string (`forever stopped`), or coalescing
same-tick interrupts into `2 commands stopped` — would mean changing a pinned string
and adding batching to the controller to serve a case that disappears at convergence.
Anyone using the fake to stop several scripted commands at once will hear the stutter;
that is a known, accepted artifact of the fake, on the same footing as decision 7
itself.

**What does not disappear at convergence is the mechanism it exposed**, and that is
recorded against DESIGN.md's announcement-channel open question rather than here: two
announcements appended to the live region within one tick are spoken as one
concatenated utterance. That is general — it applies to any pair, such as an auto-read
chunk followed immediately by a failure, or too-big followed by patience — and it is
live evidence for the deferred question of whether status announcements need their own
region with defined ordering. It also bears on B1's babble guard, which is the layer
that would throttle such a flood.
