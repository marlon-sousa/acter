# V2.1 — a heading that repeats the line above it is hidden from sight

Lane 5, the look; roadmap entry 53.1. It follows V2 and comes before V3.

## What is true today

Measured on 2026-09-23 against real shells in far-end line mode, with the V2 build driven over
the embedded WebDriver:

- **An answer to a program's question shows twice.** PowerShell `Read-Host 'Your name'`
  answered `Marlon` gave the row `Your name: Marlon`, then the heading `Marlon`, then the
  output `Marlon`. The same shape appeared for `$host.UI.PromptForChoice(...)` answered `n`,
  cmd `set /p` answered `Marlon`, Python `input()` answered `ok`, and bash `read -p` answered
  `Marlon`. On screen, the heading is a second, brighter copy of the answer.
- **In bash under WSL, not set up, every command shows twice.** The row
  `marlon@splyt:/mnt/c/Users/marlo$ read -p 'Name: ' n; echo hi $n` is followed by the heading
  `read -p 'Name: ' n; echo hi $n`.

These headings come from spec 28 decision 7: at Enter, a non-empty anchored row opens a
block headed by its text. They are how a screen reader user moves through the buffer, and
they stay. The problem is only what a sighted person sees.

## Decisions

1. **The buffer marks a heading `echoed` when the line above it already ends with the
   heading's text.** "The line above" is the element just before the heading in `#results`:
   a prompt paragraph, or the last row of the previous block's output. Both texts are
   compared with trailing whitespace trimmed and cases exactly. The line must be longer than
   the heading, and the character just before the match must be whitespace. So output `ls`
   followed by the command `ls` is not marked, and neither is `dials` followed by `ls`. Every
   measured echo has that space: `Your name: Marlon`, `…$ read -p …`, `Python asks: ok`.
2. **The mark follows the text.** It is worked out again whenever the heading's text changes
   (`openBlock` on a block that exists) and whenever the row above it changes (`applyLine` on
   the last row of the block before). The echoed row can arrive after the heading, and
   bash's unmarked echo does.
3. **CSS hides an `echoed` heading from sight only,** with the same visually-hidden rules the
   edit fields' labels use, so the heading stays in the accessibility tree at level 2.
   **A focused `echoed` heading is shown,** because the buffer focuses the last heading and a
   sighted person must see where focus went.
4. **Nothing else changes.** No role, name or element order changes. A command heading after
   a PowerShell prompt is never marked, because the prompt `PS C:\>` does not end with the
   command. cmd's prompt row `C:\Users\marlo>` does not end with the command either, so
   entry 53.2 is untouched.

## What V2.1 does not do

- It does not make cmd's or unset-up bash's prompts fold. That is entry 53.2.
- It does not stop far-end mode drawing the cursor row twice. That is entry 53.3.

## Acceptance criteria

1. Unit tests in `buffer.test.ts`:
   - a heading after a row ending with its text is marked;
   - a heading after a row that does not end with it is not marked, nor after a row that is
     only the same text, nor when the match starts inside a word;
   - a heading after a prompt paragraph is not marked;
   - a heading whose row arrives or changes afterwards is marked, and unmarked again if the
     row changes away;
   - a heading whose own text changes is re-evaluated.
2. `npm run test:ui`, `npm run typecheck` and `npm run test:e2e` pass, and no existing test is
   edited.
3. Against real shells, screenshots show `Your name: Marlon` followed directly by `Marlon` as
   the output, for PowerShell, cmd and bash; and in unset-up bash, the command once.
4. NVDA 2026.1.1 through the bridge, `user` persona: browse mode reads the `Read-Host` block
   and the bash block the same on main and on this branch, and `h` still stops on every
   heading, including the hidden ones.
