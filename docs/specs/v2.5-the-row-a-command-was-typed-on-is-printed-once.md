# V2.5 — the row a command was typed on is printed once

Lane 5, the look; roadmap entry 53.5.

## What is true today

Found on 2026-09-25 while measuring 53.4, through the `SessionEvent`s of a real `LocalPty`
session in far-end line mode:

- **Keys sent 30 ms apart, the same as `far_end_settle`, at Windows PowerShell 5.1.** After
  `echo before` finished and its prompt was drawn, a block with no command line opened and held
  `o before`, the tail of the row the line was typed on. It was read aloud as "o before". The
  same happened for `echo after` (` echo after`) and `2+2` (` 2+2`), with and without a Ctrl+C
  before them. With keys 80 ms apart, PowerShell and cmd never did it.
- **bash under WSL, integrated, Ctrl+C at an idle prompt, keys 80 ms apart.** Bash echoed `^C`,
  a block headed `^C` failed with 130 (entry 28.12), and after the prompt a block with no heading
  opened holding ` ^C`, from the row the prompt was on. It was read aloud as " ^C". In local
  mode, nothing reached the buffer.
- In both cases the stray block comes after the prompt, so in the buffer the prompt is followed
  by a block with no heading, as in 53.4.

Read from the code and reproduced in session unit tests on 2026-09-25:

- In far-end mode, a row the far end draws in a region the session does not treat as output
  (its prompt and command line, in a marked shell) is set aside in `far_end.printed`. When the
  keystroke settles, `printed` publishes every set-aside row except the cursor's, because the
  cursor's row is the command line and belongs to the field.
- The settle timer is re-armed on every read. With keys 30 ms apart, the same as
  `far_end_settle`, it never fires between keys, so the command line's latest appends are still
  set aside when Enter goes out. The settle that follows the next prompt finds the cursor on the
  new prompt's row, so the old command row is no longer the cursor's and is published. No block
  is open after the command's `D`, so `unclaimed` opens one nobody submitted, and its first line
  (V2.4) starts it with no heading.
- bash's `^C` lands on the command row after the key has gone out, and the same settle publishes
  it the same way.
- A unit test typing `ech`, settling, then `o before` and Enter without settling, produced the
  headings `echo before` then none, and the outputs `before` then `o before`. A unit test pressing
  Ctrl+C at an idle marked prompt, with `^C` drawn on the command row, produced a `^C` block and
  then a block with no heading holding `^C`.

Measured on 2026-09-25 after the first implementation, which left only the row Enter or Ctrl+C
went out on:

- **Tab, in a session unit test.** Typing `ls`, settling, then ` /tmp/al` and Tab without
  settling, with the completions and the redrawn line drawn below, produced a block with no
  heading holding ` /tmp/al` beside the candidates. The key that moves the command line to another
  row does not have to be Enter or Ctrl+C.
- **Ctrl+L, at bash under WSL, keys 30 ms apart.** `echo x` typed and Ctrl+L pressed without
  settling produced a block with no heading holding the whole old row,
  `marlon@splyt:/mnt/c/Users/marlo$ echo x`. With the anchored row left too, nothing stray was
  printed, two runs out of two.
- **Tab Tab, then Ctrl+U, `echo x` and Ctrl+L, at the same bash.** After the listing, the field held
  the candidates rather than the line, and the anchor stayed on the row the line was first typed
  on. The row the line had moved to was then printed after Ctrl+L, with or without this change:
  the anchor had not followed the line, so no rule keyed on the anchor can leave the right row.

## Decisions

1. **Nothing set aside for the command line's row is published.** That is the row the command
   line is anchored on when the keystroke settles, or the row it was anchored on when Enter or
   Ctrl+C went out, even once the cursor has moved off it. The rule follows the anchor, not a key:
   Tab and Ctrl+L redraw the line on another row while the anchor is still on the old one. The
   command line reaches the buffer as the block's heading or in the field, and in local mode
   nothing from that row reaches the buffer either.
2. **Only an anchored row is left.** A far end that hid its cursor has no anchor, and nothing is
   remembered: `gh` parks a hidden cursor on a blank row and may print its answer there.
3. **The row is forgotten at the settle that takes the next anchor**, so a later row with the
   same id is never mistaken for it.

## What V2.5 does not do

- It does not change `far_end_settle` or the pacing of keys.
- It does not make the anchor follow a line that moved before the typing settled. After a Tab
  listing typed without a pause, the field holds the candidates and the anchor stays on the old
  row, so the row the line moved to can still be printed later.
- A command line wrapped onto a second row leaves only the anchored row.
- It does not touch 28.12: at bash, the `^C` block that fails with 130 is still there.
- It does not change what is spoken.

## Acceptance criteria

1. Session tests:
   - typing that never settles, then Enter, leaves one block, headed by the command and holding
     only its output;
   - Ctrl+C at an idle marked prompt, with `^C` drawn on the command row, leaves no block with
     no heading;
   - typing that never settles, then Tab, prints the candidates and none of the row the line was
     typed on;
   - with the cursor hidden, a row drawn at the prompt still reaches the buffer after Enter;
   - `what_the_far_end_printed_at_its_prompt_reaches_the_transcript` passes unchanged.
2. All existing tests pass, and the ignored real-shell tests for PowerShell and cmd pass.
3. Against a real `LocalPty` session with keys 30 ms apart, Windows PowerShell 5.1 (`echo
   before`, `echo after`, `2+2`) and bash under WSL (idle Ctrl+C) produce no
   `CommandStarted { command_line: None }` after the prompt.
4. NVDA through the bridge, `user` persona: after `echo before`, NVDA says "before" and the
   prompt, and never "o before".
