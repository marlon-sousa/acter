# B9.5 — The session is set up after it is established

Roadmap entries **23.11** and **27.1**, specified together because they are one mechanism
arriving from two sides. Agreed in conversation 2026-08-29.

Depends on **B5.3** for the bash program this rewrites, on **B5.5** for the login-shell probe
and its three states, on **B9** decisions 3 and 7 for the question seam and the SSH probe, on
**B6.1** for the echo that identifies a submission, on **B4.9** for what a submitted line does
to a buffer a screen reader reads, and on **A13** for the words a listener is entitled to.

It closes **13.8** as a consequence rather than as a favour: this entry rewrites the connection
sentence anyway, and leaving one clause in a user's words beside two in the project's would be
worse than either.

## What happens today

Acter arms the far end **at launch**, before the user's own startup files run.

Over WSL, `Wsl::launch` puts a `PROMPT_COMMAND` program and a `WSLENV` entry naming it into the
environment `wsl.exe` is started with. Bash inherits the environment before it sources
`.bashrc`, so the program is in place before the first prompt — and every startup file the user
owns gets the last word after it.

Over SSH there is no carrier at all. B9 measured it: `PROMPT_COMMAND` sent with `SendEnv`
arrives empty, because stock `AcceptEnv` takes `LANG` and `LC_*` and nothing else. So an SSH
session is unintegrated and says so.

## What is wrong with it

23.11 measured seven scenarios against real interactive bash on a pseudoconsole inside Ubuntu
24.04 under WSL 2.5.7.0, driven through `script -qec`, with the actual `PROMPT_COMMAND` string
read out of `injection.rs` rather than retyped, and a per-scenario rcfile that proves it was
sourced. Each run submitted one command that succeeds and one that exits 7, so a wrong exit
code is visible rather than inferred.

**One failure is documented and behaves as documented.** A `.bashrc` that assigns
`PROMPT_COMMAND` itself produces no markers at all. The grace period fires, the listener hears
the unintegrated sentence, and nothing false is claimed. That is B5.3 decision 3 working.

**Three more failures exist, none documented, and none detected**, because all three keep
markers flowing — so `IntegrationUnavailable` never fires and nothing tells the listener
anything is wrong:

- **A hook appended after ours steals the `C` marker.** `PROMPT_COMMAND="$PROMPT_COMMAND; mine"`
  moved the emitted order from `ABCD` to `CABD`. The `DEBUG` trap Acter arms as its last
  statement fires on *their* hook, which is the next thing to run, and the `__acter_seen` guard
  then suppresses the marker for the command the user actually typed. This is precisely the
  trap `injection.rs` documents for its own statements, inherited whole by anything appended
  after them.
- **A hook that rebuilds `PS1` kills `A` and `B` permanently.** Result `CDCDC`: the prompt
  boundaries are gone. `__acter_marked` is a one-shot boolean, so once anything rebuilds `PS1`
  after the first prompt, Acter never wraps it again. This is the most common prompt pattern
  there is — starship, conda, virtualenv and `__git_ps1` all rebuild `PS1` from a
  `PROMPT_COMMAND` hook.
- **A hook prepended before ours reports the wrong exit code.** `PROMPT_COMMAND="mine;
  $PROMPT_COMMAND"` announced `D;0` for a command that exited **7**. `__acter_status=$?` is the
  first statement of *our string* but not of the *variable* once somebody prepends, so it
  captures their hook's status. **Acter says out loud that a failed command succeeded.**

The third is a different kind of defect from the others. Losing integration is a degradation
this product already knows how to say out loud. Reporting a failure as a success is Acter
asserting something false about a command the user ran, with markers flowing so confidently
that nothing in the system doubts it.

(A `.bashrc` that installs its own `DEBUG` trap does not hurt Acter — ours replaces theirs,
since `PROMPT_COMMAND` runs after `.bashrc`. Their tooling breaks silently instead, which is
worth saying somewhere a user can find it.)

**Every one of these exists because Acter goes first and the startup files get the last word.**

## The premise, measured

**Bash re-reads `PROMPT_COMMAND` before every prompt.** It is not a startup-time-only variable.
Measured 2026-08-29: in a session with **nothing** injected at launch, two commands produced
zero markers; the session then assigned `PROMPT_COMMAND` itself, and every prompt after that
carried the full cycle — `ABCDABCDABC`, with a command that exited 7 correctly reported as
`D;7`. Zero markers before the assignment, eleven after. No `export` is needed: `PROMPT_COMMAND`
is read by bash in the current shell, and exporting matters only for child processes. Measured
without one.

**Going last, and wrapping the user's own hook in a sandwich, defeats all four failures.**
Against a hostile rcfile that assigns `PROMPT_COMMAND` for itself — where today's launch-time
injection produces **no markers** — the sandwich produced `ABCDABCDABC` with exit codes `0` and
`7`.

**The alternative was measured and rejected on reach rather than on merit.** `bash --rcfile
<ours>`, where our file sources the user's rc first and then applies the setup, produced the
full cycle against the same hostile rcfile, and it puts nothing in the terminal buffer at all.
But it is bash-specific (zsh needs `ZDOTDIR`, fish something else), it changes login-shell
startup semantics, and it does not exist over SSH, where Acter controls no launch arguments.
One mechanism that reaches everywhere beats a cleaner one that reaches half the product.

## Decisions

### 1. Nothing is armed at launch; the session is set up after it is established

The whole of the launch-time injection goes. What replaces it is a line sent into the session
once it is up, which is the only ordering in which Acter has the last word rather than the
first.

**It gives back the property B5.3 decision 2 fought for and the original shape of 27.1 had
traded away.** Nothing is written into the distribution or onto the host: no snippet, no
dotfile, nothing left behind on a machine the user has to live in after Acter closes. The
consent question shrinks correspondingly — "set this session up?" is a different and much
easier question from "may I edit a file in your account?", and it is a question about *this
session* rather than about the machine.

**The known limit, and it is acceptable rather than merely unavoidable.** Somebody who
re-sources `~/.bashrc` afterwards clobbers us, and nothing can foresee that. It degrades the
honest way: markers stop, the grace period expires, the listener is told. That is the failure
mode this product already handles well.

### 2. One mechanism for every shell and every transport

It needs no launch arguments, so it works over SSH exactly as it works over WSL — the first
time those two share a strategy rather than having one each. It extends to zsh and fish by
knowing hook names (`precmd`, `fish_prompt`) rather than startup-file conventions, which is
what B5.5 made urgent by establishing that the far end may not be bash.

Local cmd and PowerShell are **out of scope and unchanged**. cmd's markers ride in a `PROMPT`
environment variable that its own startup does not fight over, and PowerShell's ride in a
`-Command` argument. Neither has the ordering problem this entry is about, and moving them
would be a change with no defect behind it.

### 3. The setup line is an ordinary command, and it marks itself as one

**Decided by the user, 2026-08-29**: *"this is just another command. Nothing will be hidden."*

It is submitted through the same path a typed line takes. It gets a block, and the block's
heading is the command verbatim, so a listener arrowing the buffer or pressing F6 finds exactly
what ran. Nothing is suppressed: not the heading, not the buffer, not the shell's history.

**Traced through the code, that is silent.** Opening a block says nothing; a successful setup
prints nothing; and since A6 decision 2 a successful command's exit code is not on the wire at
all. So the listener hears the connection sentence and then the prompt, and the command is
sitting in the buffer for anyone who goes looking. This replaces "suppress the heading and the
block", which was the shape 27.1 expected and which was rejected once the ruling above made
disclosure the principle: the dialog in decision 9 is the disclosure surface, and hiding the
command from the buffer after showing it in a dialog would be disclosure with the evidence
removed.

**But a command has to end, and this one would not.** The setup runs before the `DEBUG` trap
exists, so no `C` arrives; the pump opens the block from the echo instead (B4.9's path), and the
tracker's own `block_open` stays false — which means it ignores the `D` that follows, and `A`
closes nothing. The block would stay open until the user's first real command. Two consequences:
`running` stays true from the moment of connecting, and a Ctrl+C pressed before the first
command would be reported as `Applied` and then close the setup as `CommandInterrupted` — a
listener told they stopped a command they never ran.

**So the setup line emits its own `C` as its first statement, and pre-arms the `started` guard
so the very next prompt emits its `D`.** Then it is a command with the full marker cycle, it
closes with a real exit code like any other, and neither the pump nor the tracker needs
changing. The session also becomes integrated at that `C`, which is the earliest honest moment.

**Its exit code is `0` and that is honest.** What the line does is an assignment, and an
assignment succeeds. Whether the setup *worked* is a different question and decision 12 answers
it.

**One thing in the pump does have to change, and it is small.** `Pump::claim` returns an id and
drops the line it came from, so a block opened by `block_started` rather than by `boundary`
would carry `command_line: None` and reach the frontend as an empty heading — the defect B4.4's
NVDA pass found. `claim` returns the whole `Submitted`, so either path names the block.

### 4. It is sent the first time the far end speaks

Not at session start. Bytes written before the shell reads them are an unmeasured race, and
they are the launch-time injection wearing a different hat. The pump already tracks `spoken`,
which is what makes a session "connected" at all (A9 decision 3), so the trigger exists.

A banner arriving before the prompt is a fine trigger too: the line lands in bash's input
buffer and readline reads it when it starts, which is what a fast typist already does and what
B6.1's echo matching already copes with.

### 5. The grace period is armed when the far end first speaks, not at session start

Forced by decision 4, and correct on its own terms. Today's five seconds run from
`SessionService::start`, and a cold WSL distribution takes five to six seconds to say anything
at all — so a session that is going to be set up perfectly well would hear the unintegrated
sentence first and recover from it silently, which is 23.10's defect made systematic rather
than incidental.

`integration_grace` asks how long the far end has been talking without marking anything. A far
end that has not spoken has not had its chance, and the clock should not be running.

**This narrows 23.10 and does not close it.** A cold start still takes five to six seconds
before there is a prompt, and a listener still has to be told that waiting is correct.

### 6. Per-shell setup knowledge is a policy keyed by the shell's name

`ShellAdapter` answers "what environment do I launch this with". What this needs is "what do I
run inside it once it is up" — the same knowledge asked a different question, per shell rather
than per transport, and it is what lets one WSL bash and one SSH bash share a setup for the
first time.

A new policy module, `crates/acter-shells/src/setup.rs`, the shape `far_end.rs` already has:
a name in, what it licenses out. The bash program moves out of `wsl/injection.rs` into it and
stops being WSL's.

Three states, and they are B5.5's three:

- **Measured** — a line, and the `ShellMarkers` that line earns.
- **Nothing written for it** — the shell is named and no setup has been measured for it.
- **Nothing answered** — no name, and nothing is invented.

**B5.5's rule survives intact and is what keeps this honest: the identity may be guessed from
the name; the setup may never be.** Each shell's setup is measured the way B5.3 measured bash's,
one small additive entry per shell, and a shell nobody has done that for is named rather than
experimented on.

### 7. The bash program: last word, sandwich, and a `PS1` guard that tests `PS1`

Four properties, each with one of 23.11's failures behind it:

- **`__acter_status=$?` inside our own leading segment**, so a hook prepended to the variable
  cannot make us read its status instead of the user's command's.
- **The user's own `PROMPT_COMMAND` in the middle.** Before their hooks is where `$?` is still
  the user's command's status.
- **The re-wrap and the `DEBUG` trap arming last.** After their hooks is where a rebuilt `PS1`
  can be re-wrapped, and where the trap can be armed with nothing left to steal its first
  firing. Going first or last alone cannot do both.
- **The `PS1` guard becomes a test of `PS1`'s own contents rather than a one-shot boolean**, so
  a prompt rebuilt at any later moment is wrapped again on the next cycle.

Plus decision 3's two additions: the `C` printed as the line's first statement, and the
`started` guard pre-armed so the next prompt closes the block with a real `D`.

The two bash facts `injection.rs` measured survive unchanged and travel with the program: a
`trap - DEBUG` executed inside a shell function is discarded when the function returns, so the
guard is a variable rather than self-removal; and a trap armed inside a function fires for the
rest of that function, so the guard is cleared before the trap is armed and never after.

### 8. `sh` reaches `A` and `B`, and the sentence has to be able to say "partly"

> **Superseded in part by B9.6, 2026-08-29.** The verdict half of this decision is wrong: `PS1`
> is expanded every time the prompt is drawn, and `$?` at that moment is the status of the
> command that just finished, so POSIX `sh` can report exit codes with no hook at all. It now
> answers `PromptCommandLineAndExitCode`, and the offer sentence it gets is bash's. Everything
> else below stands — the program is still its own and not bash's with a substitution, and the
> tracker still synthesises `C`. See
> [b9.6-verdicts-in-sh-and-nothing-read-aloud-at-connect.md](b9.6-verdicts-in-sh-and-nothing-read-aloud-at-connect.md),
> decision 1, and roadmap 23.15.

POSIX `sh` has `PS1` but no prompt hook and no `DEBUG` trap, so the prompt boundaries are
reachable and the output boundary and the verdict very likely are not. That is not a reason to
refuse it — cmd already ships `PromptAndCommandLine` and a listener gets real value from prompt
boundaries alone.

So the per-shell answer is a `ShellMarkers` rather than a yes, and `sh` answers
`PromptAndCommandLine`, with the tracker synthesising `C` at the end of the echo as it already
does for cmd.

**It is its own measured program and not bash's with a substitution.** `\[` and `\]` are
readline's, and dash has no readline: it would print them literally into the prompt. Every line
of a setup costs its own measurement, which is the rule that produced this decision rather than
an exception to it.

`docker-desktop`, measured in B5.5's pass on 2026-08-29, runs `/bin/sh` and is the case sitting
on this machine to test it against.

### 9. The checkbox authorises; the dialog discloses

**Both, and neither is optional** (the user, 2026-08-29). True by default is what makes an
ordinary user hear headings and failures without knowing the words this project uses — A13's
whole subject — and it keeps the rule that nothing in this product is a gate. What stops "on by
default" from being a surprise is the dialog.

**The checkbox** is on the Connect dialog, checked by default, and it is the durable
authorisation: unchecking it has to be reachable without the dialog ever appearing.

**The dialog** is asked after the connection succeeds and before the setup line is sent, which
is exactly the window `ConnectQuestions` exists for. It is a third question on that seam, beside
B9's host key and B5.7's unverified file, and both of those established the two properties this
one inherits: the safe answer is the default, and refusing is a decision rather than a failure.

What it says, in the user's words rather than this project's — A13 removed "shell integration"
from what a listener hears because it is vocabulary a user does not have:

- "Acter has detected that this session runs bash."
- "Acter can set it up so it tells you more about what you run. You get a heading for each
  command, and you are told when a command fails."
  (For a shell that reaches only the prompt boundaries: "You get a heading for each command.
  Acter cannot yet tell you when a command fails in this shell.")
- "This is the command Acter will run for you:" — followed by the command **verbatim, in a
  read-only field**, the way B9 presents a host-key fingerprint and B5.7 presents a program
  path: somewhere it can be read character by character rather than only heard.
- "If you cancel, the session still works. You will hear what commands print here, but not
  whether they worked."

Controls: **Continue** (the default), **Cancel**, and a **"Do not show this dialog again"**
checkbox. Cancel refuses this session only and says so; the Connect dialog's checkbox is what
refuses durably.

The closing line is A13's shipped sentence verbatim. That is deliberate and it is the register
test: if the refusal reads in the same voice as the help topic F1 opens, the dialog is in the
user's words.

**A shell with nothing written for it produces no dialog**, because there is no command to show.
The connection sentence says so instead (decision 13) and the session goes on without a setup.

### 10. Two stored things, and the dialog preference is per shell

**They are not the same thing and storing them together is the mistake to avoid.**

**The checkbox is a property of a connection** and belongs to the saved profile, which is B8's.
B8 is not built: there is no profile store. So until it is, the checkbox lives on the Connect
dialog and travels with the attempt, and B8 adds the field rather than re-deciding it. This
spec says so in order to spare B8 the decision.

**The dialog preference is a property of the person, and it is kept per shell** (the user,
2026-08-29): *"we would want to be sure the user has a chance to review commands for all the
shells they use."* Somebody who has read and accepted what Acter runs in bash has not thereby
accepted what it runs in zsh, and a shell whose setup is added by a later entry asks again — as
it should, because it is a different command.

So what is stored is the set of shell names this person has said not to ask about again, behind
a driven port of its own. It is **not** keyed by host or by profile: tying it to a connection
would re-explain the same command for every new host, which is the thing that teaches people to
dismiss dialogs.

**Where it lives before B8 exists**: a file in the directory `acter_known_hosts` already
resolves — `%APPDATA%\acter`, with `ACTER_PROFILES_DIR` pointing elsewhere for development,
tests and the NVDA fixture. That is the precedent B9 set for Acter's own `known_hosts` before
B8 existed, and the environment is read in the composition root, which is the one place allowed
to (B8 decision 2).

### 11. The shell's own history is left alone

**Decided by the user, 2026-08-29**: *"we have nothing to hide. We execute the command, we let
this in history."* The command was disclosed verbatim and authorised before it ran, so removing
it from the user's own history would be hiding it after showing it.

**Recorded because the alternative was measured and rejected rather than overlooked**, so a
later reader does not re-derive it. Measured 2026-08-29, Ubuntu 24.04 under WSL 2.5.7.0, real
interactive bash on a pty through `script -qec`, isolated `HISTFILE`:

- With `HISTCONTROL=ignoreboth` — Ubuntu's and Debian's own `.bashrc` default — a line submitted
  with a **leading space** never reaches the history file. Three ordinary lines were written;
  the spaced one was not.
- With `HISTCONTROL` empty, the same line **is** written at exit.
- `history -d $((HISTCMD-1))` is the obvious self-removal and it is **wrong**: it deleted the
  preceding command and left ours. `HISTCMD` is already the current command's number during
  execution.
- `history -d $HISTCMD` removed exactly our line and nothing else, with `HISTCONTROL` empty.

So a leading space plus `history -d $HISTCMD` would have left nothing behind on any bash. The
setup line uses neither.

### 12. Verification is the grace period, and nothing else claims success

**A setup that claims to have worked is not one that has.** Acter does not say the session is
set up until a marker has actually arrived — which the grace period already does for free, and
which is why this entry can be small without being optimistic.

Nothing extra is announced when it works: the connection sentence already names the far end,
and a second utterance saying it went fine is noise on every connection for the sake of the rare
one. Failure is the existing sentence at the existing moment, and if the shell complains, its
complaint is in the buffer under the heading of the command that caused it — which decision 3 is
what makes possible.

### 13. The connection sentence is rewritten into A13's register, closing 13.8

Today a connection announces *"connected to SSH: acter at 127.0.0.1, port 2222, bash, with no
shell integration set up on this host"*, and "shell integration" is exactly the phrase A13
concluded a user does not have. This entry writes new clauses for two new states, so it rewrites
all of them rather than leaving the product speaking in two registers.

Four cases, and each says what it knows:

- **Set up, fully** — the shell's name and nothing more. Nothing is missing, so nothing is said
  about it. Unchanged.
- **Set up, partly** — the name, and what a listener will and will not get: *"sh. You will hear
  a heading for each command here, but not whether it worked."* This is the only case where the
  grace period will never speak, because markers do arrive, so the clause is the only chance to
  say it.
- **Named, nothing written for it** — *"zsh, which Acter cannot set up yet."* The reason B5.5
  currently only implies.
- **Nothing answered** — no clause at all. The name is not invented, and the sentence that
  covers this case is A13's, said when the grace period expires. Saying it twice in two registers
  is what 13.8 objected to.

**The status region says the same string**, which is 27.5's decision and is unaffected: there is
one function composing this sentence, so the region and the announcement cannot drift. What
27.5 asked to have re-decided if the wording changed is decided here: the region keeps reading
back exactly what was announced.

### 14. The probe stays ahead of the dialog, and twelve seconds is narrowed rather than retired

27.1 expected the probe to leave the critical path entirely and B5.5's twelve-second deadline to
be retired rather than tuned. Decision 9 settles the placement differently, for a reason that is
the user's rather than the implementation's: **the dialog names the shell it detected**, so the
shell has to be known before the dialog is asked.

That is the better trade anyway. It keeps `ShellFacts` a construction argument, so a narrower
marker claim for `sh` is known before the first byte is tracked and nothing has to mutate the
tracker mid-session; and it keeps the connection sentence one utterance with a subject, which is
what B5.5 decision 5 and 27.5 paid for.

**What does change is why the number exists.** B5.5's amendment 1 chose twelve seconds as
roughly twice the slowest cold start seen, because the probe had to clear a cold boot *before*
the client could be launched at all. The launch no longer depends on the answer, so the probe
can run beside it rather than in front of it, and the deadline stops being "long enough that a
cold boot is not a coin toss" and becomes "long enough that a distribution which is coming up is
not given up on". The implementing PR measures it and picks the number; 27.1's paragraph is
amended to say narrowed rather than retired, with this reason.

## Definition of done

- [ ] Nothing is injected at launch. `Wsl::launch` produces the client and `-d` and an empty
      environment, asserted; `WSLENV` and the `PROMPT_COMMAND` crossing no longer exist in the
      crate.
- [ ] A real bash distribution reaches the full cycle with correct exit codes through the
      runtime setup, from a cold `wsl --shutdown`, and the existing `#[ignore]`d WSL cases pass
      unchanged.
- [ ] The three silent failures of 23.11 are each a test against a real distribution with the
      hostile rcfile that produced them, and each now reports the correct exit code and the
      correct marker order. The prepend case is the one that must not regress: it is the one
      where Acter said a failed command succeeded.
- [ ] A `.bashrc` that assigns `PROMPT_COMMAND` for itself is set up successfully, which is the
      case today's strategy cannot do at all.
- [ ] The setup command opens exactly one block, headed by the command verbatim, and **closes**
      with an exit code before the user's first command — asserted, because the failure it
      guards is a session that reports "running" from the moment it connects and reports a
      command the user never ran as stopped.
- [ ] Ctrl+D and Ctrl+C immediately after connecting behave as they do in a session with nothing
      running.
- [ ] `sh` reaches the prompt boundaries and declares `PromptAndCommandLine`, measured against
      `docker-desktop` rather than asserted from documentation.
- [ ] A shell with no setup written for it starts, is named, and says so in one sentence with no
      dialog and no wait.
- [ ] The dialog is asked once per shell per person: accepting with "do not show this again"
      ticked suppresses it for that shell and for no other, across hosts and across profiles.
- [ ] Cancelling leaves the session running and unmodified, and says so.
- [ ] Unchecking the Connect dialog's checkbox skips both the dialog and the setup.
- [ ] The four connection sentences are asserted as whole clauses, because that is what a
      listener hears, and none of them contains the phrase A13 removed.
- [ ] The grace period is armed on the far end's first byte, asserted with a fake clock.
- [ ] `cargo fmt`, `cargo clippy --workspace --all-targets`, workspace tests, the `#[ignore]`d
      real-shell suite, and `npm test` in `ui/` all clean.

## Accessibility checklist for the PR body

Driven with NVDA through the screen-readers bridge as the `user` persona, silent capture,
against the real application. Items an agent can observe are checked by the agent with the
reader version and the capture mode written inline; anything turning on a beep or on subjective
comfort stays human-only and is labelled.

- [ ] Connecting to a bash distribution with the checkbox ticked: the dialog is reachable, its
      four paragraphs can be arrowed, and the command can be read character by character in the
      read-only field.
- [ ] Continue: the session comes up, the prompt is spoken, and **nothing is spoken between the
      connection sentence and the prompt**. The setup command's heading is in the buffer and F6
      reaches it.
- [ ] Cancel: the session comes up and says what it will and will not do, in one sentence.
- [ ] "Do not show this dialog again", then reconnecting to the same distribution: no dialog, and
      the session is set up.
- [ ] Then connecting to a distribution running a different shell that has a setup: the dialog
      appears again, for that shell.
- [ ] A distribution running a shell with nothing written for it: one sentence naming the shell,
      no dialog, and no five-second wait before anything is said.
- [ ] `docker-desktop`: the connection sentence says what a listener will and will not get, and
      the grace period never contradicts it.
- [ ] The Connect dialog's checkbox is reachable, labelled, and its state is spoken.
- [ ] A cold distribution: the starting sentence, then the connection, with no unintegrated
      sentence in between and none afterwards.

## What is measured today, and what the PR must measure

**Measured before this spec was written** (2026-08-29, and recorded above rather than repeated
here): that bash re-reads `PROMPT_COMMAND` before every prompt; that the sandwich defeats a
hostile rcfile that today's injection cannot survive; the three silent failures and their exact
marker orders; the `--rcfile` alternative and why it is not enough; and the four history facts
behind decision 11.

**Left to the PR, and none of it may be assumed:**

- The `sh` program, against `docker-desktop`. Every claim about what `sh` can and cannot mark is
  a measurement, including the negative ones.
- Whether OSC 133 markers cross an SSH connection at all. Expected, and unmeasured when this was
  written — B9 never had a marker to send. This is the first entry that produces one, and if they
  do not cross, an SSH session stays unintegrated and says so, which is what it does today.
  **Measured, and they cross**; see "What the PR measured" below.
- The block the setup command opens and closes, against a real distribution rather than against
  a fake.
- The probe deadline (decision 14).

### What the PR measured

All of it on 2026-08-29, on the machine B5.5 and 23.11 were measured on: Ubuntu 24.04.2 LTS with
bash 5.2.21, and `docker-desktop` running busybox 1.37.0 as `/bin/sh`, both under WSL 2.5.7.0.

**The bash program, against six dotfile shapes.** Real interactive bash on a pseudoconsole
through `script -qec`, the setup line read out of the crate rather than retyped, each run
submitting one command that succeeds and one that exits 7, and every rcfile printing a mark so a
scenario that silently did not run is visible. Plain, a hook that assigns `PROMPT_COMMAND` for
itself, one appended after ours, one prepended before ours, one that rebuilds `PS1` every
prompt, and one that installs its own `DEBUG` trap — **all six produced the identical stream**:

```
C D;0   A B C D;0   A B C D;7   A B C
```

Read as decision 3 working: the setup marks its own output, the next prompt closes it with a
real code, and every command after it gets the full cycle. The prepend case reports `D;7`, which
is 23.11's serious defect gone. The rebuild case draws its own `rebuilt$` at every prompt and is
re-wrapped at every prompt, which is `CDCDC` gone.

**The same four dotfile shapes through the whole stack**, in
`crates/acter-transports/tests/real_session.rs`, where what is asserted is what a *listener*
gets: the exit code announced, the heading the block opened with, and that a command which
worked is not announced as having failed.

**The setup command's block, against a real distribution.** It opens exactly one block, headed
by the command verbatim, closes with an exit code before the user's first command, prints
nothing, and announces nothing — and a Ctrl+C pressed straight after connecting answers that
there is nothing to stop.

**Nothing of the setup reaches the listener.** Asserted over the real stack against both the
speech path and the buffer. This is the assertion that found amendment 3.

**`sh`, against `docker-desktop`.** The probe answers `sh` for itself; the adapter claims
`PromptAndCommandLine`; a command gets a heading; and **no verdict is forged** for a command
that genuinely failed — the negative half, measured rather than inferred. Driven both through
`script` and through the whole stack. This is what found amendments 4 and 5.

**What the markers cost the shell's own line editor**, asked because "does this mangle the
prompt the user sees" is a fair question and the drawn prompt being right does not answer it.
A pseudoconsole fixed at 80 columns by `stty`, a prompt four visible columns wide, characters
typed in with no Enter so the only thing writing to the terminal is the line editor, and the
redraw watched for the moment it starts believing the line takes two rows.

**bash costs nothing.** With the markers wrapped in `\[` and `\]` exactly as `BASH` wraps
them, readline moves the cursor right by four columns on redraw — the four the prompt occupies
— and the marked and unmarked runs are byte-identical in that respect. The non-printing
brackets do their job.

**busybox `sh` costs sixteen columns.** Unmarked, it begins a second row at 76 characters
(4 + 76 = 80). Wrapped in `SH`'s two markers, at 60 (4 + 16 + 60). Each marker is
`ESC ] 1 3 3 ; A BEL` — eight bytes — and busybox counts every one of the sixteen as a
printable column, because `\[` and `\]` are readline's and it has no equivalent. The drawn
prompt is still correct, which amendment 4 fixed; what is wrong is arithmetic, and a user meets
it when a line gets long.

Filed as **roadmap 23.14**, which also has to decide what `sh` should ship, because that is a
trade a user makes rather than one an implementer may make for them. It is very probably the
cause of 23.12's busybox half.

**The distribution's own files are untouched**, compared against the same question put to a
`wsl.exe` Acter never drove.

**The probe deadline**, in amendment 6.

**OSC 133 markers cross an SSH connection.** Measured 2026-08-29 against the rig in
`docker/ssh` — Debian bookworm, bash 5.2.15, OpenSSH 9.2 — from Windows 11, over a real `sshd`
on a real channel, driving the whole pipeline the window has rather than watching bytes
(`ssh_rig.rs`, `the_markers_a_session_sets_itself_up_with_cross_an_ssh_connection`).

The remote bash accepted the same line a distribution's bash accepts, and the whole cycle came
back: the far end's prompt arrives as a `PromptDrawn`, which is an `A`..`B` pair and which
nothing else in this product produces, and `(exit 7)` is announced as **`Failed { exit_code: 7 }`**,
which needs the `D;7` the far end wrote to have survived the trip. `IntegrationUnavailable` is
gone from an SSH session for the first time.

**That is decision 2 measured rather than reasoned.** One mechanism for every transport was
argued from markers being ordinary bytes and an SSH channel being a byte pipe, which is a good
argument and was not a measurement. It is one now, and it took the same line, unchanged, from a
distribution on this machine to a container reached over a network socket.

**What it also found: over SSH, Acter's own setup command is read aloud.** Twice, at about five
hundred characters each, between the connection sentence and the prompt. The cause is the login
banner: `sshd` draws `Last login: ...` before bash draws its prompt, so the first drawn line the
setup waits for (amendment 3) is the banner rather than the prompt, and the echo is therefore
written to a row that is not the pending one. B4.9's suppression never fires. **This is the same
symptom roadmap 23.12 records for busybox `sh` and a different cause**, so that entry is widened
to cover both rather than a second one being opened; the user's own commands after the setup are
clean in the same run, which is what says the defect is the setup's window and not the echo
matcher generally.

## Amendments riding in this PR

The six below were written **while implementing**, and each is here because the code forced it
rather than because the design changed its mind. Four of them are defects a real distribution
found and a fake could not. They are recorded in the order they were met.

### 1. A fifth connection sentence, for a setup that was refused

Decision 13 enumerates four cases. Decision 9 creates a fifth and the accessibility checklist
asks for it out loud — *"Cancel: the session comes up and says what it will and will not do, in
one sentence"* — so a shell that has a measured setup which was **not run**, because the Connect
dialog's checkbox was unticked or its dialog was cancelled, needs a clause of its own. It says:

> `bash. You will hear what commands print here, but not whether they worked.`

The name, and then A13's shipped sentence. Both refusals produce the same clause on purpose: a
listener is owed the same words whether they unticked a box a minute ago or cancelled a dialog a
second ago, because what it says is what this session will and will not be able to tell them,
not which control they used to say no.

**The place is gone from all five**, which decision 13 implied and this states. "on this host"
and "in this distribution" existed to point at the dotfile a user would have to edit; there is
no dotfile to edit any more, and every one of these sentences is about *this session*. B5.5's
decision 5 is superseded rather than contradicted.

### 2. `claim` names a block only for Acter's own line

Decision 3 says `Pump::claim` should return the whole `Submitted` "so either path names the
block". Implemented literally, that overwrites the heading the frontend already gave a line the
**user** typed — which is B6.1's decision 1, and Decided: the frontend puts the typed text on
the block when the submit ack answers, and `command_line: None` means "the shell did not say
what it is running", so that heading stands. Naming it from the pump with anything but the
shell's own echo is the guess a drifted id can attach to the wrong block.

So the fallback is narrowed to the case decision 3 was actually about: **Acter's own setup
line**, which no frontend submitted, has no ack, and would otherwise reach the buffer as the
empty level 2 heading B4.4's NVDA pass found. `Submitted` carries whether the line is ours;
`claim` returns it whole either way.

### 3. The setup is sent on the far end's first *drawn line*, not its first byte

Decision 4 says the line is sent "the first time the far end speaks". Measured 2026-08-29
against Ubuntu 24.04 under WSL, that is one read too early: bash's first read carries bytes that
draw no line at all, so the submission was pending before the pump knew which row the echo would
be written onto — B4.9 decision 1's precondition. The prompt that arrived next was held together
with the echo and published with it, and **five hundred characters of Acter's own command were
read aloud between the connection sentence and the prompt**.

The trigger is now the far end having drawn something, which is the same moment in every
ordinary session and one read later in this one. A far end that draws nothing has no prompt to
mark, and the grace period — which is still armed on the first byte, as decision 5 says — is
already running.

### 4. `sh`'s markers end with a bell, not with a string terminator

Decision 8 says `sh` gets its own measured program because `\[` and `\]` are readline's. The
same rule bit twice. Measured 2026-08-29 against `docker-desktop` (busybox 1.37.0 ash): with
`ESC \` as the OSC terminator, `A` arrived as `ESC ] 133 ; A` followed by a **carriage
return**, and the prompt `rc$ ` was drawn as `c$ `. busybox expands backslash escapes in `PS1`,
so the terminator's trailing backslash glued itself to the prompt's first character. **The first
character of the user's own prompt disappeared**, in front of somebody who cannot see that it is
missing.

A bell is the other terminator OSC allows, it is what this project's own sniffer already reads,
and it puts no backslash in `PS1` at all. bash keeps `ESC \`, where its own expansion produces
the backslash correctly — measured, prompt intact.

**A bell that ends a marker is not a bell**, and that is asserted rather than assumed, because
beeping on one is a feature this product may well want: the parser consumes it inside the
sequence, so nothing rings, while a bell in the ordinary stream still arrives.

### 5. Which byte discards a pending line is the shell's answer, not the marker claim's

`SessionService` wrote `cmd.exe`'s escape ahead of a submitted line whenever the far end claimed
`PromptAndCommandLine`, on the stated reasoning that the marker declaration "is the only thing
that says which shell this is, and it says it exactly". Decision 8 ends that by making POSIX
`sh` the second shell to claim it — and an escape reaching a POSIX reader is a **keypress**.
Measured 2026-08-29 against `docker-desktop`: the escape left busybox running a fragment of the
line behind it and answering `-sh: r-sh: not found`.

So `ShellAdapter` gains `discards_line`, which is the move `SessionService`'s own comment
predicted — *"which byte discards a pending line is a fact about a shell's line editor, the same
category as its prompt injection"*. `Cmd` answers escape; everything else answers nothing.

### 6. The probe deadline is re-measured and does not move

Decision 14 asks the implementing PR to measure the deadline and pick the number. Measured
2026-08-29, same machine, Ubuntu 24.04 under WSL 2.5.7.0: warm 141, 151, 161, 161 and 170
milliseconds; cold 5.22, 5.29, 5.35 and 5.35 **seconds** with `wsl --shutdown` before each;
`wsl.exe -l -q` 50 to 91 milliseconds cold or warm.

**Twelve seconds stays.** Halving it to six would land the deadline in the middle of the
observed cold spread, which is the worst place for one to be and is exactly what B5.5's
amendment 1 recorded. What B9.5 removed is not the wait but the ordering: the client is started
while the probe is outstanding, so a healthy cold start no longer pays this deadline in front of
its own boot. The number is the same and the reason is the one decision 14 wrote.

## Open, and not closed by this entry

**23.10 is narrowed, not closed.** A cold WSL start still takes five to six seconds before there
is a prompt, and a listener still has to be told that waiting is correct. What changes is that
Acter is no longer adding to that wait to decide something it could decide later, and no longer
tells the listener the opposite of the truth while it waits.

**Somebody who re-sources their `.bashrc` afterwards clobbers the setup**, and nothing can
foresee that. It degrades honestly and that is the whole answer.

**zsh and fish are named and not set up.** Each becomes one small additive entry, measured the
way bash's was, and each will ask its own dialog the first time — which decision 10 is for.
