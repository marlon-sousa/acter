# Spec: PR B4.1 — an interrupt that interrupts

Agreed in conversation 2026-08-21. Lane 2, entry 22.1. Makes a Ctrl+C stop a program that
is genuinely running, and stops Acter claiming anything about it: the shell's own prompt
coming back is what the user hears.

## Why now / relation to the roadmap

An iteration entry from B4's manual NVDA pass, and the most serious thing that pass found:
`0x03` reaches the pseudoconsole, the program keeps producing output, and Acter announces
`command stopped` over the top of it — a claim a user cannot see to be false. Both halves
are wrong and both are fixed here: the interrupt now works, and the announcement goes.

The roadmap named two candidate mechanisms. Neither is needed. The byte was never wrong;
the shell was spawned in a state that made it refuse the signal.

## What was measured

Against a real `cmd.exe` on a real ConPTY running `ping -n 20 127.0.0.1`, counting replies
over the five seconds after the interrupt, where zero means it took effect:

- Bare `0x03` with the ignore-Ctrl+C attribute inherited: **four replies**, and the same for
  a win32-input-mode key record and for `GenerateConsoleCtrlEvent` after `AttachConsole`.
- Bare `0x03` after one call to `SetConsoleCtrlHandler(NULL, FALSE)` before the spawn:
  **zero replies**, session survives, `echo` round-trips afterwards.

The first four results were measured against a rigged baseline and are recorded in the
roadmap as a trap rather than as findings about ConPTY.

## Design decisions this spec makes

1. **The fix is to stop handing the shell a broken inherited state.**

   `SetConsoleCtrlHandler(NULL, TRUE)` sets a process attribute that children inherit, and
   `CREATE_NEW_PROCESS_GROUP` sets it implicitly for a whole group — which is how launchers
   routinely spawn children so they can kill trees. A shell spawned under it ignores Ctrl+C
   however correctly the interrupt is encoded. `LocalPty::spawn` calls
   `SetConsoleCtrlHandler(NULL, FALSE)` before spawning, so the shell inherits normal
   processing regardless of how Acter itself was launched.

   **The inheritance is transitive, and that is the whole mechanism.** Acter spawns
   exactly one process and holds one `Child`: everything the shell launches is on the far
   side of the pseudoconsole, with no pid and no handle on this side. The program that
   actually has to receive the interrupt is not the shell — it is whatever the shell ran —
   and Acter can never touch it directly. It does not need to: the attribute passes Acter
   to shell to program on its own. So the fix is not "make the shell accept Ctrl+C", it is
   "do not poison the state that everything below us inherits", and the only place to do
   that is in our own process before the spawn. Measured end to end: what stopped was
   `ping`, two links down.

2. **`INTERRUPT: u8 = 0x03` stays, and so does its unit test.**

   `an_interrupt_is_the_single_byte_0x03` pins correct behavior. Nothing about what
   `interrupt` writes changes, which is the point: this entry turned out to be about spawn
   state, not about the wire.

3. **`Transport::interrupt` is untouched, and Acter never stops a process itself.**

   A terminal client writes bytes; the pty and the OS turn them into a signal. Reaching
   into the process table to terminate anything would be doing the kernel's job from the
   wrong layer, and would cost what a real Ctrl+C preserves — handlers running, cleanup
   happening, the program choosing its own exit code. An earlier draft of this spec
   proposed exactly that on the strength of the rigged measurement; it is recorded here as
   rejected so the reasoning is not repeated.

4. **Nothing is announced, and the interrupt no longer closes the command.**

   Acter says nothing about the interrupt at all. The user hears what the *shell* says —
   the prompt coming back, read by autoread like any other output. That is evidence from
   the far end rather than a claim Acter makes, which is the whole problem this entry
   opened with. It is also the correction A6 already made for `CommandFinished`, which
   since then "carries no verdict" and speaks only through a separate `Announce`.
   `CommandInterrupted` is the one terminal event still announcing directly — an A3.1-era
   leftover exactly like the `CommandFinished` one B6's manual pass removed for saying it
   twice and saying it first.

   **This requires reverting B6 decision 10's amendment**, and the measurement says why.
   `SessionActor::output` returns early when no command is active, so output arriving after
   a close is discarded: not rendered, not spoken. If the interrupt keeps closing the
   command in an unintegrated session, the returning prompt is dropped and the user hears
   *nothing at all* — worse than the wrong announcement, because silence is
   indistinguishable from a hung session. So the interrupt stops forcing a boundary: the
   block stays open, the prompt flows into it as ordinary output, and the existing
   unintegrated rule closes it at the next submission. The amendment existed only to make
   the announcement timely; with no announcement its reason is gone.

   `SessionEvent::CommandInterrupted` stays. It still does the block bookkeeping the
   frontend needs, and `interrupted` remaining set means the eventual close reports a
   stopped command rather than inventing exit code 0 — the mis-announcement
   `protocol_events.rs` says the variant exists to prevent. Only the `announce` call goes.

   Measured, and it is what makes this work: after a real interrupt `cmd.exe` echoes no
   `^C`; what comes back is the prompt. So the thing autoread reads is exactly what the
   user described, and there is no control-character noise to filter.

5. **`windows-sys` joins `acter-transports`, for one call.**

   `Win32_System_Console` only, `#[cfg(windows)]`. The Unix arm needs nothing: a bare
   `0x03` on a Unix pty is turned into `SIGINT` by the line discipline, so `local.rs` stays
   platform-neutral apart from this one guarded call. `acter-core` gains nothing.

6. **The fix is verified in the real app, not only in tests.**

   The confound that produced the wrong diagnosis was a *launch context*, and Acter's own
   launch context differs from both the spike's and the test suite's — a Tauri GUI process
   may carry different inherited state than a `cargo test` child. The behavior was
   originally heard through NVDA, so that is where it is confirmed fixed. This is an
   acceptance criterion, not a nicety.

## Files touched

- `crates/acter-transports/Cargo.toml` — `windows-sys`, Windows-only.
- `crates/acter-transports/src/local.rs` — the `SetConsoleCtrlHandler` call in `spawn`,
  behind `#[cfg(windows)]`, with the reasoning in its doc comment.
- `crates/acter-core/src/services/session.rs` — `Pump::interrupt` stops closing the
  command at all; B6 decision 10's amendment reverted, with its reasoning updated.
- `ui/src/controllers/app.ts` — the `announce` call on `CommandInterrupted` and the
  `commandStoppedMessage` export go; the cleanup stays.
- `e2e/test/specs/stop.spec.ts` — **added during implementation.** Two of its cases waited
  on `command stopped` as their synchronisation point, so removing the announcement made
  them fail. They now wait on the output settling instead, which is the thing that was
  always being asserted, and one of them asserts the silence positively.
- `crates/acter-transports/tests/local_pty.rs` — the `#[ignore]` reason on
  `an_interrupt_stops_a_running_program` loses its "known gap" wording.
- `.github/workflows/ci.yml` — the `--skip` comes out, with its explanatory comment.
- `docs/ROADMAP.md` — entry 22.1 flipped to Done.
- `docs/specs/b4.1-interrupt-that-interrupts.md` — this file.

## Tests

Service, in `session.rs`, against the fake far end:

- An interrupt does not close the command, in an unintegrated session or an integrated
  one.
- Output arriving after an interrupt still reaches the frontend — the regression that
  closing would have caused, pinned so it cannot come back.
- The next submission closes the interrupted command as stopped rather than as finished
  with exit code 0.

Frontend, in the app controller tests:

- `CommandInterrupted` announces nothing, and still performs its block cleanup.

End-to-end, in `stop.spec.ts`:

- A stopped command's output genuinely stops, and nothing is announced over it. The
  scripted far end sends no prompt back, so the silence is the half this level can see.

Real-shell, in `tests/local_pty.rs`, `#[ignore]`d:

- **`an_interrupt_stops_a_running_program` turns green.** It already exists and already
  states the requirement; its skip comes out of CI in the same commit.
- `an_interrupt_reaches_the_shell_and_the_session_survives_it` keeps passing, and gains a
  sibling that stops a *real* program and then submits another command — so "survives" is
  proven against a program that had to be signalled rather than against `pause`.

## Acceptance criteria

1. `cargo test --workspace` green; `cargo clippy --workspace --all-targets` clean under
   `-D warnings`; `cargo fmt --check` clean; `npm test` green; the e2e suite green.
2. The `real-shell (Windows)` job passes **with no `--skip`**, and `cargo test --workspace`
   still spawns no process.
3. `acter-core` gains no dependency; `Transport` is unchanged; nothing in Acter enumerates
   or terminates a process.
4. Module role rule and the visibility ladder hold.
5. The measurement is in the PR body **including the rigged baseline** — that four
   mechanisms looked dead because of inherited spawn state is the most reusable thing this
   entry produced, and it should not have to be rediscovered.
6. **Accessibility checklist in the PR body**: a real program interrupted in the real app,
   heard through NVDA, confirming that Acter says nothing of its own and that the prompt
   coming back is read. Which items were agent-observed through the screen-readers bridge and
   which were human-verified is stated plainly.

## Out of scope

- **PowerShell.** Everything here was measured against `cmd.exe`. PowerShell does its own
  Ctrl+C handling and arrives in B5, so B5 re-runs this measurement rather than assuming
  the result carries over. The fix itself is shell-agnostic — it is about the state Acter
  hands down, not about what the shell does with a signal — but "shell-agnostic in
  principle" is not a measurement, and this entry has already been wrong once about
  exactly that kind of assumption.

- **What happens to descendants when a session is torn down.** `LocalPty::drop` kills the
  shell (`local.rs:222`) and nothing else, because nothing else is known to it. Whether a
  program the shell launched dies with the pseudoconsole or is orphaned is unmeasured, and
  is the same "we track nothing below the shell" fact this entry rests on. Not B4.1's to
  fix and not a defect anyone has reported — filed as a question worth its own roadmap
  entry rather than smuggled in here.

- **EOF.** Still B5's, by B6 decision 6 — shell knowledge, not transport knowledge.
- **B4.2, output emitted twice.** Independent and unchanged by this.
- **A program that refuses the signal outright.** Acter does not escalate to a kill, and
  says nothing it cannot support: the user hears no prompt come back, which is the truth.
  If that ever becomes a real complaint it is a new entry with its own decision.
