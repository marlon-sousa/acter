# Spec: PR B4.1 — an interrupt that interrupts

Agreed in conversation 2026-08-21. Lane 2, entry 22.1. Makes a Ctrl+C stop a program that
is genuinely running, and makes `command stopped` a claim the product can support.

## Why now / relation to the roadmap

An iteration entry from B4's manual NVDA pass, and the most serious thing that pass found:
`0x03` reaches the pseudoconsole, the program keeps producing output, and Acter announces
`command stopped` over the top of it — a claim a user cannot see to be false.

The roadmap named two candidate mechanisms. Neither is needed. The byte was never wrong;
the shell was spawned in a state that made it refuse the signal.

## What was measured

Against a real `cmd.exe` on a real ConPTY running `ping -n 20 127.0.0.1`, counting replies
over the five seconds after the interrupt, where zero means it took effect:

- Bare `0x03` with the ignore-Ctrl+C attribute inherited: **four replies**, and the same for
  a win32-input-mode key record and for `GenerateConsoleCtrlEvent` after `AttachConsole`.
- Bare `0x03` after one call to `SetConsoleCtrlHandler(NULL, FALSE)` before the spawn:
  **zero replies**, session survives, `echo` round-trips afterwards.

The first four results were measured against a rigged baseline and are recorded in the
roadmap as a trap rather than as findings about ConPTY.

## Design decisions this spec makes

1. **The fix is to stop handing the shell a broken inherited state.**

   `SetConsoleCtrlHandler(NULL, TRUE)` sets a process attribute that children inherit, and
   `CREATE_NEW_PROCESS_GROUP` sets it implicitly for a whole group — which is how launchers
   routinely spawn children so they can kill trees. A shell spawned under it ignores Ctrl+C
   however correctly the interrupt is encoded. `LocalPty::spawn` calls
   `SetConsoleCtrlHandler(NULL, FALSE)` before spawning, so the shell inherits normal
   processing regardless of how Acter itself was launched.

2. **`INTERRUPT: u8 = 0x03` stays, and so does its unit test.**

   `an_interrupt_is_the_single_byte_0x03` pins correct behavior. Nothing about what
   `interrupt` writes changes, which is the point: this entry turned out to be about spawn
   state, not about the wire.

3. **`Transport::interrupt` is untouched, and Acter never stops a process itself.**

   A terminal client writes bytes; the pty and the OS turn them into a signal. Reaching
   into the process table to terminate anything would be doing the kernel's job from the
   wrong layer, and would cost what a real Ctrl+C preserves — handlers running, cleanup
   happening, the program choosing its own exit code. An earlier draft of this spec
   proposed exactly that on the strength of the rigged measurement; it is recorded here as
   rejected so the reasoning is not repeated.

4. **The announcement moves from request time to evidence, in the unintegrated path.**

   A working `0x03` is asynchronous: the program is signalled, its handler runs, and it
   stops in its own time. Today `Pump::interrupt` writes and immediately calls `close(None)`,
   so `command stopped` is spoken before anything is known — and a program that handles the
   signal slowly, or refuses it, is exactly when the words are false. Instead: arm a short
   deadline and close on whichever comes first, quiescence after the interrupt or the
   deadline expiring. The words do not change and no new vocabulary reaches a screen reader
   user; only the moment they are allowed. The standing claim in
   `ui/src/controllers/app.ts` — that `CommandInterrupted` "says it when the interrupt took
   effect rather than when it was accepted" — becomes true. An integrated session is
   unaffected: its close is already driven by a real `BlockEnded`.

5. **`windows-sys` joins `acter-transports`, for one call.**

   `Win32_System_Console` only, `#[cfg(windows)]`. The Unix arm needs nothing: a bare
   `0x03` on a Unix pty is turned into `SIGINT` by the line discipline, so `local.rs` stays
   platform-neutral apart from this one guarded call. `acter-core` gains nothing.

6. **The fix is verified in the real app, not only in tests.**

   The confound that produced the wrong diagnosis was a *launch context*, and Acter's own
   launch context differs from both the spike's and the test suite's — a Tauri GUI process
   may carry different inherited state than a `cargo test` child. The behavior was
   originally heard through NVDA, so that is where it is confirmed fixed. This is an
   acceptance criterion, not a nicety.

## Tests

Service, in `session.rs`, against the fake far end:

- An interrupt does not close the command at request time.
- A far end that goes quiet after an interrupt closes the command as stopped.
- A far end that keeps talking past the deadline still closes, so a command cannot hang
  open — the "stranding a session in running is the one answer that is certainly wrong"
  rule from B2.

Real-shell, in `tests/local_pty.rs`, `#[ignore]`d:

- **`an_interrupt_stops_a_running_program` turns green.** It already exists and already
  states the requirement; its skip comes out of CI in the same commit.
- `an_interrupt_reaches_the_shell_and_the_session_survives_it` keeps passing, and gains a
  sibling that stops a *real* program and then submits another command — so "survives" is
  proven against a program that had to be signalled rather than against `pause`.

## Acceptance criteria

1. `cargo test --workspace` green; `cargo clippy --workspace --all-targets` clean under
   `-D warnings`; `cargo fmt --check` clean; `npm test` green; the e2e suite green.
2. The `real-shell (Windows)` job passes **with no `--skip`**, and `cargo test --workspace`
   still spawns no process.
3. `acter-core` gains no dependency; `Transport` is unchanged; nothing in Acter enumerates
   or terminates a process.
4. Module role rule and the visibility ladder hold.
5. The measurement is in the PR body **including the rigged baseline** — that four
   mechanisms looked dead because of inherited spawn state is the most reusable thing this
   entry produced, and it should not have to be rediscovered.
6. **Accessibility checklist in the PR body**: a real program interrupted in the real app,
   heard through NVDA, confirming `command stopped` is spoken once and that no further
   output follows it. Which items were agent-observed through the screen-readers bridge and
   which were human-verified is stated plainly.

## Out of scope

- **EOF.** Still B5's, by B6 decision 6 — shell knowledge, not transport knowledge.
- **B4.2, output emitted twice.** Independent and unchanged by this.
- **A program that refuses `SIGINT` outright.** Decision 4's deadline stops the session
  from hanging, but Acter does not escalate to a kill. If that ever becomes a real
  complaint it is a new entry with its own decision about what to say out loud.
