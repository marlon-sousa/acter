# Spec: PR B4.1 — an interrupt that interrupts

Agreed in conversation 2026-08-21. Lane 2, entry 22.1. Makes `LocalPty::interrupt` stop a
program that is genuinely running, and turns `command stopped` from a claim the product
makes into one it can support.

## Why now / relation to the roadmap

An iteration entry from B4's manual NVDA pass, and the most serious thing that pass found:
`0x03` reaches the pseudoconsole, the program keeps producing output, and Acter announces
`command stopped` over the top of it — a claim a user cannot see to be false.

The roadmap named two candidate mechanisms and priced one of them as certain. Both were
measured before this spec was written, and neither works. The roadmap entry now carries
the measurement and the correction; this spec restates the outcome as decisions rather
than reopening them.

## What was measured

Against a real `cmd.exe` on a real ConPTY running `ping -n 20 127.0.0.1`, counting replies
over the five seconds after the interrupt, where zero means it took effect:

- Bare `0x03`, today's behavior: **four replies**.
- A win32-input-mode Ctrl+C key record: **four replies**. ConPTY requests the mode
  unprompted and parses the record — one sent at an idle prompt makes cmd cancel its input
  line — so the key event arrives and is understood. It does not become a console control
  event for the running child.
- `AttachConsole` plus `GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)`: **five replies**, with
  `GetConsoleProcessList` confirming the shell's pid on the joined console.
- The same with `CTRL_BREAK_EVENT`: **five replies**.
- Terminating the shell's children: **zero replies**, session survives.

## Design decisions this spec makes

1. **The mechanism is stopping the shell's descendants, and it lives inside `LocalPty`.**

   Every alternative was measured and does not work. This one does. `Transport::interrupt`
   keeps its signature and its place on the port, which is what the port's own doc comment
   already promises: over SSH the same intent is a channel request travelling outside the
   data stream, and nothing above the port learns that ConPTY needs something else.

2. **It is a kill, not a Ctrl+C, and the spec says so out loud.**

   No console control handler runs in the target, so a program gets no chance to flush, to
   remove a temporary file, or to restore terminal state; its exit code is a termination
   rather than whatever it would have chosen. That is a real loss against a true Ctrl+C and
   it is written here so it is a known cost rather than a later surprise. It is also the
   only measured way to make this entry's test pass.

3. **Walk the whole tree below the shell, not just its direct children.**

   One level was enough for `ping`, but a batch file, a build tool, or anything that
   spawns workers of its own is precisely the case that makes one level wrong, and a
   half-stopped program is worse than an unstopped one because the announcement is then
   true of only part of what is running. Terminate leaves first so a parent cannot spawn
   replacements while the walk is in progress. The shell itself is never a target: the
   session has to survive, which is the other half of the requirement and what
   `an_interrupt_reaches_the_shell_and_the_session_survives_it` already pins.

4. **No descendants is `Ok(())`, not an error.**

   Reaching the transport at all means the service believed something was running, and
   `SessionService::send_key` already refuses on `running` before a request is sent. A
   shell sitting at a prompt when the walk arrives is the race B6 decision 7 accounts for
   by targeting whatever is running rather than an id the frontend supplied — not a
   failure worth a spoken sentence.

5. **The Windows-specific part goes in its own module, and the byte stays for platforms
   where it is right.**

   B4's decision 1 observed that nothing in `local.rs` was Windows-specific. This changes
   that, so the change is quarantined rather than allowed to spread: a new
   `crates/acter-transports/src/local/stop.rs`, role adapter, `#[cfg(windows)]`. On a Unix
   pty a bare `0x03` genuinely does interrupt — the line discipline turns it into `SIGINT`
   for the foreground process group — so the non-Windows arm keeps writing the byte. The
   split is honest rather than defensive: the byte is correct there and wrong here.

6. **`INTERRUPT: u8 = 0x03` and its unit test go.**

   `an_interrupt_is_the_single_byte_0x03` pins the behavior this entry exists to remove.
   It is replaced by a test of what `interrupt` now does, not deleted silently.

7. **The announcement closes immediately, and that is now honest.**

   The roadmap raised whether `command stopped` should wait until an interrupt is known to
   have taken effect. With a kill it is known by the time `interrupt` returns, so the
   unintegrated path keeps closing the command synchronously and no new vocabulary reaches
   a screen reader user. The standing comment in `ui/src/controllers/app.ts` — that
   `CommandInterrupted` "says it when the interrupt took effect rather than when it was
   accepted" — becomes true, where in an unintegrated session today it is not. No deadline,
   no quiescence rule, no second announcement: the measurement bought the simple version.

8. **`windows-sys` joins `acter-transports`, and nothing off the shelf replaces it.**

   `Win32_System_Diagnostics_ToolHelp` for the process walk, `Win32_System_Threading` for
   `OpenProcess` and `TerminateProcess`. `command-group` only extends
   `std::process::Command` and cannot reach inside `portable-pty`'s spawn. `termwiz` —
   `portable-pty`'s own sibling, whose documentation advertises `KeyboardEncoding::Win32`
   against the ConPTY keyboard spec — defines that variant and never implements it,
   returning a bare `0x03`. `acter-core` gains nothing.

## Tests

Unit, in `stop.rs`, with no process spawned:

- The walk collects descendants of a pid and never the pid itself — pinned against a
  synthetic parent/child table so the tree logic is testable without spawning anything.
- Leaves come before their parents in the termination order.

Real-shell, in `tests/local_pty.rs`, `#[ignore]`d:

- **`an_interrupt_stops_a_running_program` turns green.** The test already exists and
  already states the requirement; this PR is what makes it pass. Its skip comes out of CI
  in the same commit.
- `an_interrupt_reaches_the_shell_and_the_session_survives_it` keeps passing, and gains a
  sibling that stops a *real* program and then submits another command, so "survives" is
  proven against the mechanism that could plausibly break it rather than against `pause`.
- An interrupt with nothing running is accepted and the session stays usable.

## Acceptance criteria

1. `cargo test --workspace` green; `cargo clippy --workspace --all-targets` clean under
   `-D warnings`; `cargo fmt --check` clean; `npm test` green; the e2e suite green.
2. The `real-shell (Windows)` job passes **with no `--skip`**, and `cargo test --workspace`
   still spawns no process.
3. `acter-core` gains no dependency; `Transport` is unchanged.
4. Module role declared on the first line of the new module's `//!` comment; the visibility
   ladder holds; `module.rs` plus `module/` folder, no `mod.rs`.
5. The measurement that chose the mechanism is in the PR body, including the four
   mechanisms that failed — the negative results are the reason this shape was picked and
   they should not have to be rediscovered.
6. **Accessibility checklist in the PR body**: a real program interrupted through a real
   shell, heard through NVDA, confirming `command stopped` is spoken once and that no
   further output follows it. Which items were agent-observed through the screen-readers
   bridge and which were human-verified is stated plainly.

## Out of scope

- **EOF.** Still B5's, by B6 decision 6 — shell knowledge, not transport knowledge.
- **A true Ctrl+C on ConPTY.** Decision 2 accepts a kill deliberately. If a future Windows
  build makes console control events work through a pseudoconsole, replacing the mechanism
  behind `interrupt` touches one module.
- **B4.2, output emitted twice.** Independent, and unchanged by this. Worth noting the
  interaction: output already in flight from a killed program still arrives after the
  block closes, which is the mis-attribution B4.2 is about, not a new defect from this.
