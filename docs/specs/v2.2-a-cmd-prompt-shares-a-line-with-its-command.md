# V2.2 — a cmd prompt shares a line with its command

Lane 5, the look; roadmap entry 53.2. It follows V2 and V2.1.

## What is true today

Measured on 2026-09-23 against cmd.exe, with the V2 build driven over the embedded WebDriver: the
buffer held no `p.prompt` at all. Each prompt, `C:\Users\marlo>`, arrived as an output row,
followed by the command's heading, so on screen the prompt and the command sit on separate lines.
Against PowerShell every prompt was a `p.prompt`, and V2 folded them all.

The research for this spec (2026-09-23, from the code and the specs) corrected the entry's
reading. cmd *is* marked:

- `crates/acter-shells/src/cmd.rs` sets `PROMPT` to `$e]133;A$e\$P$G$e]133;B$e\`, so every prompt
  carries OSC 133 `A` and `B` (measured in B4.5). Its markers are
  `ShellMarkers::PromptAndCommandLine`, because cmd has no hook that could report `C` or an exit
  code.
- For a shell with no exit code, the returning prompt is the only audible "it is done". So
  B4.5 decision 4 and `Pump::marked` accept `Region::Prompt` as block content, and B5.6
  decision 1 deliberately sends no `PromptDrawn` for such a shell, "or it would say everything
  twice". The prompt is therefore an output row of the block that just ended, and it is
  spoken as one.

Bash under WSL started through `ACTER_SHELL=wsl` was unmarked for a different reason: that
development path asks its set-up question through `Unasked`, which always answers Skip. A saved
WSL connection with `set_up: Yes` does set bash up. V2.1 already hides that path's doubled
command lines.

## Decisions

1. **An output row that is a prompt says so.** `SessionEvent::Output` gains `prompt: bool`,
   true when the row was drawn in `Region::Prompt`. The service knows the region when it
   receives the line, so `Pump::line` carries it through `Held` and `Due` to `output`. What is
   spoken and when does not change. `PromptDrawn` still applies only to shells that report exit
   codes.
2. **The buffer marks that row.** `BufferDom.applyLine` gains the flag and gives the row the class
   `prompt-row`. No role, name or order changes.
3. **The fold treats a prompt row like a prompt paragraph.** CSS floats `.prompt-row` when it is
   the last row of a block followed by a heading, or the last row in the buffer, with the same
   one-character gap as V2. So `C:\Users\marlo>` and `echo hello %NAME%` share a line, and the
   last prompt shares its line with the edit field. A float keeps the row `display: block`, which
   is what NVDA reads (measured for V2).
4. **A heading that already begins with its prompt is not folded onto it.** In far-end mode,
   cmd's heading can carry the prompt itself, as in
   `C:\Users\marlo>python -c "input('Python asks: ')"` (measured). When the heading's text begins
   with the prompt row's text, the row is not floated but hidden from sight by the same
   visually-hidden rules as V2.1, so the screen shows the prompt once. The row is still in the
   page, and is still read and spoken.

## What V2.2 does not do

- It does not give cmd `PromptDrawn`, and it does not change what cmd says.
- It does not change the `ACTER_SHELL=wsl` development path.

## Acceptance criteria

1. Session tests:
   - under `PromptAndCommandLine`, the returning prompt's `Output` carries `prompt: true`;
   - output rows carry `prompt: false`;
   - under `Full`, nothing changes.
2. Buffer tests: `prompt-row` is set and cleared with the flag; a prompt row that begins the next
   heading is hidden instead of folded.
3. All existing tests pass. Test helpers gain the new field.
4. Against cmd, a screenshot shows `C:\Users\marlo> echo hello %NAME%` on one line, and the last
   prompt beside the cursor, in both line modes.
5. NVDA 2026.1.1 through the bridge, `user` persona: a cmd session reads line for line the same
   with and without the fold, and the returning prompt is still announced when a command ends.
