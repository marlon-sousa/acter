# B5.2 — the PowerShell adapter

Roadmap entry 23.2. Agreed in conversation 2026-08-23. Depends on 23.1, which supplies the
port.

**The first shell that can tell Acter a command ended, and with what.** cmd can mark its
prompt and its command line and nothing else (B4.5), so every session so far has ended its
blocks by inference and has never had an exit code. PowerShell can emit all four OSC 133
markers, which makes this the entry where `CommandFinished`, `Announcement::Failed` and the
whole verdict path stop being machinery built against fixtures and start describing a real
session.

## What the measurement found, 2026-08-24

**Everything below was read off a real pseudoconsole**, the way B4.5 read cmd's `PROMPT`,
and it contradicted this spec three times. Each contradiction is an amendment further down
rather than a footnote, because each of them would otherwise have shipped as a defect
nobody could see.

**The machine**: Windows PowerShell **5.1.26100.9168** at
`C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`, and PowerShell **7.6.5** at
`pwsh.exe`. Both editions were driven; the suite drives 5.1, because it is on every Windows
machine including the CI image and the two were measured to produce the same marker stream.

### Finding 1: PowerShell 5.1 disables PSReadLine in front of a screen reader

The session opens by saying `Warning: PowerShell detected that you might be using a screen
reader and has disabled PSReadLine for compatibility purposes`, **and it means it**:
`PSConsoleHostReadLine` does not exist in that session. PowerShell 7 makes no such check and
leaves PSReadLine on.

So the two editions disagreed about the *shape of the byte stream* in front of exactly the
users this product is for — and with PSReadLine active the result was not merely different,
it was wrong: `C` arrived immediately after `B`, before the user's line had been read, which
puts the echoed command line into a block's content instead of its heading. PSReadLine also
redraws the row as it goes: a submitted `echo acter-hello` came back as
`ESC[?25l echo acter-hel ESC[?25h lo`.

### Finding 2: `$LASTEXITCODE` is stale, and reading it alone is wrong

Measured: `cmd /c exit 3` followed by a failing `Get-Item` reported `D;3` for the
`Get-Item` — an exit code belonging to the command *before* it. `$?` alone is no better; it
throws away the code the user actually wants.

The rule that survived measurement: success is `0`; a failure whose `$LASTEXITCODE`
*changed* since the last prompt reports that code, because only a native program could have
changed it; any other failure reports `1`. Across both editions: `cmd /c exit 3` gives
`D;3`, a failing cmdlet after it gives `D;1`, a successful command gives `D;0`, and an
interrupted command gives `D;-1073741510`, the Windows control-C exit status.

**What the rule rounds, said out loud**: the same native exit code twice in a row is
reported as `3` and then as `1`, because nothing distinguishes an unchanged `$LASTEXITCODE`
from a cmdlet failing behind it. It never turns a failure into a success.

### Finding 3: neither control byte ends a PowerShell session

`0x1a` (Ctrl+Z) and `0x04` (Ctrl+D) both fail: they are echoed as caret text, the session
stays, and a line submitted behind one runs as a command the user never typed. What ends a
session is the line `exit`, so the port's answer is bytes rather than a keystroke — see the
amendment to decision 5.

### Finding 4: execution policy does not block the injection

A `-Command` string is not a script file. Measured: Windows PowerShell 5.1 started with
`-ExecutionPolicy Restricted` runs the whole snippet and emits every marker. (PowerShell 7
under `-ExecutionPolicy AllSigned` stops at a publisher-trust prompt before reaching the
string at all, because the host auto-imports PSReadLine's own `.ps1xml` first. That is the
host's behaviour in any terminal, not something an injection can avoid.)

### What the shell is actually started with

    powershell.exe   -NoLogo -NoExit -Command <snippet>
    pwsh.exe         -NoLogo -NoExit -Command <snippet>

`-NoLogo` because 5.1 otherwise opens with four lines of copyright a listener has to get
past before reaching their prompt; `-NoExit` because without it PowerShell runs the snippet
and exits, which is a session that ends before it starts.

## Decisions

### 1. Editions are values, not two adapters

`PowerShell::windows()` for Windows PowerShell 5.1 (`powershell.exe`, present on every
Windows machine) and `PowerShell::seven()` for PowerShell 7+ (`pwsh.exe`, installed
separately). One implementer, one snippet, one set of markers; what differs is the program
name and — measured, not assumed — possibly nothing else.

**Which of them exist on this machine is not this entry's question.** Discovery is I/O and
belongs to the port 23.3 introduces and the list B7 builds. This adapter answers "how do I
start this edition", and answers it for an edition that may not be installed, which is a
pure function and testable as one.

### 2. The injection is an argument, not an environment variable, and it writes nothing

`powershell.exe -NoLogo -NoExit -Command "<snippet>"`. The snippet defines the prompt
function and the marker hooks, then `-NoExit` leaves an interactive session behind it.

**Nothing is written to the user's machine**, which is the same stance cmd's `PROMPT`
injection took and it is deliberate: no profile edited, no file dropped in a temp
directory, nothing to clean up, and nothing left behind if Acter is killed. It also
sidesteps execution policy entirely — a `-Command` string is not a script file, so the
policy that blocks unsigned `.ps1` files does not apply. That last point is measured in a
locked-down state rather than reasoned about, because a shell that refuses to start on a
managed machine is exactly the failure this product cannot afford.

### 3. The four markers, and which of them are guesses until measured

The shape, following the mechanism VS Code's PowerShell integration uses:

- **A** (prompt start) and **B** (command-line start) ride inside the `prompt` function,
  the way they ride inside cmd's `PROMPT` string.
- **D** (command end, with the exit code) is emitted by the *next* `prompt` call, since
  PowerShell runs the prompt function after each command. The exit code is where care is
  needed: `$LASTEXITCODE` reports a native program's code, `$?` reports whether the last
  *PowerShell* command succeeded, and a failing cmdlet leaves `$LASTEXITCODE` untouched. The
  rule has to make both cases honest, and a wrong exit code is worse than none — it becomes
  an `Announcement::Failed` spoken about a command that succeeded.
- **C** (output start) cannot come from the prompt function, because it belongs after the
  user's line has been read. The candidate is a `PSConsoleHostReadLine` wrapper.

**Amended after measurement: `C` comes from `PreCommandLookupAction`.** The
`PSConsoleHostReadLine` candidate does not exist in a 5.1 session with a screen reader
attached, and defining one means owning the line editor — measured, a version built on
`[Console]::ReadLine()` works and even turns Ctrl+Z into a real end of input, but it emits a
stray `C` every time an interrupt breaks the read, opening a block with no command line in
it. `PreCommandLookupAction` is a scriptblock PowerShell runs when it resolves a command
name: after the line is read, before anything runs. A flag the prompt arms and the hook
disarms keeps it to one `C` per command however many names that command resolves.

**The case this had to survive is a line that looks up no command at all.** `1..3`, `2+2`
and `'a literal string'` all produce output and none is a command invocation; had the hook
not fired, their output would have landed in the `B..C` region, which `Pump::wants`
excludes — so the user would have heard nothing. Measured on both editions: every one of
them emits `C` before its first line of output, because PowerShell resolves the formatting
pipeline as a command. A line producing no output at all still gets one from the next
prompt's own lookup, which is an empty output region and exactly right.

**All four are measured off a real pseudoconsole before any of this is written**, the way
B4.5 measured cmd's `PROMPT` byte for byte rather than trusting the documentation, and for
the same reason: what a shell claims to emit and what arrives through ConPTY have already
differed once in this project.

### 4. PSReadLine is removed, so it is *not* the test of B6.1's rewritten-echo rule

**Amended after measurement, and this is the change with the most reasoning behind it.**

PSReadLine redraws the command line as the user types, so what reaches the engine is a
rewrite of the whole row, prompt included — precisely the case B6.1 named as the one a real
PowerShell session would exercise first, where the rule strips the prompt and reports
`None` rather than guessing at a heading. This entry is where that is proven against a real
shell rather than against a constructed transcript. A regression here is silent and awful:
every block gets the wrong heading.

**What was measured instead**: the two editions disagree about whether PSReadLine is there
at all, and with it active the stream is wrong rather than merely different (finding 1). So
the snippet removes PSReadLine, per session and per process, which is the same call
Microsoft already makes for 5.1 in front of a screen reader.

**Acter loses nothing by it.** The edit field, the history and the completion are Acter's
own, so PowerShell's line editor is never the thing a user types into. Nothing on disk is
touched, and `Import-Module PSReadLine` brings it straight back.

**So B6.1's rewritten-echo rule is still unproven against a real shell**, and this spec must
not claim otherwise. It is exercised here only by the golden transcript, which was captured
*with* PSReadLine active precisely so the case is not lost.

### 5. EOF arrives here

`SessionIntent::Eof`, one keybinding-table row, and one adapter method saying what byte or
key sequence this shell wants. B6 deferred it to whichever entry first had a port to hang
it on, and this is that entry.

**Amended after measurement: the answer is bytes, and PowerShell's is the line `exit`.**
This spec said "PowerShell wants Ctrl+Z followed by Enter; bash wants `0x04`", and the first
half is simply false — neither control byte ends a session (finding 3). Had the method been
shaped as "which control byte", it would have had to answer "none" for the very shell it was
introduced for.

`None` is the honest answer for a shell nobody has measured, and it is not the same as "this
shell cannot be ended": it is "Acter does not know how", which the session reports rather
than guessing at a byte and leaving text on the line. **Bash under WSL answers `None` for
exactly that reason** — `0x04` is probably right, nobody has driven it, and this entry is the
evidence that "probably right" is not good enough.

### 6. Golden transcripts

The first real PowerShell session is recorded in B2's transcript format and committed as a
fixture, which is what the original B5 entry asked for: a captured real session becomes a
replayable fake session, so everything above the transport can be tested against real
PowerShell behaviour without PowerShell.

## Definition of done

- [x] The snippet is measured off a real pseudoconsole and this spec's expectations are
      replaced by what was actually observed — see the measurement section, which records
      four findings, three of which contradict what was written here first.
- [x] All four markers arrive in a real session; a real `ShellMarkers::Full` session opens
      and closes blocks by marker rather than by inference
      (`a_real_powershell_marks_every_boundary_and_finishes_its_blocks`).
- [x] A failing command produces the right exit code, and a failing *cmdlet* and a failing
      *native program* are both reported correctly — the case where `$LASTEXITCODE` and `$?`
      disagree is a test rather than a note, and the rule it pins was written *from* that
      disagreement rather than around it.
- [ ] **Not done, and deliberately so: typing with PSReadLine active.** The snippet removes
      PSReadLine, so this cannot be asserted against a live session here — see decision 4 as
      amended. The rewritten-row case is carried by the golden transcript, captured with
      PSReadLine active for exactly that reason, and B6.1's rule remains unproven against a
      live shell. **This box stays open rather than being reworded to something that passes.**
- [x] The session starts under a restrictive execution policy (finding 4).
- [x] EOF reaches a real PowerShell and ends the session
      (`ctrl_d_ends_a_real_powershell_session`), and a shell with no measured answer says so
      rather than guessing (`ctrl_d_in_a_shell_with_no_measured_answer_does_nothing`).
- [x] A golden transcript is recorded and replays through the scripted transport
      (`fixtures/powershell_prompt.json`, driven from `pipeline.rs`).
- [x] Unit tests for the snippet's shape and for both editions' launches; the real-shell
      tests are `#[ignore]`d like every other test that spawns a process.
- [x] `cargo fmt`, `cargo clippy --workspace --all-targets`, workspace tests clean, and the
      ignored real-shell suite green: 19 passed, five of them PowerShell's.

**Accessibility checklist in the PR body**, because this is the first session a listener can
hear a verdict in: a failing command announces its exit code after its output, a successful
one says nothing about its code, and the block boundaries a listener navigates by are the
shell's own rather than inferred.

## One amendment that came from merging rather than from measuring

**`SessionService::start` takes a `ShellFacts` value**, not a `ShellMarkers` and not a
`&dyn ShellAdapter`.

This entry gave the domain a *second* thing to ask a shell — end-of-input, beside markers —
and the first implementation passed the adapter itself so the service could ask for both.
B5.3 landed in parallel and had reshaped the same seam differently, so the two met on rebase
and neither survived as written. The resolution, agreed in conversation 2026-08-25: bundle
what the session needs into one value, which is the reasoning `ShellLaunch` is already built
on, applied to the other side of the seam. The launch is what the transport needs; this is
what the session needs; each travels whole rather than as a growing argument list that every
entry in B5 would have to edit.

Values rather than a borrowed adapter, for two reasons worth keeping: the service reads both
facts once at construction and holds them for the life of the session, so a borrow would be
a reference it never uses again; and the tests whose whole subject is a shell with its
injection *deliberately* removed have no adapter to hand over. It also deleted the fake
adapter `acter-core`'s own tests had needed.
