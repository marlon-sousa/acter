# B4.9 — the echo is held rather than read back, and a bare Enter reaches the shell

Roadmap entry 22.12, both halves, in one PR. Agreed in conversation 2026-08-23.

Two defects a listener meets in the same minute. The first: every command after the first
is read back at the user in their own words before its output arrives, because the far
end's echo is forwarded as the previous block's output and B4.4 turned autoread on. The
second: pressing Enter on an empty field does nothing at all — no prompt, no sound, no
evidence the session is alive.

## What this changes, in one sentence each

1. **The echo is held on the row the submission is pending on, and dropped once it turns
   out to be the echo.** Not compared against the heading, and not held generally: held
   positionally, on one row, from the instant Enter was pressed.
2. **An empty submission is sent to the far end instead of being discarded**, and it opens
   no block: a bare Enter is a re-orient gesture, not a command.

## The B4.4 objection, re-examined rather than inherited

B4.4 left the echo in the stream and wrote down why: "Removing it instead would mean
holding every row back until it was complete, which delays speech and strands text when a
far end goes quiet mid-row."

That reasoning still stands, and it is not an objection to this spec. It is an objection to
a rule that holds **every** row, which is what a content-matching fix would need, because
any row might turn out to equal the heading. This rule holds **one** row — the one the far
end's cursor was on when Enter was pressed — and only while a submission is pending on it.
Every other row is forwarded the instant it arrives, including output produced while a
submission is pending.

What the objection's second half costs here is real, bounded, and stated rather than
argued away: text appended to the pending row and then followed by nothing is held until
something else arrives. That is at most one pending line's worth of characters — the hold
is bounded by `Pump::window`, as B4.4 built it — and it is text appended to a row whose
beginning the listener has already heard, because the prompt was forwarded before Enter
was pressed. A password prompt, the case that would matter, is unaffected: it is drawn
before the user types, so it is already spoken.

## Decision 1 — what "the row the cursor is on" is, in terms the pump already has

**The pending row is the line the far end last wrote to when the submission was written** —
the most recent `Appended` or `Rewritten` item, remembered as `Pump::cursor` and captured
into `Pump::pending_row` in `Pump::submit`.

That is exact for the case this entry is about, for the reason the roadmap gives: the only
thing that reaches the far end is what Acter wrote, so anything appended to that row after
that instant is the far end echoing it. It needs no markers, which is the whole point — it
reaches inside a container, an `ssh`, a `wsl` and a REPL, where OSC 133 cannot.

**Rejected: asking the engine.** A `TerminalEngine::cursor_line` would be truer to the
words "where the cursor is", and it was not taken. It is new port surface implemented three
times — Alacritty and both fakes — to answer a question the pump can already answer from
the stream it is holding, and it would not answer it any better: a cursor sitting on a row
that has no text yet has no `LineId` to report, which is exactly the case Decision 3 gives
up either way.

## Decision 2 — the hold extends from "no block is open" to "a submission is pending on this row"

`Pump::line` forwards an append to the open block unless the append landed on the pending
row while a submission is pending; in that case it goes to `Pump::hold`, which B4.4 built
for the empty-heading case, unchanged in shape:

- Accumulated per `LineId`, so a read that cuts the echo in half cannot change the outcome.
  Position is chunk-independent, which is what
  `every_session_says_the_same_thing_when_every_byte_is_its_own_read` requires.
- Bounded by `Pump::window` — the longest line still waiting for an echo, plus one — so
  held text can never exceed what an echo could be.
- Released by `Pump::spill` the moment it can no longer be an echo: a different row
  arrives, the window closes, or the bound is passed.

`Pump::boundary` already strips a matched echo off the end of held text and publishes
whatever came before it. One change there: what came before it goes to the block that is
open, and opens an unclaimed block only when none is. Today it always opens one, which was
right when holding only ever happened before the first block existed.

**Where it does not apply.** A marked `cmd.exe` session's own echo is in
`Region::CommandLine`, which `Pump::wants` already rejects and `Pump::boundary` already
skips, so nothing about the outer shell changes. This rule is for everything past the
injection point, which is where B4.5 left the seam.

## Decision 3 — what is knowingly not covered, and why it cannot be

Two shapes stay as they are today, both named here so the PR is not read as claiming them.

**A far end that ends the row before the echo starts.** If the last thing written before
Enter ended its row, the echo begins a fresh line the pump cannot name in advance, and it
is forwarded. Every prompt this product meets leaves the cursor on the prompt row —
`cmd.exe`, a container's `sh`, an `ssh` login, a REPL's `>>>`, a `[y/N]` — so the case is
theoretical for a shell and real only for a program that reads a line having printed
nothing at all.

**A second line typed ahead of the first.** With two submissions pending, the second is
echoed on a row the far end chooses after it has finished the first, which is not knowable
when Enter was pressed. No positional rule can reach it: between the two echoes lies the
first command's output, so "the next row written" is output rather than an echo. The first
submission of a backlog is covered; the rest are read back, exactly as today.

Both fail in the safe direction — an echo spoken once, never text hidden.

## Decision 4 — an empty submission is never queued for correlation

`Pump::submit` writes the Enter and returns; it pushes nothing onto `submitted`.

This is what makes "an empty submission opens no block" true rather than hoped for. A
queued empty submission could not match any echo — `Pump::echoed` and `Pump::window`
already ignore an empty line — so it would sit at the front of the queue until some later
block claimed it, and `Pump::claim` claims from the front. That is B6.1's drift, restored
by a keystroke: the next command's output would open a block under the bare Enter's id
while the block the frontend opened for that command stayed empty.

Not queueing it also keeps `running` honest. `Pump::settle_running` computes it from the
queue and the open block, so Ctrl+C after a bare Enter still answers "nothing running to
stop".

## Decision 5 — the cancel byte goes ahead of a bare Enter too

`Pump::cancel_pending_input`'s gate becomes "nothing else was already pending", which is
what its `submitted.len() == 1` meant before an empty submission stopped being queued.

It is not a side effect worth hiding. At a marked `cmd.exe` prompt holding an unclaimed
device-query answer (22.11), a bare Enter without the cancel byte submits that answer as a
command, and the user hears that something they never typed is not recognized as an
internal or external command. The gate is unchanged in substance: a shell whose prompt
Acter injected, sitting in `Prompt` or `CommandLine`, with nothing else pending.

## Decision 6 — what a bare Enter does, in each session shape

The frontend sends it in all three. What the far end does with it differs, and none of the
three is silent:

- **Unintegrated `cmd.exe`**: the shell redraws its prompt, which is forwarded to the block
  that is still open and spoken. No new block.
- **Inside a container, an `ssh` or a REPL**: the same, in the block the proxying command
  opened. No new block. This is the case the user asked for.
- **Marked `cmd.exe`**: the block of the previous command has already closed on that
  command's `B`, so the prompt this Enter brings back arrives with nothing open and
  `Pump::unclaimed` gives it a block of its own — the shell's own text getting a block with
  no heading, which is what B4.5 already ships for the first prompt of a session. The
  prompt is spoken. No synthetic `C` is involved: the tracker ends a command-line region
  only on a line item landing on another row, and nothing was echoed.

The third is a consequence rather than a choice, and it is the one to listen to in the
manual pass. If an empty heading per bare Enter grates, the fix is about how the frontend
renders a headingless block, and it belongs to 22.9 rather than here.

## Decision 7 — the frontend submits the empty line and opens no block

`AppController.submit` stops returning early on an empty field. It submits the trimmed text
whatever it is, clears the field, and opens a buffer block only when that text is not
empty. The ack's id is still minted and simply ignored for an empty line, so nothing about
the protocol changes.

## DESIGN amendment, riding in this PR

Per CLAUDE.md a **Decided** item changes in the PR that implements the change. Under *Edit
field ownership*, the bullet "The block opens where the echo arrives, not where Enter was
pressed" currently ends by saying the echo stays in the block that was open when the far
end wrote it, because removing it would mean holding every row back until it was complete.

That half is replaced: the echo is held on the row the submission is pending on and dropped
when it completes. The sentence about holding every row is kept, as the reason the rule is
positional rather than general. The same bullet gains the empty-submission rule: a
submission with no text matches no echo, opens no block, and is not carried in the
correlation queue — a bare Enter is a re-orient gesture, and the prompt it brings back is
the answer to it.

The *Echo exclusion* bullet's B4.5 amendment already decides the marked case positionally —
"only text appended to the row the prompt was drawn on stays in the excluded region". This
is the same rule one layer out, for the far ends no marker reaches, and is noted there as
such.

## Acceptance criteria

1. In an unintegrated session, no command's echo reaches the buffer as output — the second
   and third commands as well as the first.
2. In an integrated session, a line typed into a nested shell is not read back: its echo
   lands in the open `C..D` of the proxying command and is dropped.
3. Output arriving on any other row while a submission is pending is forwarded
   immediately, not held.
4. Text held on the pending row that turns out not to be an echo is still spoken, and no
   more than one pending line's worth is ever held.
5. The prompt is still forwarded and still the last thing announced after every command.
6. A bare Enter is written to the far end, queues no correlation id, leaves nothing
   running, and opens no block in the frontend.
7. A bare Enter at a marked `cmd.exe` prompt holding an unclaimed device-query answer does
   not run that answer as a command.
8. Chunk independence holds: the pipeline suite still says the same thing byte-at-a-time as
   whole.
