# B4.5 — cmd.exe carries OSC 133 A and B, and an unclaimed device-query reply stops corrupting the next command

Covers roadmap entries **22.5** and **22.11**, in one PR because they are the same session
seen twice: 22.5 gives a cmd session real regions, and those regions are what decide where
22.11's stray bytes land. Agreed in conversation 2026-08-22.

## Why one PR

22.5 changes what 22.11's second fault *is*. The escape bytes 22.11 found sit on the
prompt row, between the shell's prompt and the echo of the submitted line — which in an
unmarked session is text with no region at all, and in a marked one is `B..C`, a region
`Pump::wants` already excludes. So the marker work removes the second fault for the outer
cmd shell as a side effect, and leaves it exactly where the markers cannot reach.

They also share the gate that makes 22.11's fix safe. The cancel byte below must go only to
a shell reading a line, never to a program reading raw input, and "the prompt has been drawn
and nothing has said output began" is a region only the markers supply. Measuring 22.11
turned that from a convenience into a precondition: it is the only gate left once the
entry's stated cause turned out to be wrong — see decision 6.

## What is Decided going in

From ROADMAP 22.5's pinned answers, restated rather than reopened:

- An A/B-only shell is `Integrated`. No third `Integration` state.
- What differs is a declaration by the shell that it marks `A` and `B` only.
- `C` is synthesized by the tracker at the end of the echoed line. It is not a guess: in a
  line-oriented shell the echo is the one line the shell read.
- A verdict stays unavailable in cmd. Every command ends with `exit: None`.
- In a shell known not to emit `C`, a line that cannot be classified must be forwarded,
  not dropped.

From the conversation of 2026-08-22, answering what 22.5 left for the spec:

- **The declaration is a value, not a port.** `ShellMarkers` lives in `acter-core` and is
  passed to `SessionService::start`. When B5's `ShellAdapter` lands it returns this value;
  nothing about the port's shape is decided here.
- **The prompt is still spoken.** See decision 4, which amends the pinned `D` answer.

## Decision 1 — `ShellMarkers`, and cmd's injection

`ShellMarkers` is an entity/value in `acter-core` with two variants: `Full`, every
session's assumption until now, and `PromptAndCommandLine`, a shell whose prompt can carry
`A` and `B` and which has no post-execution hook to carry `C` or `D`. It is passed to
`SessionService::start` and reaches both the boundary tracker and `Pump::wants`.

The cmd knowledge itself goes in `acter-shells`, which is the crate for it and has been an
empty facade since PR 0: a `cmd` module holding the prompt string that carries the markers
and the `ShellMarkers` it implies. `LocalPty::spawn` grows an environment parameter so the
container can set it — the transport still names no shell, which is DESIGN's
transport-versus-shell criterion.

## Decision 2 — the synthetic `C` rule

While `ShellMarkers::PromptAndCommandLine` is in force and the region is `CommandLine`,
**anything that is not a further append to the command-line row ends that region**: the
tracker emits `BlockStarted`, moves to `Output`, and only then processes the item that
ended it. The command-line row is the `LineId` the prompt was drawn on, which is the row
the echo is written onto (measured in B4.4 and recorded in the real-shell notes).

One rule, and it answers all three edges 22.5 left open:

- **A command line long enough to wrap.** `cmd.exe` swallows the continuation into the
  same `LineId`, so it is a further append and the region does not end early. Verified
  rather than assumed — the rule keys on the id, so a shell that starts a new row instead
  simply opens its block one row sooner, which costs a heading, never text.
- **A command that produces no output at all.** The next thing on the wire is the next
  prompt's `A`, which is a marker and therefore ends the region: the block opens, the
  prompt flows into it, and it closes. A submission that would otherwise report running
  forever ends properly, with a heading and no content.
- **An empty submission.** Nothing is echoed and nothing matches, so no region ends and no
  block opens, unchanged.

It also satisfies the safety constraint by construction. Text arriving on a *new* row
while the region is `CommandLine` ends the region and is forwarded as `Output`; only text
appended to the prompt row itself stays in `CommandLine`, and that is the echo and the
stray reply bytes and nothing else. The failure direction is a block that should not have
opened — extra structure — and never a silent line.

## Decision 3 — where a block ends in a shell with no `D`

**The block closes on `B`, not on `A`**, when `ShellMarkers::PromptAndCommandLine` is in
force. This amends 22.5's pinned answer that `PromptStart` calls `end_open_block`; the
pinned answer was written before the audibility question in decision 4 was asked, and the
two cannot both be satisfied by closing on `A`.

In cmd the whole prompt string is one write, so `A`, the prompt text and `B` arrive
together: closing on `B` puts the returning prompt inside the block of the command that
just ended, and closes it a few bytes later. Closing on `A` instead leaves the prompt with
no block to belong to, which produces exactly the headingless block that 22.10 and 22.4
were about.

`ShellMarkers::Full` keeps today's behaviour untouched, including DESIGN reliability case
3: `A` mid-block still closes it.

## Decision 4 — the prompt is block content when the shell emits no `D`

`Pump::wants` accepts `Region::Prompt` as well as `Region::Output` for a
`PromptAndCommandLine` shell. This is a new `wants` arm and 22.5's pinned answer said
there would not be one; the pinned answer was about not adding a *third integration
state*, and this is not that — it is one shell's declaration changing what counts as
content.

The reason it has to change: a cmd session has no exit code, so nothing is announced when
a command ends. Today the returning prompt is spoken because an unintegrated session
forwards it as output of the still-open block, and that is the only audible "it is done"
such a session has — which is why 22.12 records it as a requirement. Marking the session
without this arm would move the prompt into `Region::Prompt`, exclude it, and end every
cmd command in silence. That is a regression the marker work must not ship.

## Decision 5 — device-query answers are still written, always and promptly

Not reopened: `cmd.exe` will not draw its first prompt until the cursor-position query is
answered, so withholding the answer does not avoid a defect, it replaces one with a session
that never starts. B3 decision 4 stands.

## Decision 6 — 22.11's stated cause is wrong, and the measurement says so plainly

**Measured 2026-08-22**, driving a real `cmd.exe` through `LocalPty` with a slow consumer at
the far end — a PowerShell one-liner that writes the cursor-position query and then sleeps
for six seconds without reading. Every read the session received was logged.

The entry records that Acter answers the query itself, in `TerminalEngine::take_replies`,
and that its own answer is what lands unread in front of the next submitted line. **The
query never reaches Acter at all.** The only reads that arrive are the shell's own startup
query — which `cmd.exe` asks and reads — the echo of the submitted line, and then, already
formed, the text `C:\Users\marlo>^[[3;1R`. ConPTY intercepted the program's query, answered
it into the console input queue itself, and what Acter sees is that answer being echoed back
as input nobody read.

So the bytes are not Acter's. Two consequences, and they reshape the fix:

- **No ledger of what this pump wrote can see them coming**, because it never wrote them.
  The evidence gate this spec originally proposed — recognising our own answer's caret
  rendering — has no case to fire on and is not implemented.
- **The premise that separated this entry from 22.10's cmd-fidelity ruling is weakened.**
  The entry says the boundary holds because the bytes are Acter's own and `cmd.exe` never
  sends a cursor position report into its own input. ConPTY does. Whether a real `cmd.exe`
  window behaves the same way is a question for the user's own console, exactly as 22.10
  was; it is recorded in ROADMAP rather than ruled here. What is not in doubt is that a
  screen reader user cannot see the corrupted line, and that Acter can prevent it.

An answer that does reach Acter — a program's query travelling as data over SSH, past any
ConPTY — is still answered and written back exactly as before. That path is untouched, and
it is where a ledger would belong if one is ever needed.

## Decision 7 — one cancel byte ahead of a line submitted at a prompt

The submitted line is preceded by a bare escape when the far end is a shell Acter injected
cmd's prompt into, the tracker's region is `Prompt` or `CommandLine`, and this line is the
only one queued.

**Measured, same session:** `cmd.exe`'s line editor treats a bare escape as "discard the
pending line", erases the queued characters and runs `echo acter-second-line`, which prints
`acter-second-line`. Without it the shell answers
`'s not recognized as an internal or external command,`. A control run with nothing queued
shows the byte is harmless: the line runs normally.

**It is written on its own, never joined to the line.** ConPTY translates input bytes into
key events, and an escape immediately followed by a letter is `Alt`+that letter rather than
a bare escape — sent as one write the line was still rejected, and sent as its own write it
runs. The same distinction explains the whole defect: an escape followed by `[` is the start
of a sequence and is echoed as the literal characters it is made of, which is why an unread
cursor-position answer sits in the buffer as `^[[3;1R` instead of quietly cancelling
anything.

**The two gates, and both are load-bearing.**

*The shell is one whose line editor does this.* Escape clearing the line is `cmd.exe`'s
behaviour, not a universal; a POSIX shell's reader takes it as a meta prefix. That is
`ShellAdapter`'s knowledge and B5's port, and until then the marker declaration is the only
thing that says which shell this is — it says it exactly, because the declaration and the
injection are set together.

*The shell is reading a line.* An escape reaching a program that reads raw input is a
keypress. `Prompt` or `CommandLine` is exactly "the prompt has been drawn and nothing has
said output began". **This is what makes 22.5 the precondition for 22.11 rather than a
neighbour of it**: without markers there are no regions and the question has no answer.
Inside a REPL, a nested shell or a container the region is `Output` — the proxying command
never ended — so the gate stays shut and those far ends are untouched.

## Decision 8 — Acter's own answers are never spoken, and where that reaches

In a marked cmd session the caret text lands in `B..C`, which `wants` excludes, so it is
never block content; and the cancel erases it from the row before the block's heading is
read, so the heading is clean too. Both measured.

**Where markers do not reach it is not fixed**, and the original spec's mechanism for that —
withholding a fragment that could be one of our own answers — was removed with the ledger,
because the bytes are not ours to recognise. A nested shell or a container can still put
caret text in the buffer. Recognising it there would mean matching a *shape* rather than
bytes we wrote, which is a different decision from the one this PR was scoped to; it is
recorded in ROADMAP as what is left of 22.11.

## Decision 9 — the fake shell learns the same line discipline

`TranscriptShell` now discards everything pending on the line when a bare escape arrives,
and echoes nothing for it, because that is what the shell it stands for was measured to do.
An escape followed by `[` still accumulates, which keeps a device-query answer a
device-query answer.

Modelled rather than skipped: without it the scripted far end echoed the cancel back, the
emulator took the escape and the letter after it for one sequence, and a submitted `dir`
came back as `ir`.

## Definition of done

- A tracker under `PromptAndCommandLine` opens a block at the end of the echoed line, for a
  wrapped line, for a command with no output, and never for an empty submission.
- A tracker under `Full` behaves exactly as it does today, property tests included.
- A cmd session started with the injected prompt produces, per command: a block whose
  heading is the command line, whose content is the output followed by the returning
  prompt, and which closes.
- The prompt is spoken after every command in a cmd session.
- A submission following an unread device-query answer runs, in a real shell.
- That answer never reaches the buffer as text in a marked session.
- Every session says the same thing when every byte is its own read.
