# B5.6 — the prompt is spoken again in an integrated session

Roadmap entry 23.6. **Found by the user 2026-08-25**, listening to the first real PowerShell
session; specified the same day.

## What regressed, and why

In a session over a shell that marks all four boundaries — PowerShell since 23.2, bash under
WSL since 23.3 — the prompt is never read. Not after a command, not at all.

That matters because the prompt is not decoration. It is where a terminal user learns the
working directory, the git branch, the virtualenv, and whatever else their own prompt puts
there. The user's words: it "says me where I am, git branch, and everything else". A sighted
user reads it constantly without noticing; a listener currently cannot hear it at any point.

`SessionService::wants` decides what a block accepts, and it decides by marker set:

- `PromptAndCommandLine` (cmd) accepts `Output` **and** `Prompt`, with a comment naming
  22.12: with no `D` there is no verdict, so the returning prompt is the only ending such a
  session has.
- `Full` accepts `Output` alone, on the reasoning that `D` replaces it.

**The reasoning is half right, and that is the whole defect.** `D` replaces the prompt as an
*ending signal*. It replaces nothing about what the prompt *says*. Those were two different
jobs the same bytes were doing, and only one of them was handed over. So the better the
integration, the less the listener hears — exactly backwards.

## Decisions

### 1. The prompt is its own event, not block content

`SessionEvent::PromptDrawn { text }`, emitted when the prompt region is complete.

**Not by adding `Region::Prompt` to `wants`**, which is the one-line change and the wrong
one. Block content is `C..D` by DESIGN's echo exclusion, and a prompt admitted there would
arrive *inside* a block, before its verdict, reading as though the shell had printed it as
output. The prompt is not output. It is the state the next command will run in, and it
deserves a shape that says so.

It also keeps cmd untouched: a `PromptAndCommandLine` session already speaks its prompt as
content, for 22.12's reasons, and emitting this event there as well would say everything
twice. This event is for shells whose prompt has nowhere else to go.

### 2. It arrives after the verdict, because that is the order a listener needs

A6 decision 2's rule, applied again: the announcement about what happened comes before
anything about what happens next. A command that failed says its output, then
`command failed, exit code 3`, and only then the new prompt. That falls out of the byte order
— the shell draws its next prompt after `D` — but it is stated here so a later change cannot
quietly reverse it.

### 3. Every prompt, not only the ones that changed

The user asked to hear the prompt after each command, and that is what a terminal does.

**The alternative was considered and rejected for now**: announcing only when the prompt
*differs* from the last one would spare somebody running twenty `git status` calls from
hearing the same directory twenty times. It is cheap to build — the pump already keeps the
last prompt — and it is a real refinement, but it makes the product quieter than the terminal
it replaces in exactly the case where a user is working fast and relying on rhythm. If the
repetition proves tiring in use, it becomes a setting rather than a silent default, and this
spec is where that conversation starts.

### 4. The first prompt counts

A session's opening prompt is drawn before any command has run, and it is the first thing a
sighted user sees. It is announced the same way, so a listener starts the session knowing
where they are rather than having to run a command to find out.

### 5. It goes in the buffer, as its own thing

The buffer is where a listener reviews what happened, so a prompt that is spoken and not kept
is a fact they cannot go back to. It is rendered as its own element between blocks — not a
heading, because heading navigation is how a listener walks *commands* and inserting prompts
into that sequence would double its length and break the rhythm B4.4 and A5 were built for.

## Amendment A — a prompt with no command between it and the last is a repaint

**Made 2026-09-02, for roadmap 28.10, in the PR that fixes it.** Decision 3 stands as
written for the case it was written about; what follows narrows the word "every".

`readline` re-emits the whole prompt string on every redraw, invisible parts included. An
integrated session's `PS1` is where Acter puts its markers, so a redraw sends `A`, the
prompt and `B` again — and `Pump::drawn` treats each one as a prompt being drawn. Measured
2026-09-02 at a real `bash` under WSL with Acter's own setup sourced into it: two Tabs at
`cd a` produced a second `PromptStart`, and the prompt was announced again over a line the
user was in the middle of editing. It happens on every Tab, every history recall and every
`Ctrl+L`, and only in an integrated session — an unwrapped `PS1` carries no markers, which
is why the user found this worked unintegrated and not integrated.

**A prompt drawn with nothing having happened since the last one is that same prompt being
repainted, and is not announced again.** A command starting or ending is what makes the next
prompt news; between two prompts with neither, the far end has repainted the one already
standing.

**Told apart by what happened in between, never by the text.** An ending prompt is usually
identical to the one before it — `git status` twice in one directory draws the same string —
so "announce it when it differs" would take away exactly what decision 3 protects, and it
stays rejected. It is pinned from both sides:
`the_same_prompt_after_a_command_is_still_announced`, where the text repeats and the
announcement repeats with it, and `a_completion_redraw_does_not_announce_the_prompt_again`,
built from the captured Tab-Tab batch.

Decision 5 follows the announcement: a repaint does not go into the buffer either, so a
listener's transcript does not gain a prompt row per Tab.

## Files touched

- `crates/acter-core/src/entities/protocol_events.rs` — the new event.
- `crates/acter-core/src/services/session.rs` — emitting it when the prompt region completes;
  the pump already tracks the prompt text to strip it from echoes, so what is added is the
  emission rather than the knowledge.
- `ui/src/protocol.ts` — the mirrored type.
- `ui/src/controllers/app.ts` — announcing it and putting it in the buffer.
- `ui/src/adapters/buffer.ts` — rendering it as its own element.
- Tests in each, plus a real-shell assertion and an E2E one.

## Definition of done

- [ ] A `Full` session emits the prompt when it is drawn, including the session's first.
- [ ] A `PromptAndCommandLine` session does not emit it, and cmd's behaviour is unchanged.
- [ ] The event arrives after `CommandFinished` and after any `Announce { Failed }`.
- [ ] The frontend announces the prompt and renders it into the buffer as its own element.
- [ ] Heading navigation still walks one heading per command, with prompts not among them.
- [ ] Unit tests in the domain, vitest for the frontend, a real-shell test against a live
      PowerShell, and an E2E test.
- [ ] `cargo fmt`, `cargo clippy --workspace --all-targets`, workspace tests, vitest and E2E
      all clean.

## Accessibility checklist for the PR body

- [ ] After a command finishes, the prompt is read, and it is read *after* the verdict.
- [ ] The prompt at session start is read without running anything.
- [ ] The prompt is in the buffer and can be reviewed after the fact.
- [ ] Heading navigation still moves command to command.
